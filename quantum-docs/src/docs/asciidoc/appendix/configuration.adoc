[[configuration]]
=== Configuration Reference

This appendix explains key configuration properties used in Quantum applications, organized by functional area.

==== Configuration Basics

===== File Locations
- `src/main/resources/application.properties` - main configuration
- `src/test/resources/application.properties` - test overrides
- `.env` file - local development secrets (not committed)

===== Profiles and Environment Variables
[source,properties]
----
# Profile-specific properties
%dev.com.b2bi.jwt.duration=7200
%test.quarkus.mongodb.database=test-db
%prod.quarkus.log.level=WARN

# Environment variable substitution
quarkus.mongodb.connection-string=${MONGODB_CONNECTION_STRING:mongodb://localhost:27017/?replicaSet=rs0}
postmark.api-key=${POSTMARK_API_KEY}
----

===== Precedence
System properties > Environment variables > application.properties

==== Database Configuration

===== MongoDB Connection
[source,properties]
----
# Basic connection (a replica set; see the note below)
quarkus.mongodb.connection-string=mongodb://localhost:27017/?replicaSet=rs0
quarkus.mongodb.database=my-app

# With authentication
quarkus.mongodb.connection-string=mongodb://user:pass@host:27017/database?authSource=admin

# Disable dev services (use real MongoDB)
quarkus.mongodb.devservices.enabled=false
----

NOTE: MongoDB must run as a replica set, even with a single node. Migrations, reference-checked deletes and TBox activation use multi-document transactions, which a standalone `mongod` does not support. See xref:{doc-root}/user-guide/testing.adoc[Testing] for a single-node replica set you can start locally.

===== Morphia Configuration
[source,properties]
----
# Database and package scanning
quarkus.morphia.database=my-app-db
quarkus.morphia.packages=com.example.model,com.example.entities

# Schema management
quarkus.morphia.create-caps=true
quarkus.morphia.create-indexes=true
quarkus.morphia.create-validators=true
----

==== Authentication Configuration

===== JWT Provider
[source,properties]
----
# Enable JWT authentication
quarkus.smallrye-jwt.enabled=true
auth.provider=custom

# JWT validation
mp.jwt.verify.publickey.location=publicKey.pem
mp.jwt.verify.issuer=my-app
mp.jwt.verify.audiences=my-app-users

# Access-token lifetime in seconds (required by quantum-jwt-provider; no default)
com.b2bi.jwt.duration=3600

# Signing keys (required outside the dev and test profiles; see below)
quantum.jwt.private-key-location=${JWT_PRIVATE_KEY_LOCATION}
quantum.jwt.public-key-location=${JWT_PUBLIC_KEY_LOCATION}
----

The `quantum-jwt-provider` module (`CustomTokenAuthProvider`, `TokenUtilsConfigurer`) reads these keys:

[cols="2,1,3"]
|===
|Property |Default |Description

|`auth.provider`
|`custom`
|Comma-separated, ordered list of authentication provider names. The first name is the default provider. A name only works when a matching `AuthProvider` bean is on the classpath; `custom` is the provider in `quantum-jwt-provider`.

|`mp.jwt.verify.issuer`
|— (required)
|Issuer written into tokens this service mints and expected on tokens it verifies.

|`com.b2bi.jwt.duration`
|— (required)
|Access-token lifetime in seconds.

|`quantum.auth.refresh-token.duration`
|`604800` (7 days)
|Refresh-token lifetime in seconds. It is never shorter than the access token's lifetime. Each refresh issues a new refresh token.

|`quantum.auth.session.max-duration`
|`2592000` (30 days)
|Longest a session can be kept alive by refreshing, in seconds, counted from sign-in. The last refresh token is cut short to this deadline; after it the user signs in again. A value smaller than the refresh-token lifetime is rejected.

|`quantum.jwt.private-key-location`, `quantum.jwt.public-key-location`
|`privateKey.pem` / `publicKey.pem` on the classpath (dev and test only)
|Where the signing key pair is read from. Outside the non-production profiles both must be set explicitly; startup fails rather than fall back to the default keys.

|`quantum.jwt.signing-enabled`
|`true`
|Set `false` on a resource server that only verifies tokens (through SmallRye JWT and a JWKS URL) and never mints them. No issuer key is loaded.

|`auth.jwt.key-id`
|unset for signing; `quantum-auth` at the JWKS endpoint
|The key id (`kid`). When set, signed tokens carry it (`TokenUtilsConfigurer`); when unset, `TokenUtils` uses the private-key location as the `kid`. The OAuth server's JWKS endpoint (`JwksResource`) publishes this value and defaults to `quantum-auth`, so the two disagree unless it is set. Set it explicitly on any issuer whose tokens are verified through its JWKS.
|===

The password encoder for locally stored credentials (`PBKDF2Encoder`) needs three values with no defaults: `com.ard333.quarkusjwt.password.secret`, `com.ard333.quarkusjwt.password.iteration` and `com.ard333.quarkusjwt.password.keylength`.

===== Other providers

`auth.provider` can name more than one provider (for example `custom,oidc`). This repository ships only the `custom` provider; an OIDC or cloud identity provider is a separate module with its own configuration keys. Standard Quarkus OIDC settings (`quarkus.oidc.*`) are documented in the Quarkus OIDC guide. See xref:{doc-root}/user-guide/multiple-auth-providers.adoc[Multiple Authentication Providers] for provider selection and issuer resolution.

===== Request security and sessions

These keys are read by `SecurityFilter` and its collaborators in `quantum-security-runtime`. All are optional.

[cols="2,1,3"]
|===
|Property |Default |Description

|`quantum.security.filter.enforcePreAuth`
|`true`
|Checks the rules for the request's functional area, functional domain and action in the request filter, and denies the request before the resource method runs when the result is not `ALLOW`.

|`quantum.auth.trust-token-claims`
|`false`
|Delegated identity. When `true`, the configured claims provider validates the bearer token and supplies its claims before any local identity repository is read, so the service does not need its own credential database. `false` keeps local-credential behaviour.

|`quantum.auth.principal-source`
|unset
|Unset keeps the local principal construction. `remote` resolves every verified bearer through a `RemotePrincipalSource` bean: the token only identifies the caller (an _identity-only token_) and the directory owner returns roles and tenancy. Startup fails (typed `PrincipalSourceConfigurationException` codes) if `remote` is set without exactly one source bean, without an application id, together with `quantum.security.session.realm` or `quantum.security.session.selection-policy`, with `quantum.auth.trust-token-claims=true`, with `quantum.auth.expected-audience` or `mp.jwt.verify.audiences`, or with `quarkus.http.auth.proactive=false`. A deployment whose configuration declares `remote` for its profile but whose effective value is overridden to something else also fails (`PRINCIPAL_SOURCE_NOT_REMOTE`).

|`quantum.auth.principal-source.application`
|`configured`
|Which application Auth resolves each caller for in remote mode. `configured` is this service's own (`quantum.security.session.application-id`). `caller` is for a platform service that holds data for other applications, such as the memory plane: each request names its application in the `X-Application-Id` header, and Auth admits the caller to it and resolves their realm, tenant and roles for it, as it would for that application itself. A request that names none is refused (400 `INVALID_REQUEST`); it never falls back to the service's own application, whose id stays required. `caller` without `remote`, or any other value, fails startup (`PRINCIPAL_SOURCE_INVALID`).

|`quantum.security.session.application-id`
|unset
|Application session (opt-in). A user's session runs as this application, whichever application the token was minted for. Roles are resolved for (user, session realm, this application). Also the receiving application id sent to the remote principal source; `quantum.application-registration.application-id` is the fallback there. Service tokens and anonymous requests are unchanged.

|`quantum.security.session.realm`
|unset
|Application session (opt-in). The realm a user's session runs in when the request names none. An explicit `X-Realm` still applies, with its own checks.

|`quantum.security.session.selection-policy`, `quantum.security.session.selection-policy-version`
|unset
|Selects an installed `SessionSelectionPolicy` bean by id and exact version to propose the session realm. Set both or neither. Startup fails when the policy is not installed, is installed more than once, or its version differs. The policy only proposes a realm; authorization still runs in the filter.

|`quantum.security.system-realm.authority-roles`
|`system`
|Roles that allow a delegated token minted for the system realm to adopt the cross-tenant system data domain.

|`quantum.security.anonymous-registration-application`
|`quantum-auth`
|Application id that anonymous registration requests are scoped to.

|`quantum.security.identity-store-realm`
|unset
|Realm that user profiles and user groups are read from. Unset reads them from the request's realm.

|`quantum.security.policy-store-realm`
|unset
|Central realm for policy, functional-area and functional-domain documents. Unset reads policy from the request realm.

|`quantum.security.policy-scope.require-application`
|`false`
|Fail closed when application-scoped policy evaluation has no application id. When `true`, also set `quantum.migration.application-id` so startup migrations have one.

|`quantum.security.group-scope.require-application`
|`false`
|Refuses to save a user group that has no `applicationId`.

|`quantum.security.policy-admission.enabled`
|`false`
|Admission checks on save: a policy's scope and vocabulary are validated, and a functional domain must name a registered application (or `*`). A rule may name the application's own domains, or a domain its application row borrows through `uses` that the owning application holds, with an action the owner declares; a borrowed grant goes to one of the application's declared roles when it declares any, and a wildcard area or domain is admitted only over vocabulary the application owns. A vocabulary refusal is a `PolicyAdmissionRefusedException` whose message starts with its code (`POLICY_TRIPLE_UNDECLARED`, `USES_UNKNOWN`, `POLICY_BORROWED_FOREIGN_ROLE`, `POLICY_WILDCARD_OUTSIDE_APPLICATION`); scope errors (no applicationId or realmRefName, unknown application, no vocabulary) stay plain `IllegalArgumentException`.
|===

Rule evaluation (`RuleContext`) has its own switches:

[cols="2,1,3"]
|===
|Property |Default |Description

|`quantum.security.scripting.enabled`
|`true`
|Allows script conditions in rules.

|`quantum.security.scripting.timeout.millis`
|`250`
|Time limit for one script evaluation.

|`quantum.security.scripting.maxStatements`
|`10000`
|Statement limit for one impersonation script evaluation in the request filter.

|`quantum.security.scripting.allowAllAccess`
|`false`
|Lifts the script sandbox. Leave `false`.

|`quantum.security.rules.requestCache.enabled`
|`true`
|Memoizes permission checks within one request.

|`quantum.security.rules.realmCache.enabled`
|`false`
|Caches each realm's effective rules. When off, a check loads only the policies that match the caller's user id and roles.

|`quantum.security.rules.index.enabled`
|`false`
|Uses a compiled rule index for lookups instead of the list-based cache.

|`quantum.security.rules.index.maxRealms`
|`10`
|Number of realms kept in the rule index and rule cache.

|`security.rules.noResourceFilterPolicy`
|`DEFER`
|How a rule that carries a filter is treated when a single-resource check has no concrete resource. `DEFER` is the legacy-compatible behaviour; `CONSERVATIVE_NA` is strict.
|===

===== Application Registration (optional module)

The `quantum-application-registration` module lets an application announce itself to its environment at startup, so first arrival can install, seed and migrate it. It is inert unless enabled, and requires an `ApplicationRegistrar` implementation on the classpath.

[source,properties]
----
# Off by default; the framework starts identically without this.
quantum.application-registration.enabled=false

# Selects the registrar: matches its getName() OR its fully-qualified class name.
quantum.application-registration.provider=system-manager

# Required when enabled. Never inferred -- a service that guesses its
# environment can register into the wrong one.
quantum.application-registration.application-id=my-app
quantum.application-registration.environment=production

# Realms this application reads and writes, comma separated.
quantum.application-registration.realms=my-app-P1

# Build identity; participates in the already-registered fingerprint.
quantum.application-registration.application-version=1.4.2

# Whether a failed registration stops the service. Defaults to true.
quantum.application-registration.fail-on-error=true
----

Registration is attempted once per fingerprint (application + version + environment + realms). On every later boot the registrar's cheap local check short-circuits it, so a restart costs one indexed read rather than a call to the control plane.

See xref:{doc-root}/user-guide/application-registration.adoc[Application Registration] for the SPI and implementation rules.

===== OAuth Server (optional module)

The `quantum-oauth-server` module uses the same JWT configuration properties listed above (`mp.jwt.verify.issuer`, `mp.jwt.verify.publickey.location`, `com.b2bi.jwt.duration`) and publishes the key id from `auth.jwt.key-id` at its JWKS endpoint (default `quantum-auth`). Set `auth.jwt.key-id` explicitly so the published `kid` matches the one on signed tokens; no other properties are required. The OAuth endpoints (`/oauth/authorize`, `/oauth/token`, `/oauth/jwks`, `/.well-known/openid-configuration`, `/oauth/userinfo`) activate automatically when the module is on the classpath.

OAuth clients are registered in the `oauth_clients` MongoDB collection. Authorization codes are stored in `oauth_authorization_codes` with a 5-minute TTL index for automatic cleanup.

See xref:{doc-root}/user-guide/oauth-server.adoc[OAuth Server Module] for client registration and integration examples.

===== Email Templates (Postmark)
[source,properties]
----
# Postmark API key (required for email delivery)
postmark.api-key=${POSTMARK_API_KEY}

# Default sender address (required for email delivery)
postmark.default-from-email-address=noreply@yourdomain.com

# Optional default recipient address
postmark.default-to-email-address=ops@yourdomain.com

If either property is missing, the `PostmarkEmailSender` logs an info message and skips delivery, allowing development environments to run without Postmark credentials.

Classpath templates are loaded from `templates/email/{templateKey}/` with files `subject.txt`, `body.html`, and `body.txt`. See xref:{doc-root}/user-guide/email-templates.adoc[Email Templates] for details.

==== Quantum Framework Configuration

===== Database Migration
[source,properties]
----
# Migration settings (version and scope are required; they have no default)
quantum.database.version=1.0.0
quantum.database.scope=DEV
quantum.database.migration.enabled=true

# Optional CSV list of additional realms to initialize on startup before seed packs run
quantum.migration.apply.realms=system-com,mycompany-com,test-com
----

Change sets are CDI beans that implement `ChangeSetBean`; they are discovered from the bean container, not from a configured package.

[cols="2,1,3"]
|===
|Property |Default |Description

|`quantum.database.version`
|— (required)
|The schema version this application requires (SemVer). A realm whose stored version is lower fails the migration check until its pending change sets have run.

|`quantum.database.scope`
|— (required)
|Scope label for the migration run (for example `DEV`).

|`quantum.database.migration.enabled`
|`true`
|Read by the per-request migration check, the migration endpoints and the startup runners. `false` turns the request check off, and startup seeding then no longer waits for a migrated database.

|`quantum.migration.apply.realms`
|unset
|Additional realms to initialize on startup before seed packs run. Unset: the system realm is always evaluated, and the default realm when it exists.

|`quantum.migration.application-id`
|unset
|Application id the startup migration runs as. Needed when `quantum.security.policy-scope.require-application=true`; otherwise the migration runs under the system contexts without one.

|`quantum.realm.seed-system-only`
|`false`
|Restricts startup realm resolution (migrations and seeds) to the system realm: the test realm and the default realm are not scanned unless listed explicitly.

|`quantum.baseline-identity.seed-system-only`
|`false`
|Seeds only the cross-tenant system identity at startup and skips the default-tenant and test-tenant administrators and their groups.

|`quantum.database.coordination-database`
|`quantum-coordination-shared`
|Shared database used only for short-lived migration, seed and index-creation locks.

|`quantum.database.index-lock-duration-seconds`
|`300`
|How long the per-realm index-creation lock is held before it expires. It must exceed a cold index build for the largest realm; the expiry exists so that a killed process cannot hold the lock forever.
|===

===== Seed packs (filesystem + classpath)
[source,properties]
----
# Enable seed pack discovery and application on startup
quantum.seed-pack.enabled=true
quantum.seed-pack.apply.on-startup=true

# Filesystem root for seed packs when present in the app repo
# If the path does not exist, the framework still loads classpath seed packs
# contributed by dependencies (e.g., quantum-framework) from resources under seed-packs/
quantum.seed-pack.root=src/main/resources/seed-packs

# Optional CSV filter to apply only specific seed pack names
# Example: quantum.seed.apply.filter=system-initialize,my-tenant
quantum.seed.apply.filter=
----

Further seed settings, all optional:

[cols="2,1,3"]
|===
|Property |Default |Description

|`quantum.seed-pack.apply.realms`
|unset
|CSV list of realms to seed on startup. Unset, and with no flagged catalog realms, the system, default and test realms are used. An empty value or `none` disables the list.

|`quantum.seed-pack.apply.honor-realm-flags`
|`true`
|Adds realms whose catalog record has `applySeedsOnStartup=true` to the startup list. A service that holds the environment's realm catalog sets this `false` so it seeds only `quantum.seed-pack.apply.realms`.

|`quantum.seed-pack.lifecycle`
|`production`
|CSV of pack lifecycles this runtime admits. A pack whose manifest scope is labelled `demo` is applied only when the list includes `demo`. Unlabelled packs count as `production`.

|`quantum.seed-pack.scopes.enabled`
|`false`
|Enforces the manifest scope `type` (global, per tenant, tenant list) and its realm include/exclude lists. The lifecycle check above applies whether or not this is set.

|`quantum.seed.conflict-policy`
|`SEED_WINS`
|What happens when a dataset that was applied before has a different checksum now. `SEED_WINS` applies it again, `EXISTING_WINS` skips it with a warning, `ERROR` fails.

|`quantum.seed.batch.size`
|`1000`
|Records written per batch.

|`quantum.seed.discovery.cache-ttl-seconds`
|`60`
|How long discovered pack descriptors are cached.

|`quantum.seed.discovery.parallel`
|`true`
|Scans seed sources in parallel.

|`quantum.seed.file-uri.enabled`
|`false`
|Allows the filesystem seed source to open seed content through `file:` URIs. Off by default; such a request fails.

|`quantum.identity-contribution.vocabulary-enforcement`
|`WARN`
|How an identity pack's vocabulary diagnostics are enforced when the pack is applied. `WARN` logs them and loads the pack; `REFUSE` refuses it. Declaration errors refuse the pack in both modes. See xref:{doc-root}/user-guide/seed-packs.adoc[Seed packs].

|`quantum.refname.legacy-allowed.<EntityName>`
|unset
|CSV of non-canonical refNames that framework writes may still create for a `@CanonicalRefName` entity (for example `quantum.refname.legacy-allowed.UserGroup`). Client-supplied writes are always refused these names.
|===

[NOTE]
====
Classpath seed loading: The framework automatically discovers seed packs packaged
under `seed-packs/` on the application classpath (including JAR dependencies).
Apps depending on the framework no longer need to copy framework seeds locally
or reference absolute file paths. If both filesystem and classpath contain seed
packs with the same name, the latest semantic version is applied.
====

===== Bootstrap packs
[source,properties]
----
# Enable BootstrapPack infrastructure
quantum.bootstrap-pack.enabled=true

# Apply discovered bootstrap packs on startup
quantum.bootstrap-pack.apply.on-startup=false

# Optional CSV list of realms to target on startup
# If omitted, the framework uses the system/default/test realms when available
quantum.bootstrap-pack.apply.realms=system-com,mycompany-com,test-com

# Optional CSV filter to apply only selected pack refs
quantum.bootstrap-pack.apply.filter=pack-a,pack-b
----

[NOTE]
====
Bootstrap packs are not the same thing as seed packs.

- Use seed packs for deterministic baseline data.
- Use bootstrap packs for idempotent operational setup steps.

See xref:{doc-root}/user-guide/bootstrap-packs.adoc[Bootstrap Packs] for details.
====

===== Realm and Tenant Configuration

The values below are the defaults in `EnvConfigUtils`. Override them for your deployment.

[source,properties]
----
# System realm
quantum.realmConfig.systemRealm=system-com
quantum.realmConfig.systemTenantId=system.com
quantum.realmConfig.systemOrgRefName=system.com
quantum.realmConfig.systemAccountNumber=0000000000
quantum.realmConfig.systemUserId=system@system.com

# Default realm
quantum.realmConfig.defaultRealm=mycompanyxyz-com
quantum.realmConfig.defaultTenantId=mycompanyxyz.com
quantum.realmConfig.defaultOrgRefName=mycompanyxyz.com
quantum.realmConfig.defaultAccountNumber=9999999999
quantum.realmConfig.defaultUserId=test@mycompanyxyz.com

# Anonymous user
quantum.anonymousUserId=anonymous@system.com
----

The baseline identity created at startup takes its passwords from `quantum.defaultSystemPassword` and `quantum.defaultTestPassword`. Both have built-in development defaults; set your own values in every deployed environment.

===== Agent tools per realm

The default `TenantAgentConfigResolver` in `quantum-mcp-server` reads optional per-realm settings. The realm id is part of the key. In this release they shape tool discovery only; none of them restricts execution. `AgentExecuteHandler` (`POST /api/agent/execute`) and the MCP tools do not read them, so execution always runs as the authenticated caller with that caller's permissions. Use permission rules to restrict what a caller may do.

[cols="2,3"]
|===
|Property |Description

|`quantum.agent.tenant.<realm>.runAsUserId`

==== Ontology Configuration (optional)

Enablement

The ontology is enabled by adding the ontology modules (`quantum-ontology-core`, `quantum-ontology-mongo`, `quantum-ontology-policy-bridge`) to the application; there is no master switch property. With the modules present, repository saves materialize edges automatically:

[source,properties]
----
# Materialize ontology edges when an entity is saved or deleted (default: true)
ontology.auto-materialize=true
----

TBox Persistence

[source,properties]
----
# Persist each TBox built from sources to MongoDB (default: true). The persisted TBox is the
# version history and the baseline of the stable-relation check; it is not served in place of
# the sources, so annotation, entity and YAML changes all take effect on the next build.
quantum.ontology.tbox.persist=true

# Stable-relation check of a TBox built from sources against the last one built (default: enforce).
# enforce refuses a build that breaks a stable relation without a pack version bump; warn logs it.
quantum.ontology.stable-diff=enforce

# How long a refused build is rethrown before the sources are scanned again (ms, default 30000).
quantum.ontology.stable-diff.retry-after-ms=30000

# The application whose builds are each other's baseline (default: quarkus.application.name).
# quantum.ontology.tbox.builder=orders-app

# No longer has an effect: the TBox is always built from sources.
# quantum.ontology.tbox.force-rebuild=false

# Package scanning for @OntologyClass and @OntologyProperty annotations
quantum.ontology.scan.packages=com.example.model,com.example.entities
----

Runtime limits and switches

[cols="2,1,3"]
|===
|Property |Default |Description

|`quantum.ontology.chain-propagation.max-rederivations`
|`1000`
|Upper bound on the entities one write re-derives while propagating a property chain backwards. When the bound is reached, propagation stops, an error is logged, and the remaining derived edges stay stale until `DriftRepairJob` or a reindex runs.

|`quantum.ontology.expand.max-targets`
|`1000`
|Most distinct targets `expand(@relation)` hydrates for one page of results. A larger expansion is refused.

|`quantum.ontology.expand.max-edges`
|`10000`
|Most edges `expand(@relation)` reads for one page and relation before it is refused.

|`quantum.ontology.rule-edge-scope`
|`DATA_DOMAIN`
|How far a permission rule's `hasEdge` / `hasIncomingEdge` lookups reach. `DATA_DOMAIN`: the caller's whole DataDomain. `ACCOUNT`: any tenant of the caller's organisation, account and data segment, for applications whose tenants share one realm. Only rule lookups are widened, and only for reads.

|`quantum.ontology.cache.staleness-check-interval-ms`
|`5000`
|How often a cached realm registry is checked for a newer activated TBox on another instance. `0` checks on every read; a negative value never checks.

|`quantum.ontology.rule-vocabulary-validation.enabled`
|`true`
|Refuses a policy whose scripts or filters use ontology predicates the registry does not declare.

|`quantum.ontology.functional-domain-validation.enabled`
|`true`
|Checks a policy's functional domain and action against the registered functional domains.

|`quantum.ontology.provenance.split`
|`false`
|Stores edge provenance in a side collection instead of on the edge document.

|`quantum.ontology.publish-to-service`
|`false`
|Publishes the TBox built from sources to a central ontology service. Uses `quantum.ontology.service.base-url`, `.token`, `.realm` (default: the default realm), `.auto-activate` (default `true`) and `.pack-id` (default `annotation-derived`).

|`feature.ontologyList.aggregation.enabled`
|`false`
|Lets list endpoints of ontology-aware resources run `expand` through the governed aggregation path.
|===

Registry modes

- In-memory (recommended to start): build a TBox in code/resources and instantiate OntologyRegistry.inMemory(tbox).
- Mongo-backed (advanced): load a TBox from a Mongo collection and cache it in memory for hot reload/versioning.
- Persisted TBox (recommended for production): each TBox built from sources is persisted to MongoDB as history and as the baseline of the stable-relation check.

Edges collection and indexes

- The MongoDB `edges` collection (the collection name of the `OntologyEdge` entity) supports open edge qualification via compound indexes:
  - `idx_domain_p_dst_props`: `{ "dataDomain": 1, "p": 1, "dst": 1, "props": 1 }` -- optimizes `hasEdge` / `srcIdsByDst` lookups.
  - `idx_domain_src_p_props`: `{ "dataDomain": 1, "src": 1, "p": 1, "props": 1 }` -- optimizes `hasIncomingEdge` / `dstIdsBySrc` lookups.
- Inferred edges carry `inferred: true` with provenance and timestamp metadata for maintenance and TTL eviction.

Materialization hooks

- Use `OntologyMaterializer` to recompute inferred edges when entities change (sources and intermediates for your property chains).

==== Control-plane split (deployment mode)

[cols="2,1,3"]
|===
|Property |Default |Description

|`quantum.mode`
|`embedded`
|Deployment mode of the control-plane split. `embedded`: the app owns its
system realm — system-realm migrations, baseline identity, seeds, and
bootstrap packs run locally (today's behavior, wp3 tiers 0/1). `remote`: the
control plane owns the system realm; this app skips system-realm startup
work while app-realm work runs locally (tier 2). Unknown values fail loud at
startup.

|`quantum.directory.mode`
|unset (older routing)
|Where the realm catalog and memberships live, together: `local` (this
deployment's system realm) or `remote` (the environment's directory owner,
`quantum-auth-service` in the centralized-Auth reference architecture).
Independent of `quantum.mode`: an embedded service with `remote` keeps its
own system realm for its own records and reads realms and memberships from
Auth. Unset, memberships follow `quantum.mode` and the catalog follows
`quantum.system.directory.mode`, exactly as before.

|`quantum.directory.base-url`
|—
|The directory owner's endpoint. Required when the directory is remote
(startup fails loud without it). Falls back to
`quantum.system-service.base-url`.

|`quantum.directory.token`
|—
|Service bearer for directory calls made outside a request (startup). The
caller's own bearer is used inside a request. Falls back to
`quantum.system-service.token`.

|`quantum.system-service.base-url`
|—
|Deprecated for the directory: use `quantum.directory.base-url`. Still read
as its fallback for one release, with a startup warning when the directory
mode is set.

|`quantum.system-service.token`
|—
|Older key for the service bearer. Still read as the fallback of `quantum.directory.token`.

|`quantum.system.directory.mode`
|follows `quantum.mode`
|Deprecated: use `quantum.directory.mode`. Overrides the realm catalog alone
(`local`/`remote`); memberships still follow `quantum.mode`. Ignored when
`quantum.directory.mode` is set.

|`quantum.system-rest.enabled`
|`true`
|Build-time switch over the control-plane admin REST surface
(`/admin/tenants*`, `/security/realm*`, `/security/realm-memberships`,
`/admin/seeds`, `/system/migration`, `/admin/bootstrap-packs`,
`/onboarding/*`). `false` removes all nine resources at build — the tier-1
hardening that replaces per-type `quarkus.arc.exclude-types` lists, and what
a tier-2 tenant-plane app sets.
|===
