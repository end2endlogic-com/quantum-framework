[[oauth-server]]
=== OAuth Server Module

The `quantum-oauth-server` is an optional module that turns any Quantum application into an OAuth 2.0 authorization server with discovery and user-info endpoints. When added, your application exposes standard OAuth endpoints (`/oauth/authorize`, `/oauth/token`, `/oauth/jwks`, `/.well-known/openid-configuration`, `/oauth/userinfo`) so external clients can authenticate using industry-standard OAuth flows without a separate identity provider.

This is the complement to an OIDC auth provider: such a provider lets Quantum *consume* tokens from an external IdP, while this module lets Quantum *issue* tokens itself.

The module authenticates users and clients and issues tokens. It does not grant access: the application named by the client still has to be authorized for the user, and each receiving application authorizes requests from its own records (see xref:{doc-root}/user-guide/auth.adoc#authn-authz-separation[Authentication and Authorization Are Separate]).

==== When to Use

Use `quantum-oauth-server` when:

* You want AI assistant platforms or other external MCP clients to connect to your MCP server via OAuth
* Third-party applications need OAuth-based access to your APIs
* You want a self-contained deployment with no external IdP dependency
* You already manage user identities in Quantum (credentials, user profiles, user groups) and want to leverage them directly

Use an external IdP instead when:

* You need advanced IdP features (social login, MFA, federation, SAML)
* Your organization already standardizes on a specific IdP
* You need to share identities across non-Quantum applications

==== Adding the Dependency

[source,xml]
----
<dependency>
    <groupId>com.end2endlogic</groupId>
    <artifactId>quantum-oauth-server</artifactId>
</dependency>
----

The OAuth endpoints activate automatically via CDI discovery. No additional configuration is needed beyond the standard JWT properties that your application already has. The module has no enable switch of its own: adding the dependency exposes the endpoints.

==== Prerequisites

The module delegates to existing Quantum infrastructure. Ensure your application has:

[source,properties]
----
# These properties are already configured if you use quantum-jwt-provider
mp.jwt.verify.issuer=https://your-app.example.com
mp.jwt.verify.publickey.location=publicKey.pem
com.b2bi.jwt.duration=3600

# Key id advertised by /oauth/jwks and stamped on signed tokens (JWKS default: quantum-auth)
auth.jwt.key-id=quantum-auth
----

`mp.jwt.verify.issuer` is also the base URL the discovery document builds its endpoint URLs from, so it must be the externally reachable address of the service.

==== Endpoints

[cols="2,1,1,4", options="header"]
|===
| Endpoint | Method | Auth | Description

| `/.well-known/openid-configuration`
| GET
| Public
| OIDC discovery document. Returns issuer, endpoint URLs, supported grant types, signing algorithms, and scopes. OAuth clients use this for auto-configuration.

| `/oauth/jwks`
| GET
| Public
| JSON Web Key Set. Serves the RSA public key (from your configured key location; `quantum-default-keys` in development only) in JWK format, with the key id from `auth.jwt.key-id`, so clients and resource servers can verify token signatures.

| `/oauth/authorize`
| GET
| Public
| Authorization endpoint. Validates the client and request parameters, then presents a login form to the user. Supports PKCE with S256 code challenge method.

| `/oauth/authorize`
| POST
| Public
| Processes the login form submission. Authenticates the user via `AuthProviderFactory`, generates a short-lived authorization code (5-minute TTL), and redirects back to the client with `?code=XXX&state=YYY`. The code records the user's password revision at sign-in, so the session it starts ends with the user's next password change like any other.

| `/oauth/token`
| POST
| Public
| Token endpoint. Exchanges credentials or codes for access and refresh tokens. Supports `authorization_code`, `client_credentials`, and `refresh_token` grant types. Accepts client authentication via HTTP Basic or form-encoded `client_id`/`client_secret`.

| `/oauth/userinfo`
| GET
| Bearer
| Returns claims about the authenticated user (`sub`, `iss`, `email`, `preferred_username`, `groups`) extracted from the access token.
|===

==== Supported Grant Types

===== Authorization Code + PKCE

The primary flow for browser-based OAuth clients (AI assistant platforms, web applications).

[source,text]
----
1. Client redirects user to:
   GET /oauth/authorize?response_type=code
       &client_id=my-client
       &redirect_uri=https://client.example.com/callback
       &scope=openid+profile+email
       &state=random-state
       &code_challenge=BASE64URL(SHA256(code_verifier))
       &code_challenge_method=S256

2. User sees login form, enters credentials

3. Server authenticates user, generates authorization code,
   redirects to:
   https://client.example.com/callback?code=XXXXX&state=random-state

4. Client exchanges code for tokens:
   POST /oauth/token
   Content-Type: application/x-www-form-urlencoded

   grant_type=authorization_code
   &code=XXXXX
   &redirect_uri=https://client.example.com/callback
   &client_id=my-client
   &client_secret=my-secret
   &code_verifier=original-random-verifier

5. Server returns:
   {
     "access_token": "eyJ...",
     "token_type": "Bearer",
     "expires_in": 3600,
     "refresh_token": "eyJ..."
   }
----

===== Client Credentials

For service-to-service integrations where no user interaction is needed.

[source,text]
----
POST /oauth/token
Authorization: Basic BASE64(client_id:client_secret)
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials

Response:
{
  "access_token": "eyJ...",
  "token_type": "Bearer",
  "expires_in": 3600
}
----

For `client_credentials`, the server looks up a `CredentialUserIdPassword` with a `userId` matching the `client_id`. Create this credential when registering the client. Without it the request is refused with `invalid_client`. A public client cannot use this grant (`unauthorized_client`).

===== Refresh Token

[source,text]
----
POST /oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token
&refresh_token=eyJ...
&client_id=my-client
&client_secret=my-secret
----

The response has the same shape as the code exchange and always contains a new refresh token. Three rules from the session model apply (see xref:{doc-root}/user-guide/auth.adoc#session-lifetime[Session lifetime and refresh]):

* `expires_in` is the real remaining lifetime of the returned access token, not the configured duration. Near the session's maximum length (`quantum.auth.session.max-duration`) the token is cut short to the deadline and `expires_in` is smaller.
* Once the session has reached its maximum length, or the user's password has changed since sign-in, the refresh is refused with `invalid_grant` and the user must authorize again.
* The refresh re-checks the credential, its realm and its application grant.

==== Registering OAuth Clients

An `OAuthClient` document must exist in the `oauth_clients` MongoDB collection before a client can authenticate. Create one via the Quantum API, seed packs, or directly in MongoDB.

[cols="1,1,3", options="header"]
|===
| Field | Type | Description

| `clientId`
| String
| Unique client identifier (e.g., `chatgpt-mcp-client`)

| `clientSecretHash`
| String
| Bcrypt hash of the client secret. Use `EncryptionUtils.hashPassword(secret)` to generate.

| `publicClient`
| boolean
| If `true`, no client secret is required (for PKCE-only public clients like SPAs).

| `redirectUris`
| List<String>
| Allowed redirect URIs. The authorization endpoint rejects requests with unregistered URIs.

| `allowedGrantTypes`
| List<String>
| Allowed grant types: `authorization_code`, `client_credentials`, `refresh_token`.

| `allowedScopes`
| List<String>
| Allowed scopes (e.g., `openid`, `profile`, `email`).

| `realm`
| String
| The realm sessions of this client are issued for. The credential must be authorized for it.

| `applicationId`
| String
| The application sessions of this client sign in to. When unset, `clientId` is used as the application id. This requests an application; it does not grant access to it.

| `clientDescription`
| String
| Free-text description of the client.

| `active`
| boolean
| Set to `false` to disable the client without deleting it.
|===

For `client_credentials` grant, also create a `CredentialUserIdPassword` with `userId` matching the `clientId` and `credentialType=OAUTH`:

[source,java]
----
CredentialUserIdPassword cred = CredentialUserIdPassword.builder()
    .userId("chatgpt-mcp-client")
    .subject(UUID.randomUUID().toString())
    .credentialType(CredentialType.OAUTH)
    .roles(new String[]{"user"})
    .domainContext(domainContext)
    .lastUpdate(new Date())
    .build();
----

==== Integration Examples

===== MCP Client Integration

Register your Quantum MCP server in the external MCP client with these settings:

[cols="1,3", options="header"]
|===
| Client field | Value

| Server URL
| `https://your-app.example.com/mcp`

| Authentication
| OAuth 2.0

| Authorization URL
| `https://your-app.example.com/oauth/authorize`

| Token URL
| `https://your-app.example.com/oauth/token`

| Client ID
| Your registered `OAuthClient.clientId`

| Client Secret
| The plaintext secret (hashed version stored in `clientSecretHash`)

| Scopes
| `openid profile email`
|===

When a user connects:

1. The client opens a browser to `/oauth/authorize` with the registered client_id
2. The user sees the Quantum login form and enters their credentials
3. On success, the server redirects back to the client with an authorization code
4. The client exchanges the code for tokens at `/oauth/token`
5. Subsequent MCP tool calls include the access token as a Bearer header
6. Quantum verifies the token (same issuer, same keys) and `SecurityFilter` resolves the user's principal: realm, tenant and roles

===== Other Platforms

The same pattern applies to any platform that supports OAuth 2.0:

1. Register an `OAuthClient` with the platform's callback URL as a redirect URI
2. Provide the discovery URL (`/.well-known/openid-configuration`) or the individual endpoint URLs
3. The platform handles the OAuth flow; Quantum handles authentication and token issuance

===== Service-to-Service (Client Credentials)

For backend integrations that don't involve user interaction:

[source,bash]
----
# Obtain an access token
TOKEN=$(curl -s -X POST https://your-app.example.com/oauth/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=client_credentials" \
  -d "client_id=my-service" \
  -d "client_secret=my-secret" | jq -r '.access_token')

# Use the token to call APIs
curl -H "Authorization: Bearer $TOKEN" https://your-app.example.com/api/...
----

==== Architecture

The module is a thin REST layer over existing Quantum infrastructure:

[cols="1,3", options="header"]
|===
| Existing Component | OAuth Use

| `CustomTokenAuthProvider` (via `TokenUtils`)
| Issues access and refresh tokens at `/oauth/token`, applying the same credential, realm and application checks as sign-in

| `TokenUtils.readPublicKey()`
| Serves the `/oauth/jwks` endpoint

| `AuthProviderFactory.getAuthProvider().login()`
| Validates user credentials during authorization code flow

| `CredentialRepo`
| Looks up user and client credentials

| RSA key pair (`quantum-default-keys`)
| Signs all issued tokens

| `mp.jwt.verify.issuer`
| Populates the discovery document `issuer` field

| `SecurityFilter`
| Builds the principal for the issued tokens on subsequent API calls (same issuer, same keys)
|===

Tokens issued by the OAuth server are standard Quantum JWTs, minted by the same provider code as `/security/login`: the access token carries the same claims. The refresh token additionally carries `oauth_client_id` and can be exchanged only at `/oauth/token` by the client it was issued to.

==== Data Model

Two new MongoDB collections are created:

* **`oauth_clients`** -- registered OAuth clients (persistent, managed by admin)
* **`oauth_authorization_codes`** -- short-lived authorization codes (auto-expire after 5 minutes via MongoDB TTL index)

Both follow standard Quantum patterns (`BaseModel`, realm-scoped, Morphia-managed).

==== Security Considerations

* Store client secrets securely. The `clientSecretHash` uses bcrypt -- never store plaintext secrets.
* Use HTTPS for all OAuth endpoints in production.
* Register specific `redirectUris` per client -- never use wildcards.
* Public authorization-code clients must use S256 PKCE on both GET and form POST. Confidential clients retain the existing no-PKCE flow; any supplied challenge must use S256.
* Authorization codes are single-use and expire after 5 minutes.
* Public clients (`publicClient=true`) cannot use `client_credentials`. Machine clients must be confidential and authenticate with a client secret.
* The login form is minimal by design. For custom branding, override `OAuthAuthorizeResource` in your application.

==== Application grants and client-bound refresh

Token issuance reuses the issuer's credential lifecycle, realm, and application authorization checks. Set `OAuthClient.applicationId` to the intended application; when unset, `clientId` is used as that application's identifier. This mapping requests an application, but does not grant access to it. The credential or its realm assignment must independently authorize the application and realm.

OAuth refresh tokens carry a signed `oauth_client_id` distinct from `azp`. Exchange them only at `/oauth/token` with the issuing client. A different client, an unbound legacy refresh token, and the generic `/security` refresh path cannot refresh that OAuth session. Refresh issuance retains the client binding and revalidates current application and realm grants. Existing unbound OAuth sessions must sign in again after upgrading.

Password authentication rejects missing passwords and credentials with missing or blank password hashes as invalid credentials. Server-verified external identity flows use their separate verified-subject path; they do not make password login valid for a passwordless credential.


==== Compatibility and implementation limits

Public-client authorization requires an unpadded 43-character base64url S256
challenge and `code_challenge_method=S256`. Code exchange requires a matching
43–128 character verifier. Missing or invalid proof is rejected before user
authentication or code consumption. The GET and POST paths use the same
validation. Invalid public machine-grant registrations are refused, and token
exchange also rejects previously stored public registrations requesting
`client_credentials` with the existing `unauthorized_client` error shape.

These are intentional security denial changes. Inventory affected clients before
release; retaining Java signatures does not make unsafe callers compatible.
Existing endpoint signatures, OAuth response records, error envelopes and
confidential no-PKCE flows remain unchanged.

The current token response does not contain an OIDC `id_token`, and the authorize
path does not implement a reusable issuer browser session. Discovery advertising
`openid` is not proof of complete OIDC or cross-application browser SSO. Likewise,
issuing a replacement refresh token does not demonstrate atomic consumption of
the previous token. Session-family rotation, replay protection and negotiated
OIDC remain separate implementation work; do not claim them from these fixes.

For changes to provider contracts, run the pinned released-provider binary probe
in `compatibility/auth-provider/README.md`. It compiles against the released
provider version pinned there and runs unchanged bytecode on the candidate. Its scope is provider linkage and
login-response constructors, not the whole API/ABI or generated SDK matrix.
Run `mvn -pl quantum-oauth-server test` for the resource and Quarkus HTTP checks.
The HTTP fixture mocks the client repository; production persistence, affected
registrations and mixed-version deployment still need their own verification.
