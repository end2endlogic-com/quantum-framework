[[multiple-auth-providers]]
= Multiple Authentication Providers

Quantum supports running multiple authentication providers simultaneously, enabling scenarios such as an internal JWT provider alongside an external OIDC provider.
Providers are registered via a single configuration property. Sign-in tries them in order, and a refresh token is routed to the provider whose issuer matches its `iss` (issuer) claim.

A provider authenticates: it proves who the caller is. It does not decide what the caller may do. Roles, realm and tenant are resolved afterwards from the application's own records (see xref:{doc-root}/user-guide/auth.adoc#authn-authz-separation[Authentication and Authorization Are Separate]).

== How It Works

The `AuthProviderFactory` is the central registry for all configured authentication providers.
At startup it reads the `auth.provider` property, which accepts a comma-separated list of provider names, instantiates each one via CDI, and holds them in an ordered list.

[source,properties]
----
# Single provider (default)
auth.provider=custom

# Multiple providers
auth.provider=custom,oidc
----

=== Provider Resolution

`AuthProviderFactory` offers three lookups:

1. **By issuer** -- `AuthProviderFactory.getProviderForIssuer(String issuer)` iterates through the configured providers and calls `getIssuer()` on each.
The first provider whose issuer equals the given issuer wins. A missing issuer, or one no configured provider matches, throws: routing by issuer fails closed and never falls back to the default provider.
2. **By name** -- `AuthProviderFactory.getProviderByName(String name)` performs a case-insensitive lookup (for example `"custom"` or `"oidc"`).
3. **Default** -- `AuthProviderFactory.getAuthProvider()` returns the first configured provider.
Callers that intentionally want the default provider must request it explicitly.

Where each lookup is used:

[cols="2,3", options="header"]
|===
| Operation | Provider used

| Sign-in (`POST /security/login`)
| The ordered chain from `AuthProviderFactory.getLoginProviders`: the request's `provider` query parameter (a comma-separated ordered list) when present, otherwise the `auth.provider` configuration. Every named provider must be available; configuration errors are not silently skipped. The chain stops at the first provider that authenticates, and also at a definitive application or realm answer (selection required, not authorized, authorization missing), which is not retried against the next provider.

| Refresh (`POST /security/refresh`)
| The provider whose `getIssuer()` equals the refresh token's `iss`.

| Password and user management
| The provider named in the request; otherwise the provider matching the credential's `issuer`; otherwise the default provider. The credential type is checked first (see the authentication guide), so a provider override cannot give a service credential a password.

| Incoming API requests
| Quarkus security verifies the bearer token (signature, issuer, audience, expiry) from the configured `mp.jwt.*` or `quarkus.oidc.*` settings. `SecurityFilter` then builds the principal. With `quantum.auth.trust-token-claims=true` it asks the default provider, which must implement `ClaimsAuthProvider`, for the token's claims.
|===

=== Canonical Identity Service

`CanonicalIdentityService` (`quantum-framework`) is an injectable helper for application code that must validate a token itself and wants one identity shape whichever provider issued it. `SecurityFilter` does not call it; request-time verification is described in the table above.
It has two signatures:

[source,java]
----
// Use the default provider
SecurityIdentity validateAccessTokenCanonical(String token);

// Route to the provider matching this issuer
SecurityIdentity validateAccessTokenCanonical(String token, String issuer);
----

Internally, the service supports two provider interfaces:

* **`ClaimsAuthProvider`** -- a modern SPI where the provider returns a `ProviderClaims` object (subject, roles, attributes).
The service then passes those claims to `IdentityAssembler`, which resolves the userId from the credential store (by subject, then by userId), merges roles from the token, the credential and the user's groups, and builds a canonical `QuarkusSecurityIdentity`. It does not apply realm assignments or application bindings; the principal a request runs as is always the one `SecurityFilter` builds.
* **Legacy `AuthProvider`** -- the provider returns a `SecurityIdentity` directly, and the service normalizes it via `SecurityIdentityNormalizer` (ensuring the principal is always the userId, not the IdP subject).

This means you can mix modern claims-based providers with legacy ones in the same application.

== Configuring `application.properties`

=== Minimal Custom JWT Provider

[source,properties]
----
# Select the custom JWT provider
auth.provider=custom

# Enable SmallRye JWT validation
quarkus.smallrye-jwt.enabled=true

# Public key for token signature verification (classpath resource)
mp.jwt.verify.publickey.location=publicKey.pem

# Issuer claim that tokens must contain
mp.jwt.verify.issuer=https://myapp.example.com/issuer

# Audiences the token must target
mp.jwt.verify.audiences=my-api-client,my-api-client-refresh

# Access-token lifetime in seconds (required by the custom provider)
com.b2bi.jwt.duration=3600

# Optional: refresh-token lifetime and the longest refreshable session, in seconds
# (defaults: 7 days and 30 days)
quantum.auth.refresh-token.duration=604800
quantum.auth.session.max-duration=2592000
----

Tokens are RS256-signed with the key pair described under <<per-tenant-key-pairs,Key Pair Management>>. The `auth.jwt.secret`, `auth.jwt.expiration` and `auth.jwt.refresh-expiration` properties found in older sample configurations are not read by any module in this repository.

=== Adding an OIDC Provider

To add an external OIDC provider alongside the custom provider you need an `AuthProvider` bean for it (named `oidc` in the example) on the classpath. This repository ships the custom JWT provider only; an OIDC provider comes from your application or another module. The `auth.oidc.*` and `aws.cognito.*` keys below belong to that provider and are shown as an example of its configuration, using a hosted OIDC user pool:

[source,properties]
----
# Enable both providers
auth.provider=custom,oidc

# --- Custom JWT provider (unchanged) ---
quarkus.smallrye-jwt.enabled=true
mp.jwt.verify.publickey.location=publicKey.pem
mp.jwt.verify.issuer=https://myapp.example.com/issuer
mp.jwt.verify.audiences=my-api-client
com.b2bi.jwt.duration=3600

# --- OIDC provider ---
quarkus.oidc.enabled=true
quarkus.oidc.auth-server-url=https://cognito-idp.${aws.cognito.region}.amazonaws.com/${aws.cognito.user-pool-id}
quarkus.oidc.client-id=${aws.cognito.clientId}
quarkus.oidc.token.issuer=https://cognito-idp.${aws.cognito.region}.amazonaws.com/${aws.cognito.user-pool-id}
quarkus.oidc.roles.role-claim-path=cognito:groups
auth.oidc.provider-name=oidc
auth.oidc.role-claim-path=cognito:groups
auth.oidc.username-claim=preferred_username

# Cognito environment variables
aws.cognito.user-pool-id=${USER_POOL_ID}
aws.cognito.client-id=${APPLICATION_CLIENT_ID}
aws.cognito.region=us-east-1
aws.cognito.jwks.url=https://cognito-idp.${aws.cognito.region}.amazonaws.com/${aws.cognito.user-pool-id}/.well-known/jwks.json
----

=== Using Another OIDC Provider

The pattern is the same for any provider that publishes OIDC discovery -- configure `quarkus.oidc.*` to point at its discovery endpoint:

[source,properties]
----
quarkus.oidc.auth-server-url=https://idp.example.com/realms/my-realm
quarkus.oidc.client-id=my-client
quarkus.oidc.credentials.secret=${OIDC_CLIENT_SECRET}
quarkus.oidc.roles.role-claim-path=realm_access/roles
----

Quarkus OIDC automatically discovers the `.well-known/openid-configuration` endpoint from the `auth-server-url`, so you do not need to specify individual endpoints for token validation, JWKS, or user info.

== Issuer Resolution in Detail

This is the path `CanonicalIdentityService.validateAccessTokenCanonical(token, issuer)` and the refresh flow take when they route by issuer:

....
Token with an "iss" claim
    |
    v
AuthProviderFactory.getProviderForIssuer(issuer)
    |
    +-- Iterate configured providers:
    |     issuer.equals(provider.getIssuer()) ?
    |       -> yes: use this provider
    |       -> no: try next
    |
    +-- No match, or no issuer: fail (IllegalArgumentException); no default is used
    |
    v
Provider validates the token (CanonicalIdentityService) or refreshes it (refresh flow)
....

Each provider's `getIssuer()` method returns its expected issuer string.
For the custom JWT provider, this is the value of `mp.jwt.verify.issuer`.
For an OIDC provider, it is typically the `auth-server-url` (for example, `https://cognito-idp.us-east-1.amazonaws.com/{pool-id}`).

=== Role Provenance Tracking

The framework tracks the source of every role via `RoleAssignment` (a role plus a set of `RoleSource` values):

[cols="1,3", options="header"]
|===
| Source | Meaning

| `TOKEN`
| Role came from the verified token's claims. Honored only in the realm the token was issued for.

| `CREDENTIAL`
| Flat role stored on the credential record. Applies in every realm the credential can enter.

| `REALM`
| Role granted by the user's `UserRealmRole` assignment for the realm.

| `USERGROUP`
| Role inherited from `UserGroup` membership via the user's `UserProfile`
|===

The effective roles are the union of the sources that apply.
`LoginPositiveResponse` carries a `List<RoleAssignment>` for sign-in and refresh, and `POST /system/permissions/role-provenance` reports the breakdown for a user, so audit tooling can trace where each role originated.

== Creating a New Auth Provider

To add a new authentication provider:

1. Create an `@ApplicationScoped` CDI bean that extends `BaseAuthProvider` and implements `AuthProvider` and optionally `ClaimsAuthProvider` or `UserManagement` as needed.
2. Return a stable name from `getName()` (e.g., `"saml"`, `"apikey"`, `"azure-ad"`).
3. Implement `getIssuer()` to return the issuer string that your tokens will carry.
4. Implement `validateAccessToken(token)` to parse, verify, and build a `SecurityIdentity`.
5. Optionally implement `ClaimsAuthProvider.validateTokenToClaims(token)` for the claims-based flow. It is required when the provider is the default one and the service runs with `quantum.auth.trust-token-claims=true`.
6. Add your provider name to `auth.provider` in `application.properties`.

[source,java]
----
@ApplicationScoped
public class MyOidcProvider extends BaseAuthProvider
        implements AuthProvider, ClaimsAuthProvider, UserManagement {

    @ConfigProperty(name = "my.oidc.issuer")
    String issuer;

    @Override
    public String getName() {
        return "my-oidc";
    }

    @Override
    public String getIssuer() {
        return issuer;
    }

    @Override
    public ProviderClaims validateTokenToClaims(String token) {
        // Validate token against the OIDC provider's JWKS
        // Extract subject, roles, attributes
        // Return ProviderClaims
    }

    // ... implement remaining AuthProvider and UserManagement methods
}
----

Then activate it:

[source,properties]
----
auth.provider=custom,my-oidc
my.oidc.issuer=https://my-idp.example.com
----

See xref:{doc-root}/user-guide/auth.adoc[Authentication and Authorization] for the full `AuthProvider` and `UserManagement` interface contracts and `BaseAuthProvider` capabilities.

== Key Pair Management

=== Default Keys Module (`quantum-default-keys`)

The framework ships a convenience module, `quantum-default-keys`, that places a default RSA key pair (`privateKey.pem` / `publicKey.pem`) on the classpath.
This module is declared as an `<optional>true</optional>` dependency of `quantum-jwt-provider`, so it is available during framework development but does **not** propagate transitively to consuming applications.

To use the default keys in your application during development or testing, add the dependency explicitly:

[source,xml]
----
<dependency>
    <groupId>com.end2endlogic</groupId>
    <artifactId>quantum-default-keys</artifactId>
    <version>${quantum.version}</version>
</dependency>
----

In production, remove the `quantum-default-keys` dependency from your POM and set the key locations explicitly (see below). The configured paths take precedence over any classpath defaults, and a production start without them fails.

WARNING: The default keys are published in the open-source framework repository and are intended only for development and testing.
Never use the default keys in production.
Always generate and deploy your own key pair.

=== Configurable Key Locations

By default, `TokenUtils` loads keys from classpath resources named `privateKey.pem` and `publicKey.pem`.
You can override these locations in `application.properties` to point at external key files:

[source,properties]
----
# Load signing key from the filesystem
quantum.jwt.private-key-location=file:/opt/keys/signing.pem

# Load verification key from the filesystem
quantum.jwt.public-key-location=file:/opt/keys/verify.pem
----

Supported path prefixes:

[cols="1,3", options="header"]
|===
| Prefix | Behavior

| `file:`
| Load from the filesystem (e.g., `file:/opt/keys/signing.pem`)

| `classpath:`
| Load from the classpath (e.g., `classpath:mykeys/signing.pem`)

| _(no prefix)_
| Treated as a classpath resource name (backward compatible with `privateKey.pem`)
|===

When these properties are set, `TokenUtilsConfigurer` applies them at application startup and invalidates any previously cached keys.

`TokenUtilsConfigurer` also enforces three rules at startup:

* Outside the `dev` and `test` profiles both properties must be set explicitly. If either is missing, startup fails with "Production JWT startup requires ... to be explicitly configured; default JWT key fallback is not allowed".
* `quantum.jwt.signing-enabled=false` (default `true`) is for a service that only verifies tokens. It loads no signing key, and the two location properties are not required.
* `auth.jwt.key-id`, when set, is stamped on every signed token as the `kid` header. Set it to the same value the JWKS endpoint advertises so other services can resolve the signing key.

Key material is opened through the `JwtKeyResolver` SPI. The default bean, `DefaultJwtKeyResolver`, handles the `file:` and `classpath:` prefixes above; provide your own `JwtKeyResolver` bean to read keys from another source.

==== Typical Production Setup

[source,properties]
----
# Point at externally managed keys — no quantum-default-keys JAR needed
quantum.jwt.private-key-location=file:/etc/quantum/keys/privateKey.pem
quantum.jwt.public-key-location=file:/etc/quantum/keys/publicKey.pem

# SmallRye JWT validation must also reference the public key
mp.jwt.verify.publickey.location=/etc/quantum/keys/publicKey.pem
----

NOTE: `TokenUtils` handles signing (private key); SmallRye JWT handles verification (public key via `mp.jwt.verify.publickey.location`).
Both must reference the same key pair.
When you move to external keys, update both the `quantum.jwt.*` properties and `mp.jwt.verify.publickey.location`.
