= Permission Resource: Check APIs and Client Usage
:toc: macro
:toclevels: 3

This guide explains how to use the Permission Resource check APIs and how to evaluate the server-produced access decisions on the client using the provided JavaScript library.

All endpoints are under `/system/permissions` (`PermissionResource`, in `quantum-system-rest`). Where this guide writes `/check` or `/check-with-index` it means `/system/permissions/check` and `/system/permissions/check-with-index`.

It covers:

- The `/check` API (server-evaluated permission)
- The `/check-with-index` API (client-evaluable snapshot)
- Request payloads and detailed response structures
- Scope and data-domain fallback behavior
- Using the JavaScript client in a browser, React, or Vue

[NOTE]
This document reflects the current and evolving server behavior. The JavaScript client library is available at runtime from Quarkus as `/security/acl-client.js` and is forward-compatible with the scoped access-matrix format described here.

== Who may inspect permissions

All four inspection endpoints under `/system/permissions` require authentication:
`POST /role-provenance`, `/check`, `/check-with-index`, and `/fd/evaluate`.
A caller may inspect their own request-context `userId` in their request-context
realm. An omitted `realm` uses that context realm, including for role provenance.
The successful response fields are unchanged.

Another identity (including a role name), or a different realm, requires the
framework system principal or a realm administrator of the requested realm.
These are the same authorities used by access-invite management; a token role
named `system` alone or a membership-administrator role is insufficient.
In a pooled/multi-tenant realm the administrator must be authorized for every
tenant on the target's realm assignment and any explicitly requested tenant.
Because these diagnostics expose complete roles rather than a tenant-filtered
projection, missing, empty, or regex-based target tenant scope is refused for
pooled-realm administrators. The system principal may inspect across realms.

For `/check` and `/fd/evaluate`, client-supplied extra `roles` must already be
held in the authenticated request context, unless the caller has the above
administrative authority. `/check-with-index` applies the same validation,
although that endpoint does not add supplied roles to its snapshot.

Unauthorized inspections return HTTP `403` with the standard `RestError` payload
and `errorCode: PERMISSION_INSPECTION_FORBIDDEN`. The code and message are the
same for existing and nonexistent targets. Authorization happens before target
credential, profile, group, or role resolution; pooled scope checks use realm
assignment metadata only after qualifying the caller as an administrator.
Consumers that formerly simulated arbitrary identities, realms, or extra roles
must use an appropriately authorized administrator or restrict requests to self.

=== Role provenance

`POST /system/permissions/role-provenance` accepts `userId` and optional `realm`.
It returns credential/profile presence, credential roles, profile groups, token
roles and mapped groups, net roles, and role-source assignments. The caller
restriction above applies before any of those values are read.

== APIs

Every endpoint requires an authenticated caller (`@Authenticated`): send the bearer token. The checks answer a question about policy ("would this identity be allowed?"); they do not grant anything, and they do not let a caller act as the identity it asks about.

Three inputs are resolved the same way by `/check`, `/check-with-index` and `/fd/evaluate`:

* `applicationId`: policies are evaluated in the scope of one application. It is taken from the request, else from the authenticated caller's principal. When neither names one the call is refused with `400 applicationId is required`.
* `realm`: from the request, else the realm the caller's request runs in, else the framework default realm.
* Roles: when `identity` is a userId, its roles are resolved by `IdentityRoleResolver` for that realm and that application (credential, realm assignment and the groups of that application or `*`, plus token roles when the identity is the caller itself). A group of another application does not count, so the check agrees with what the application itself resolves. `roles` in the request adds roles to evaluate "what if"; it changes no stored grant.

=== GET /system/permissions/fd and /fd/areas: an application's vocabulary

`GET /system/permissions/fd[?includeActions=true]` without `applicationId` answers as before: the union of the vocabulary this service discovers in its own code and every stored `FunctionalDomain`, as `area -> [domain]` (or `area -> domain -> [action]` with `includeActions`).

With `?applicationId=<app>` it answers that application's registered vocabulary only: its `FunctionalArea` rows (an area may hold no domain yet) and its `FunctionalDomain` rows with their declared actions (CRUD when a row declares none). Rows tagged `*` or with another application, and the code discovered in this service, are not part of it. An application this service does not know answers `404 {"code":"APPLICATION_UNKNOWN"}`.

`GET /system/permissions/fd/areas?applicationId=<app>` lists that application's `FunctionalArea` records, sorted by `refName`. `applicationId` is required (`400` without it, `404 APPLICATION_UNKNOWN` for an unknown application).

Both reads apply the caller's rules to the stored rows, the same as `/fd` always has. The rows reach a separate Auth through the application's identity contribution (`/v1/identity-contributions`: submit, activate, apply).

=== POST /system/permissions/check
Performs a server-side permission check for a single request using the named identity and an optional data domain (organization/account/tenant/segment/owner). Data-domain fields that are omitted fall back to the caller's own principal.

.Request
[source,json]
----
{
  "identity": "user-123",
  "realm": "b2bi",
  "applicationId": "acme-orders",
  "area": "security",
  "functionalDomain": "userProfile",
  "action": "view",
  "resourceId": "12345",
  "orgRefName": "acme",
  "accountNumber": "A1",
  "tenantId": "t-001",
  "dataSegment": 0,
  "ownerId": "user-123",
  "roles": ["user", "admin"],
  "scope": "api"
}
----

.Response (example)
[source,json]
----
{
  "finalEffect": "ALLOW",
  "winningRule": "SysAnyActionSecurity",
  "explanations": [
    { "rule": "SysAnyActionSecurity", "effect": "ALLOW" }
  ]
}
----

Notes:
- This endpoint is authoritative and understands scripts/postconditions and any dynamic runtime evaluation.
- Use `/check` when you must account for scripts, context-enriched rules, or when you don’t have the precomputed snapshot.

=== POST /system/permissions/check-with-index
Returns everything one identity may do in one application, in one call, so a client can show or hide
actions without asking again. The backend still enforces every request; the snapshot only decides what
to show.

Each action the application registers (its FunctionalArea and FunctionalDomain rows, as listed by
`GET /fd?applicationId=`) is decided by the rule engine exactly as `/check` decides it: the system rules,
the realm's and the application's policies, rule precedence, wildcard patterns and scripts all count.
Nothing in the snapshot is a guess, so every cell agrees with `/check` for the same identity, realm,
application and data domain.

Only allowed actions are returned. A missing cell means denied.

The application and its vocabulary are read under the caller's own rules, as `GET /fd?applicationId=`
reads them, so tenant isolation and any deny on those records hold. A caller who may not see the
application gets the same `404` as for an unregistered one; a caller who may not list its vocabulary is
refused (`403`). To let people load their own snapshot, grant them, by policy, `VIEW` on
`SECURITY/APPLICATION` and `LIST` on `SECURITY/FUNCTIONAL_AREA` and `SECURITY/FUNCTIONAL_DOMAIN` for
the application's rows.

`applicationId` is required (or taken from the caller's principal). An application that is not
registered, or that the caller may not see, returns `404` with `"code": "APPLICATION_UNKNOWN"`. `area`, `functionalDomain` and `action`
narrow the evaluation when given. `roles` adds no role to the snapshot.

.Request (send data-domain as top-level fields; omitted fields come from the caller's context, and `ownerId` defaults to `identity`)
[source,json]
----
{
  "identity": "user-123",
  "realm": "b2bi",
  "applicationId": "orders-app",
  "orgRefName": "acme",
  "accountNumber": "A1",
  "tenantId": "t-001",
  "dataSegment": 0,
  "ownerId": "user-123"
}
----

.Response
[source,json]
----
{
  "enabled": true,
  "version": 163044986023000,
  "policyVersion": 163044986023000,
  "sources": ["user-123", "user"],
  "requiresServer": false,
  "rules": [],
  "scopes": {
    "org=acme|acct=a1|tenant=t-001|seg=0|owner=user-123": {
      "requiresServer": false,
      "matrix": {
        "orders": {
          "order": {
            "view": { "effect": "ALLOW", "rule": "view-own-orders", "priority": 10, "finalRule": false }
          }
        }
      }
    }
  },
  "requestedScope": "org=acme|acct=a1|tenant=t-001|seg=0|owner=user-123",
  "requestedFallback": ["org=acme|acct=a1|tenant=t-001|seg=0|owner=user-123"]
}
----

Field semantics

- enabled: always true; requiresServer: always false. Every registered action has been decided.
- version / policyVersion: the rule set's version on the server that answered. It is per server and does not
  change when a person's roles or group membership change, so also refresh on a timer and on sign-in.
- sources: the identity and the roles Auth resolved for it in this realm and application. Use these
  instead of reading roles from the token: tokens carry identity only.
- scopes: exactly one scope, the request's data domain, keyed by `requestedScope`. Keys and
  `area → domain → action` names are lower case; look them up lower-cased. Each cell names the winning
  rule, its priority and whether it was final.
- rules: empty. The flat rule list of earlier versions is no longer returned.
- A decision that depends on the record (a rule with a filter or script) is `ALLOW` here when some
  record could be allowed, as `/check` reports it without a resource; the backend decides each record.

[NOTE]
Earlier versions built this snapshot from the system rules alone, so it missed realm and application
policies, and flagged rules it could not represent with `requiresServer`. Clients must now look names up in lower case and use `requestedScope`
rather than widening to other scopes; `acl-client.js` does both. A client that looked names up in their
registered case finds nothing and denies everything, which is safe but hides every action.

== Data-Domain Scope and Fallback

A scope key is a canonical string combining the data-domain dimensions:

```
org=<v>|acct=<v>|tenant=<v>|seg=<v>|owner=<v>
```

- Values are specific strings or `*` for wildcard.
- Fallback traversal order: owner → segment → tenant → account → org → global.

== JavaScript Client Library

NOTE: The browser examples in this guide show only the request body. Every call must also carry the caller's bearer token (`Authorization: Bearer <token>`), and `applicationId` unless the caller's principal already names an application.

The JavaScript client provides helpers to evaluate the snapshot on the client.

- Served by Quarkus at: `/security/acl-client.js`
- Path in repo: `quantum-framework/src/main/resources/META-INF/resources/security/acl-client.js`

.Exported API
[source,js]
----
ACLClient.scopeKeyFromDataDomain(dataDomain) // => scope key string
ACLClient.buildFallbackChain(scopeKey)       // => [scopeKey] (kept for compatibility; one scope is returned)
ACLClient.lookupAreaDomainAction(matrix, area, domain, action) // => Outcome | null
ACLClient.decide(snapshot, dataDomain, area, domain, action)   // => 'ALLOW' | 'DENY'; names match without case
// dataDomain may be null (the snapshot's own data domain). For any other data domain decide is 'DENY'
// and decideOutcome is null: ask /check instead.
ACLClient.decideOutcome(snapshot, dataDomain, area, domain, action) // => Outcome | null
ACLClient.interpretCheckResponse(check)  // => { decision, scope, constraints, filterConstraintsPresent, filterConstraints }
ACLClient.interpretEvaluateResponse(res) // => { allow, deny, decisions, evalModeUsed, getDecision(area, domain, action) }
----

Outcome structure:
[source,json]
----
{
  "effect": "ALLOW",
  "rule": "<winning rule name>",
  "priority": 0,
  "finalRule": true,
  "source": "role:user"
}
----

Allowed effect values are "ALLOW" or "DENY".

== Single-resource check API: evalMode and SCOPED decisions

The `/system/permissions/check` endpoint accepts an optional `evalMode` parameter to control
how the server evaluates filter strings and postcondition scripts in single-resource checks. It also
supports sending a shallow snapshot of a concrete resource instance so that filters can be evaluated
in-memory when appropriate.

Eval modes:

- LEGACY (default):
  * If a concrete resource instance is provided (with `modelClass` and `resource`), the server attempts in-memory
    evaluation of rule filter strings; if filters match and postcondition is true/absent, the decision is `EXACT`.
  * If no resource is provided and a matching rule carries filters and/or scripts, the server returns a `SCOPED`
    decision: the outcome (`ALLOW`/`DENY`) is accompanied by `scopedConstraints` enumerating the applied filters and/or scripts.
  * List endpoints should continue to use `getFilters(...)`/`check-with-index` for DB-side filtering; `SCOPED` simply
    surfaces constraints to the client for transparency.

- AUTO: Same behavior as LEGACY; provided for client clarity.

- STRICT:
  * With a resource present, the evaluator runs. If filter evaluation returns false, the rule is treated as NOT_APPLICABLE.
  * Without a resource for non-LIST actions, matching rules with filters/scripts produce a `SCOPED` candidate (constraints listed)
    instead of being silently allowed/denied. Postconditions are not executed in-memory in this case.
  * LIST is never suppressed; constraints are surfaced.

Request fields (additive):

* `identity` (string, required)
* `realm` (string, optional)
* `applicationId` (string; required unless the authenticated caller's principal already names an application)
* `area`, `functionalDomain`, `action`, `resourceId` (optional; may be wildcard `*` unless doing a specific check)
* `modelClass` (string, optional): fully qualified class name or resolvable entity name
* `resource` (object, optional): shallow JSON snapshot of the domain resource
* `evalMode` (string, optional): `LEGACY` | `AUTO` | `STRICT` (defaults to `LEGACY`)

Response fields (additive and backward compatible):

- `decision` — canonical decision string, mirrors `finalEffect` ("ALLOW"|"DENY").
- `decisionScope` — one of:
  * `EXACT` — fully evaluated in-memory (filters and scripts, when present).
  * `SCOPED` — conditionally applies; `scopedConstraints` lists the filters/scripts that must hold.
  * `DEFAULT` — no rule applied; the decision fell back to the default (`naLabel` will be `NA-ALLOW` or `NA-DENY`).
- `evalModeUsed` — echoes the server-applied eval mode.
- `scopedConstraintsPresent` and `scopedConstraints[]` — present when `decisionScope=SCOPED`.
- `filterConstraintsPresent` and `filterConstraints[]` — legacy-compatible constraint listing; kept for LIST and transition.
- `notApplicable[]` — rules that were considered but did not apply (with phase and reason).
* Winning rule metadata (additive):
  - `winningRuleName`, `winningRulePriority`, `winningRuleFinal` — the rule that produced the decision
    (for `EXACT`), or the selected candidate (for `SCOPED`). These are null for `DEFAULT`.

Example request enabling evaluator:

```
POST /system/permissions/check
{
  "identity": "alice@end2endlogic.com",
  "realm": "b2bi",
  "area": "sales",
  "functionalDomain": "order",
  "action": "update",
  "modelClass": "com.example.domain.Order",
  "resource": { "id": "ORD-123", "customerId": "5f1e1a5e5e5e5e5e5e5e5e51" },
  "evalMode": "STRICT"
}
```

Client usage to interpret the decision:

```
const res = await fetch('/system/permissions/check', { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify(req) });
const check = await res.json();
const out = ACLClient.interpretCheckResponse(check);
if (out.scope === 'EXACT' && out.decision === 'ALLOW') {
  // fully allowed
} else if (out.scope === 'SCOPED' && out.decision === 'ALLOW') {
  // allowed subject to the following constraints (filters/scripts):
  console.log(out.constraints);
} else {
  // denied or default; inspect check.naLabel / check.notApplicable as needed
}
```

== Evaluate API: per-action decisions with SCOPED semantics

The `/system/permissions/fd/evaluate` endpoint classifies an identity’s permissions across discovered
areas/domains/actions and now supports the same `evalMode` and optional `modelClass`/`resource` parameters as `/check`.
When the server cannot fully evaluate constraints for a given action (e.g., no resource supplied), it returns a
`SCOPED` decision for that action along with the enumerated constraints.

Every decision comes from the rule engine (`/check`'s evaluation). `useIndex` is accepted for compatibility
and ignored: it used to answer from a precomputed matrix that could disagree with the engine.

Request (additive parity with `/check`):

```
POST /system/permissions/fd/evaluate
{
  "identity": "alice@end2endlogic.com",
  "realm": "b2bi",
  // Optional narrowing
  "area": "sales",
  "functionalDomain": "order",
  "action": "view",
  // Optional single-resource evaluation controls
  "modelClass": "com.example.domain.Order",
  "resource": { "id": "ORD-123", "customerId": "5f1e1a5e5e5e5e5e5e5e5e51" },
  "evalMode": "STRICT"
}
```

Response (additive):

```
{
  "allow": { ... },
  "deny": { ... },
  "decisions": {
    "sales": {
      "order": {
        "view": {
          "effect": "ALLOW",
          "decisionScope": "SCOPED",
          "scopedConstraintsPresent": true,
          "scopedConstraints": [
            { "type": "FILTER", "detail": "customerId:^[${accessibleCustomerIds}]", "joinOp": "AND" }
          ],
          "naLabel": null,
          "rule": "user-sales-order-view-filter",
          "priority": 100,
          "finalRule": false,
          "source": null
        }
      }
    }
  },
  "evalModeUsed": "STRICT"
}
```

Client usage:

```
const res = await fetch('/system/permissions/fd/evaluate', { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify(req) });
const body = await res.json();
const ev = ACLClient.interpretEvaluateResponse(body);
const decision = ev.getDecision('sales', 'order', 'view');
if (decision && decision.decisionScope === 'EXACT' && decision.effect === 'ALLOW') {
  // fully allowed
} else if (decision && decision.decisionScope === 'SCOPED' && decision.effect === 'ALLOW') {
  // allowed subject to constraints
  console.log(decision.scopedConstraints);
}
```

=== Which rule produced the decision?

`decisions[area][domain][action]` includes `rule`, `priority` and `finalRule` from the winning rule of the
engine's evaluation, as `/check` reports them.

== Behavior matrix (summary)

* With resource present (any mode): evaluator runs. Filters=true and postcondition=true/absent ⇒ `EXACT`.
  Filters=false ⇒ rule is `NOT_APPLICABLE`. Failures to evaluate ⇒ fallback to SCOPED in STRICT, legacy-compatible otherwise.
* Without resource:
  - `LEGACY`/`AUTO`: matching rules with filters/scripts surface as `SCOPED` candidates; constraints listed.
  - `STRICT` (non-LIST): also returns `SCOPED`; postconditions are skipped; constraints listed.
  - LIST is never suppressed; DB-side filters continue via `getFilters(...)`; constraints surfaced for transparency.

== Migration notes

* Prefer `evalMode` over the deprecated `enableFilterEval`. If `enableFilterEval=true` and both `modelClass` and `resource`
  are supplied, the server treats it as `AUTO` for backward compatibility.
* Existing clients that only use `finalEffect` remain compatible. To opt in to richer semantics, read `decision`,
  `decisionScope`, and `scopedConstraints`.
* For list/search pages, continue to rely on DB-side `getFilters(...)` or `check-with-index`; do not pass a resource
  snapshot to `/check` for lists.

== Troubleshooting / FAQs

Q: Why do I get `SCOPED` instead of `EXACT`?
  * A: The server did not have a concrete resource to evaluate, or the predicate engine was not available. Use `STRICT`
     with `modelClass` + `resource` for a fully evaluated decision when applicable.

Q: What is `NA-ALLOW` / `NA-DENY`?
  * A: They are labels for default fallbacks when no rule could make a decision (`decisionScope=DEFAULT`). The value
     mirrors the `finalEffect` chosen as the default.

Q: How do I know which rule produced the result?
  * A: Inspect `winningRuleName`, `winningRulePriority`, `winningRuleFinal` on `/check` responses, or per-action
     `rule/priority/finalRule` in `/fd/evaluate` responses.

=== Using in a Browser (no build tools)

.HTML
[source,html]
----
<script src="/security/acl-client.js"></script>
<script>
  async function canViewProfile() {
    // 1) Get a snapshot for the user
    const res = await fetch('/system/permissions/check-with-index', {
      method: 'POST', headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ identity: 'user-123', realm: 'b2bi', applicationId: 'orders-app', orgRefName: 'acme', accountNumber: 'A1', tenantId: 't-001', dataSegment: 0, ownerId: 'user-123' })
    });
    const snapshot = await res.json();

    // 2) Evaluate locally
    const decision = ACLClient.decide(snapshot, null, 'security', 'userProfile', 'view');
    if (decision === 'ALLOW') {
      // show UI
    } else {
      // hide or show alternative
    }
  }
</script>
----

=== Using in React

.Installation (served by your Quarkus backend)
- No npm package is required; include as an external script in `public/index.html` or via dynamic import.

.React example
[source,jsx]
----
import { useEffect, useState } from 'react';

export default function ProfileButton() {
  const [allowed, setAllowed] = useState(false);

  useEffect(() => {
    async function run() {
      const res = await fetch('/system/permissions/check-with-index', {
        method: 'POST', headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ identity: 'user-123', realm: 'b2bi' })
      });
      const snapshot = await res.json();
      const effect = window.ACLClient.decide(snapshot, null, 'security', 'userProfile', 'view');
      setAllowed(effect === 'ALLOW');
    }
    run();
  }, []);

  if (!allowed) return null;
  return <button>View Profile</button>;
}
----

== Caching Guidance

- Clients should cache the `/check-with-index` response keyed by `(identity, realm, applicationId, data domain)`
  for a few minutes, and drop it on sign-out. `policyVersion` is per server and does not track role or
  membership changes, so it is not enough on its own.

== Troubleshooting

- A missing matrix entry is a `DENY`.
- Ensure `effect` comparisons are case-insensitive on the client (`String(effect).toUpperCase()`).
