[[query-language]]
== Query Language Reference

Quantum uses an ANTLR-based query language, BIAPI (grammar file `BIAPIQuery.g4` in the `quantum-models` module), for filtering, searching, and constraining data across all REST endpoints. This single, consistent syntax works everywhere: list APIs, the Query Gateway, permission rules, and access resolvers.

=== Basic Syntax

==== Operators

[cols="1,2,3"]
|===
|Operator |Symbol |Example

|Equals |`:` |`name:"Widget"`
|Not equals |`:!` |`status:!"DELETED"`
|Less than |`:<` |`price:<##100`
|Greater than |`:>` |`quantity:>#50`
|Less than or equal |`:<=` |`createdDate:<=2024-12-31`
|Greater than or equal |`:>=` |`updatedAt:>=2024-01-01T00:00:00Z`
|Field exists |`:~` |`description:~`
|In list |`:^` |`status:^["ACTIVE","PENDING"]`
|Not in list |`:!^` |`status:!^["DELETED","ARCHIVED"]`
|===

==== Value Types

[cols="1,2,3"]
|===
|Type |Prefix |Example

|String |none or `"..."` |`name:widget` or `name:"Super Widget"`
|Number (integer) |`#` |`quantity:#42`
|Number (decimal) |`##` |`price:##19.99`
|Date |none |`shipDate:2024-12-25`
|DateTime |none |`createdAt:2024-12-25T10:30:00Z`
|Boolean |none |`active:true`
|Null |none |`description:null`
|ObjectId |none |`id:507f1f77bcf86cd799439011`
|Reference |`@@` |`parentId:@@507f1f77bcf86cd799439011`
|Variable |`${...}` |`ownerId:${principalId}`, `tier:^${facet.allowedTiers}`, `zone:${coord.salesZone}`
|===

In-memory scalar equality and inequality preserve stored JSON text when the
query operand is a string, including a typed string variable. For example,
`dataDomain.accountNum:${pAccountId}` matches account `"0000000001"` when the
variable contains that same string, and distinguishes it from `"1"`. This also
applies to equality against elements of JSON arrays. Explicit numeric and date
operands retain their existing comparison behavior.

NOTE: **Dotted Variable Identifiers & Single-Variable IN**: The query grammar admits dotted variable paths (`${facet.<key>}`, `${coord.<key>}`, `${principal.<attr>}`, `${dd.<attr>}`). When paired with the list membership operator (`:^`), a single variable resolving to a Java `Collection` or array (e.g. `allowedTiers = ["TIER_1", "TIER_2"]`) can be passed without brackets (`tier:^${facet.allowedTiers}`), and the query compiler will automatically unpack the elements into a native `$in` evaluation.

==== Logical Operators

[cols="1,2,3"]
|===
|Operator |Symbol |Example

|AND |`&&` |`active:true && price:>##10`
|OR |`\|\|` |`status:"ACTIVE" \|\| status:"PENDING"`
|NOT |`!!` |`!!(price:<##5)`
|Grouping |`()` |`(active:true \|\| featured:true) && price:>##0`
|===

=== Common Patterns

==== String Matching

[source]
----
# Exact match
name:"Super Widget"

# Wildcard matching
name:*widget*        # contains "widget"
name:widget*         # starts with "widget"
name:*widget         # ends with "widget"

# Case sensitivity: string matches ignore case unless ~cs is appended
name:"WIDGET"        # matches "widget", "Widget" and "WIDGET"
name:"WIDGET"~cs     # matches "WIDGET" only
name:*widget*~cs     # case-sensitive contains
name:*widget*~ci     # case-insensitive contains (the default, stated explicitly)
----

Notes:

- `*` is the only wildcard and stands for any run of characters at the start, the end, or both ends of a value. There is no single-character wildcard.
- Equality (`:`) and inequality (`:!`) on unquoted and quoted string values, and wildcard matches, are case-insensitive by default. Append the case mode `~cs` for a case-sensitive match; `~ci` states the default explicitly. Both listeners (database and in-memory) apply the same rule.
- The case mode applies to string values only. Numbers, dates, booleans, ObjectIds and variables are compared as typed values.
- An unquoted string may contain letters, digits, spaces between words, and the characters `_ . / @ ' -`. Quote any value that contains other characters (for example `:`, `,`, parentheses or brackets) or that must keep leading or trailing spaces. Inside quotes, write a double quote as `""`.

==== Text Search

[source]
----
# Full-text search (requires MongoDB text index)
text("priority escalation")

# Combine text search with other filters
text("priority escalation") && status:"OPEN"

# Valid: top-level text AND a grouped OR of non-text predicates
text("priority") && (status:"OPEN" || status:"PENDING")
----

Notes:

- `text(...)` maps to MongoDB `$text` queries and is case-insensitive by default.
- MongoDB allows only one `text(...)` clause per query.
- Text search must be backed by a text index on the target collection. If the collection has no text index, MongoDB returns an error (Quantum does not pre-check index existence).
- The lexer keyword `text` is also accepted as a normal field name or unquoted value, so queries such as `type:text` and `text:active` remain valid.
- In-memory evaluation (policy/tests) approximates `$text` with case-insensitive **whole-word** matching (tokenized contains-any). It does not implement stemming or stop words. Example: `text("cat")` matches `"the cat sat"` but not `"category"`.

IMPORTANT: MongoDB requires `$text` to be a top-level query operator. The following usages are **not allowed** and will be rejected at parse time:

[cols="1,2,3"]
|===
|Invalid Usage |Example |Reason

|Inside NOT
|`!!text("foo")`
|MongoDB does not support `$text` inside `$not` or `$nor`

|Inside OR
|`text("foo") \|\| status:"OPEN"`
|MongoDB does not allow `$text` inside `$or`

|Inside elemMatch
|`tags:{text("foo")}`
|MongoDB does not support `$text` inside `$elemMatch`

|Multiple text clauses
|`text("foo") && text("bar")`
|Only one `$text` operator is allowed per query
|===

Valid usage: `text(...)` combined with `&&` (AND) at the top level is supported because MongoDB allows `$text` alongside other top-level conditions.

==== Numeric Ranges

[source]
----
# Price between 10 and 100
price:>=##10 && price:<=##100

# Quantity greater than 0
quantity:>#0

# Exact count
itemCount:#5
----

==== Date and Time Queries

[source]
----
# Orders from today
createdDate:>=2024-12-25

# Orders from last week
createdDate:>=2024-12-18 && createdDate:<2024-12-25

# Specific timestamp
updatedAt:2024-12-25T14:30:00Z

# Orders modified this year
updatedAt:>=2024-01-01T00:00:00Z
----

==== List Membership

[source]
----
# Status in specific values (IN)
status:^["ACTIVE","PENDING","PROCESSING"]

# Exclude statuses (NOT IN)
status:!^["DELETED","ARCHIVED"]

# User IDs from a list (IN)
ownerId:^["user1","user2","user3"]

# Exclude specific users (NOT IN)
ownerId:!^["user1","user2"]

# ObjectId list (IN)
categoryId:^[@@507f1f77bcf86cd799439011, @@507f1f77bcf86cd799439012]

# ObjectId list (NOT IN)
categoryId:!^[@@507f1f77bcf86cd799439011, @@507f1f77bcf86cd799439012]

# Numbers in a list are written without the # prefix; unquoted list values are
# coerced to numbers, booleans, dates or ObjectIds when they look like one
priority:^[1,2,3]

# Quote a list value to keep it a string
code:^["1","2","3"]

# Using variables (CSV expansion supported by access resolvers)
customerId:!^[${accessibleCustomerIds}]
----

===== Null and Existence Checks

[source]
----
# Field has any value (not null)
description:~

# Field is null
description:null

# Field is not null
description:!null

# Field exists and is not empty string
description:~ && description:!""
----

=== Querying Dynamic Attributes

Models that implement `DynamicAttributeSupport` can store flexible, user-defined attributes organized into named sets. These can be queried using the elemMatch syntax for array fields.

==== Dynamic Attribute Structure

Dynamic attributes are stored as:

[source,json]
----
{
  "dynamicAttributeSets": [
    {
      "name": "logistics",
      "attributes": [
        { "id": "uuid-1", "name": "weight", "value": 25.5, "type": "NUMBER" },
        { "id": "uuid-2", "name": "hazmat", "value": false, "type": "BOOLEAN" }
      ]
    },
    {
      "name": "compliance",
      "attributes": [
        { "id": "uuid-3", "name": "certNumber", "value": "CERT-123", "type": "STRING" }
      ]
    }
  ]
}
----

==== Querying by Attribute ID and Value

Use elemMatch syntax `{...}` to query attributes within the array:

[source]
----
# Find records where a specific attribute (by ID) has a specific value
dynamicAttributeSets.attributes:{id:21f63b90-08b4-4280-a28d-f003f9c114b3 && value:"Conference hall"}

# Find records with a numeric attribute value
dynamicAttributeSets.attributes:{id:94138c39-2115-4681-8c18-aa0c0596b065 && value:#99}

# Find records with a decimal attribute value
dynamicAttributeSets.attributes:{id:uuid-1 && value:##25.5}
----

==== Querying by Attribute Name and Value

[source]
----
# Find records where an attribute named "weight" has value > 10
dynamicAttributeSets.attributes:{name:"weight" && value:>##10}

# Find records with a specific attribute name and string value
dynamicAttributeSets.attributes:{name:"certNumber" && value:"CERT-123"}

# Boolean attribute query
dynamicAttributeSets.attributes:{name:"hazmat" && value:true}
----

==== Combining Multiple Dynamic Attribute Conditions

[source]
----
# Multiple attributes must match (separate elemMatch conditions)
dynamicAttributeSets.attributes:{name:"weight" && value:>##10} &&
dynamicAttributeSets.attributes:{name:"hazmat" && value:false}

# OR within a single attribute query
dynamicAttributeSets.attributes:{value:"A" || value:"B"}

# Combined with regular field queries
status:"ACTIVE" && dynamicAttributeSets.attributes:{name:"priority" && value:"HIGH"}
----

==== Querying by Set Name

To filter by the set name itself:

[source]
----
# Records that have a "logistics" attribute set
dynamicAttributeSets:{name:"logistics"}

# Combine set name with attribute value
dynamicAttributeSets:{name:"logistics"} &&
dynamicAttributeSets.attributes:{name:"weight" && value:>##50}
----

==== Advanced Tags (Simple Key-Value)

For simpler tag-based filtering, use `advancedTags`:

[source]
----
# Find by tag name and value
advancedTags:{name:"priority" && value:"urgent"}

# Multiple tag conditions
advancedTags:{name:"region" && value:"US"} && advancedTags:{name:"tier" && value:"premium"}
----

==== Advanced Examples

===== Complex Business Logic

[source]
----
# Active products under $50 OR featured products at any price
(active:true && price:<##50) || featured:true

# Orders needing attention: overdue OR high-value pending
(dueDate:<2024-12-25 && status:!"COMPLETED") ||
(status:"PENDING" && totalAmount:>##1000)

# Products with inventory issues
(quantity:<=#5 && reorderPoint:>#5) || stockStatus:"OUT_OF_STOCK"
----

===== Multi-tenant Filtering

[source]
----
# User's own records
dataDomain.ownerId:${principalId}

# Organization-wide access
dataDomain.orgRefName:${orgRefName}

# Tenant-scoped with public sharing
dataDomain.tenantId:${pTenantId} || dataDomain.orgRefName:"PUBLIC"
----

===== Audit and Compliance

[source]
----
# Records modified by specific user
auditInfo.lastUpdatedBy:"john.doe"

# Changes in date range
auditInfo.lastUpdatedDate:>=2024-12-01 &&
auditInfo.lastUpdatedDate:<2024-12-31
----

NOTE: The right-hand side of a condition is always a value. The language cannot compare one field with another; `fieldA:fieldB` compares `fieldA` with the string `fieldB`.

==== Variables in Filters

Variables are resolved from the current security context and can be used in permission rules and access resolvers.

===== Standard Variables

These are set by `MorphiaUtils.createStandardVariableMapFrom` from the caller's `PrincipalContext` and the request's `ResourceContext`. The DataDomain values come from the DataDomain resolved for the query (DataDomain policy), or else from the principal's own DataDomain.

[cols="1,3"]
|===
|Variable |Description

|`${principalId}`, `${principal.userId}` |Current user's ID
|`${pTenantId}`, `${dd.tenantId}` |Tenant ID of the effective DataDomain
|`${pAccountId}`, `${dd.accountNum}` |Account number of the effective DataDomain
|`${orgRefName}`, `${dd.orgRefName}` |Organization of the effective DataDomain
|`${ownerId}`, `${dd.ownerId}` |Owner ID of the effective DataDomain
|`${pDataSegment}`, `${dd.dataSegment}` |Data segment of the effective DataDomain
|`${defaultRealm}`, `${principal.defaultRealm}` |The principal's default realm
|`${area}` |Current functional area
|`${functionalDomain}` |Current functional domain
|`${action}` |Current action
|`${resourceId}` |Resource id of the current request
|`${dcTenantId}`, `${dcOrgRefName}`, `${dcAccountId}`, `${dcDataSegment}` |The same coordinates taken from the principal's DomainContext, when it has one
|`${facet.<key>}`, `${coord.<key>}` |Facet values supplied by the DataDomain policy for this query
|`${principal.<key>}` |Custom principal properties (also available as `${<key>}`)
|===

===== Unresolved Variables Fail Closed

A variable that cannot be resolved never widens a result:

- In a query converted with variable substitution, a `${var}` that has no value raises an error ("Unresolved resolver variable ...") instead of being compared as literal text. This applies to single values and to `IN` lists.
- In a permission rule, a matched ALLOW rule whose filter references a variable that is missing, null, or whose `AccessListResolver` threw is not dropped. It contributes a filter that matches nothing, so the rule grants no rows, and a warning names the rule and the variables.
- For in-memory rule evaluation and for the write check, an ALLOW rule with an unresolved variable does not apply and a DENY rule does.

==== Performance Tips

===== Efficient Queries

[source]
----
# Good: Use indexed fields first
status:"ACTIVE" && createdDate:>=2024-01-01

# Better: Combine with specific values
status:"ACTIVE" && ownerId:${principalId} && createdDate:>=2024-01-01

# Avoid: Leading wildcards on large collections
name:*widget  # can be slow on millions of records

# Exact, case-sensitive equality compiles to a plain equality match
status:ACTIVE~cs
----

String equality is case-insensitive by default and is executed as an anchored case-insensitive regular expression. Where the stored case is known, append `~cs` so the condition becomes a plain equality that an ordinary index can serve.

===== Projection for Large Objects

[source]
----
# In REST calls, limit returned fields
GET /products/list?filter=active:true&projection=+id,+name,+price,-description
----

==== Error Handling

Common syntax errors and solutions:

[source]
----
# Wrong: A value with punctuation outside the unquoted character set
name:Widget (Large)
# Right:
name:"Widget (Large)"

# Wrong: Incorrect number prefix
price:19.99
# Right:
price:##19.99

# Wrong: Invalid date format
createdDate:12/25/2024
# Right:
createdDate:2024-12-25

# Wrong: Unbalanced parentheses
(active:true && price:>##10
# Right:
(active:true && price:>##10)

# Wrong: text() inside NOT
!!text("search")
# Right: Use text() at top level only
text("search") && status:!"DELETED"

# Wrong: text() inside OR
text("search") || status:"ACTIVE"
# Right: Use text() with AND only
text("search") && (status:"ACTIVE" || status:"PENDING")

# Wrong: Multiple text() clauses
text("foo") && text("bar")
# Right: Combine search terms in a single text()
text("foo bar")
----

==== Execution engines and listeners

The BIAPI query syntax is parsed once (via ANTLR) and can be executed by different "listeners" depending on the use case. Quantum ships with two primary implementations that share the same grammar and semantics:

- Morphia listener: converts a query into Mongo/Morphia Filters for database-side execution (`quantum-morphia-repos`)
- In-memory listener: converts a query into a Java Predicate over JSON data for Quarkus/GraalVM-friendly in-memory execution (`quantum-query-runtime`)

The in-memory predicates live in their own module, `quantum-query-runtime` (package `com.e2eq.framework.query.runtime`: `QueryPredicates`, `QueryToPredicateJsonListener`, `ValidatingQueryToPredicateJsonListener`). The module has no repository or HTTP endpoint and does not depend on `quantum-morphia-repos` or `quantum-framework`, so a service can evaluate BIAPI predicates, including the write-permission check on rule filters, without the framework aggregate. `quantum-morphia-repos` depends on it.

===== Morphia: QueryToFilterListener

Use this when you want the database to perform the filtering. The listener walks the parse tree and produces a dev.morphia.query.filters.Filter which you can apply to Morphia queries. This is ideal for repository APIs and any endpoint where you want to leverage MongoDB indexes and avoid loading large data sets into memory.

Key characteristics:
- Output type: Morphia Filter
- Execution: database-side (MongoDB)
- Semantics: identical to grammar (comparisons, IN/NIN, exists, null, regex with wildcards, elemMatch, boolean &&/||/!!)
- Text search: `text("...")` is supported when a collection has a text index; only one text clause is allowed per query, and it must be at the top level (cannot be inside OR, NOT, or elemMatch).
- Variable expansion: supports ${vars} and single-variable IN list expansion (e.g., [${ids}] can expand to a collection/array or a comma-separated string)

Example:

[source,java]
----
import com.e2eq.framework.grammar.*;
import com.e2eq.framework.model.persistent.morphia.QueryToFilterListener;
import dev.morphia.query.filters.Filter;
import dev.morphia.query.filters.Filters;
import org.antlr.v4.runtime.*;
import org.antlr.v4.runtime.tree.ParseTreeWalker;
import org.apache.commons.text.StringSubstitutor;

String query = "(status:Assigned||status:Pending)&&displayName:*Route*";
var vars = java.util.Map.<String,String>of();

// Parse
CharStream cs = CharStreams.fromString(query);
BIAPIQueryLexer lexer = new BIAPIQueryLexer(cs);
CommonTokenStream tokens = new CommonTokenStream(lexer);
BIAPIQueryParser parser = new BIAPIQueryParser(tokens);
BIAPIQueryParser.QueryContext tree = parser.query();

// Build Morphia filter
QueryToFilterListener listener = new QueryToFilterListener(vars, new StringSubstitutor(vars), /* modelClass */ null);
ParseTreeWalker.DEFAULT.walk(listener, tree);
Filter morphiaFilter = listener.getFilter();

// Use with Morphia query (example)
// datastore.find(MyEntity.class).filter(morphiaFilter).iterator().toList();
----

A few query examples (taken from testQueryStrings.txt):

- Equality: field:"quotedString"
- Comparisons: field:>##12.56, field:<=#123
- IN/NIN: field:^[value1,value2], field:!^[value1,value2]
- Exists/Null: field:~, field:null
- elemMatch: arrayField:{(subField:<#12)||(subField:>#15)}

===== In-memory (JsonNode): QueryToPredicateJsonListener

Use this when you need to evaluate queries in memory without reflection on POJOs. This implementation compiles a query into a java.util.function.Predicate over a Jackson JsonNode. It is Quarkus/GraalVM friendly, useful for:
- Unit tests where you want to validate query behavior without a database
- Post-filtering or pre-filtering of already-fetched data
- Evaluating access rules or business logic against transient objects

Key characteristics:
- Output type: Predicate<JsonNode>
- Execution: in-memory
- No runtime reflection: operates on JsonNode
- Semantics and variable expansion match the Morphia listener

Convenience helpers exist in QueryPredicates:

[source,java]
----
import com.e2eq.framework.query.runtime.QueryPredicates;
import com.fasterxml.jackson.databind.JsonNode;
import java.util.function.Predicate;
import java.util.Map;

String query = "(status:Assigned||status:Pending)&&displayName:*Route*";
Predicate<JsonNode> p = QueryPredicates.compilePredicate(query, Map.of(), Map.of());

// Example data as a POJO or Map -> convert to JsonNode
record Ticket(String status, String displayName) {}
Ticket ticket = new Ticket("Assigned", "Route Exception in Route:To[http://com.xxx/update]");
JsonNode node = QueryPredicates.toJsonNode(ticket);

boolean include = p.test(node); // true
----

Additional examples

- Equality and comparisons
[source,java]
----
var vars = Map.<String,String>of();
var objVars = Map.<String,Object>of();
Predicate<JsonNode> eq = QueryPredicates.compilePredicate("quantity:#42", vars, objVars);
Predicate<JsonNode> gt = QueryPredicates.compilePredicate("price:>##19.99", vars, objVars);

JsonNode product = QueryPredicates.toJsonNode(Map.of("quantity", 42, "price", 25.00));
assert eq.test(product);
assert gt.test(product);
----

- IN / NIN with variable expansion
[source,java]
----
var vars = Map.of("principalId", "66d1f1ab452b94674bbd934a");
Predicate<JsonNode> in = QueryPredicates.compilePredicate("ownerId:^[${principalId},value2]", vars, Map.of());
JsonNode doc = QueryPredicates.toJsonNode(Map.of("ownerId", "66d1f1ab452b94674bbd934a"));
assert in.test(doc);
----

- elemMatch over arrays of objects
[source,java]
----
String q = "items:{(sku:abc||qty:>#10)&&price:<=##9.99}";
Predicate<JsonNode> em = QueryPredicates.compilePredicate(q, Map.of(), Map.of());
JsonNode order = QueryPredicates.toJsonNode(Map.of(
  "items", java.util.List.of(
     Map.of("sku","abc","qty", 5,  "price", 9.99),
     Map.of("sku","xyz","qty", 12, "price", 8.50)
)));
// Matches: first item by sku OR second item by qty with price cap
assert em.test(order);
----

- Regex with wildcards
[source,java]
----
Predicate<JsonNode> rx = QueryPredicates.compilePredicate("displayName:*Route*", Map.of(), Map.of());
JsonNode ticket = QueryPredicates.toJsonNode(Map.of("displayName", "Route Exception in Route:To[...]"));
assert rx.test(ticket);
----

===== Choosing the right listener

- Use Morphia (QueryToFilterListener) when:
  * You are filtering MongoDB collections and want the DB to do the work (indexing, pagination, scalability)
  * You need server-side performance and minimal memory footprint

- Use In-memory (QueryToPredicateJsonListener) when:
  * You run in Quarkus native image and want to avoid reflection on POJOs
  * You are writing unit tests or applying rules to transient/aggregated data
  * You need to evaluate a query over already materialized objects without another database round-trip

Both listeners aim to maintain parity with the grammar. If you observe mismatches, please file an issue with the query string, the evaluated data sample, and the expected vs actual results.

===== Query Field Validation

Quantum provides validation capabilities to detect references to non-existent fields before query execution, preventing runtime errors and providing early feedback.

====== Validating Listeners

Two validating listener implementations extend the standard listeners:

- ValidatingQueryToFilterListener: extends QueryToFilterListener for Morphia queries
- ValidatingQueryToPredicateJsonListener: extends QueryToPredicateJsonListener for in-memory predicates

Both validate field references against a model class during parsing and accumulate errors.

Example usage:

[source,java]
----
import com.e2eq.framework.model.persistent.morphia.ValidatingQueryToFilterListener;
import com.e2eq.framework.grammar.*;
import org.antlr.v4.runtime.*;
import org.antlr.v4.runtime.tree.ParseTreeWalker;

String query = "name:John && invalidField:test";

BIAPIQueryLexer lexer = new BIAPIQueryLexer(CharStreams.fromString(query));
CommonTokenStream tokens = new CommonTokenStream(lexer);
BIAPIQueryParser parser = new BIAPIQueryParser(tokens);

ValidatingQueryToFilterListener listener =
    new ValidatingQueryToFilterListener(UserProfile.class);
ParseTreeWalker.DEFAULT.walk(listener, parser.query());

if (listener.hasValidationErrors()) {
    List<String> errors = listener.getValidationErrors();
    throw new IllegalArgumentException("Invalid query: " + errors);
}

Filter filter = listener.getFilter();
----

====== @ValidQueryFilter Annotation

For automatic validation in DTOs and models, use the `@ValidQueryFilter` annotation:

[source,java]
----
import com.e2eq.framework.annotations.ValidQueryFilter;
import jakarta.validation.constraints.NotNull;

public class SearchRequest {
    @NotNull
    @ValidQueryFilter(modelClass = UserProfile.class)
    private String filterQuery;

    // getters/setters
}
----

The annotation integrates with Jakarta Bean Validation and is automatically enforced by the ValidationInterceptor during entity persistence.

REST endpoint example:

[source,java]
----
@Path("/users")
public class UserResource {

    @GET
    public Response searchUsers(@Valid @BeanParam SearchParams params) {
        // filterQuery is validated before this method executes
        return Response.ok(userService.search(params.getFilterQuery())).build();
    }
}

public class SearchParams {
    @QueryParam("filter")
    @ValidQueryFilter(modelClass = UserProfile.class)
    private String filterQuery;
}
----

Persisted filter example:

For programmatic validation without listeners:

import com.e2eq.framework.annotations.QueryFieldValidator;

- Early error detection: catch field reference errors before query execution

==== Expressing Ontology Constraints in Queries (optional)

The BIAPI query language primarily targets fields on documents. When using the ontology modules, there are two ways to incorporate ontology relationships into queries:

Option A: Variable from an AccessListResolver

- A resolver computes the set of IDs from the ontology edge store (e.g., orders related by placedInOrg to the caller’s org).
- Use an IN clause over id in your filter string:
+
[source]
----
# idsByPlacedInOrg is published by an AccessListResolver
id:^${idsByPlacedInOrg}
----

Option B: the ontology operators described next.

==== Ontology operators: hasEdge, hasOutgoingEdge, and hasIncomingEdge

When the ontology module (`quantum-ontology-mongo`) is installed, you can constrain results by semantic graph relationships using `hasEdge`, `hasOutgoingEdge`, and `hasIncomingEdge`. `hasOutgoingEdge` is an alias of `hasEdge`.

The operators see every edge of the relation, whatever its materialization mode. A relation's edges are either stored in the edge collection when data is written (EAGER) or computed by a provider when they are read (LAZY and ONDEMAND). The query listeners resolve the operators through the `OntologyEdgeLookup` interface, implemented in `quantum-ontology-mongo` over `ComputedEdgeReader`, so a predicate matches whether or not its edges were ever written to MongoDB.

===== Syntax

[source]
----
# Standard 2-argument form (relationship existence)
hasEdge(predicate, dst)
hasOutgoingEdge(predicate, dst)
hasIncomingEdge(predicate, src)

# Qualified 3-argument form (relationship existence WITH edge property constraints)
hasEdge(predicate, dst, { edgeFilter })
hasOutgoingEdge(predicate, dst, { edgeFilter })
hasIncomingEdge(predicate, src, { edgeFilter })
----

===== Arguments

- `predicate`: Relationship identifier. Can be an unquoted identifier (`placedInOrg`), a quoted string (`"placedInOrg"`), or a variable expression (`${orgPredicate}`).
- `dst` / `src`: Target or source entity coordinate. Can be a string literal (`"OrgA"`), an ObjectId, a reference literal (`@@507f1f77bcf86cd799439011`), or a variable placeholder (`${orgRefName}`, `${principalId}`).
- `{ edgeFilter }`: (Optional) A bracketed sub-query containing filtering expressions evaluated directly against the properties of the matching edge in the `edges` collection.

===== Edge Property Scoping and Mechanics

When querying an edge with property constraints:

1. **Automatic Field Scoping**: Any attribute referenced inside the `{ ... }` block that is not a reserved root edge attribute is automatically rewritten to target dynamic edge properties stored under `props.<field>`. The reserved names are `src`, `srcType`, `p`, `dst`, `dstType`, `inferred`, `derived`, `props`, `prov`, `support`, `ts`, `dataDomain`, `id`, `_id`, `created`, `updated`, `version`, and any name starting with `props.`, `dataDomain.` or `prov.`. For example, `{ role:"PRIMARY" && active:true }` is compiled to `props.role == "PRIMARY" AND props.active == true`.
2. **MongoDB Compound Index Utilization**: Edge property filters are pushed down directly into MongoDB queries on the `edges` collection. They take advantage of compound indexes:
   - `idx_domain_p_dst_props`: `{"dataDomain": 1, "p": 1, "dst": 1, "props": 1}` (for `hasEdge` / `hasOutgoingEdge`)
   - `idx_domain_src_p_props`: `{"dataDomain": 1, "src": 1, "p": 1, "props": 1}` (for `hasIncomingEdge`)
3. **Supported Operators**: All standard BIAPI equality (`:`), inequality (`:!`), comparisons (`:>`, `:<`, `:>=`, `:<=`), list membership (`:^`, `:!^`), existence (`:~`), and logical compositions (`&&`, `||`, `!!`) are supported on edge properties.
4. **Prohibited Operators**: Full-text search `text(...)` is prohibited inside `{ edgeFilter }` blocks because MongoDB does not permit `$text` inside embedded document conditions or sub-filters; queries containing `text(...)` within edge filters are rejected at query validation time.

===== Defaults and Fallback Behavior

[cols="1,2,3"]
|===
| Element | Default Behavior | Rationale

| **Omitted `{ edgeFilter }`**
| Matches any edge with the specified `predicate` and target/source, regardless of properties.
| Preserves 100% backward compatibility for standard 2-argument calls.

| **Missing Edge Properties**
| Evaluates to `false` (no match). If an edge does not contain the queried property in its `props` map, the filter fails closed.
| Predictable fail-closed semantics for dynamic schemas.

| **No Matching Edges**
| The operator becomes a filter that matches no document (`_id: "__none__"`). The same happens when the ontology declares a domain (for `hasEdge`) or range (for `hasIncomingEdge`) for the predicate that does not fit the queried entity type.
| An edge predicate that cannot match returns nothing rather than everything.

| **Tenant Scoping & Missing Security Context**
| Edges are read in the caller's full DataDomain (organization, account, tenant, data segment), taken from the authenticated principal. Without a principal the DataDomain is built from the query variables (`pTenantId`/`tenantId`, `orgRefName`, `pAccountId`, `pDataSegment`); if any is missing the query fails with an error. A tenant variable that differs from the principal's tenant is refused.
| Inviolate multi-tenant data isolation; queries never leak edge relationships across realms or unauthenticated callers.

| **Ontology Module Not Installed**
| The database listener (`QueryToFilterListener`) fails the query with an error ("no OntologyEdgeLookup ... is installed"). The in-memory listener (`QueryToPredicateJsonListener`) matches nothing.
| Fail closed: a relationship constraint that cannot be enforced never passes rows.

| **Dynamic Model Schema Validation**
| When query schema validation is enabled (`ValidatingQueryToFilterListener`), edge property keys bypass static entity model field validation.
| Edge properties are open and dynamic; static entity models do not need predefined getters or schema mappings for edge property names.
|===

===== Examples

.Basic edge existence check (2-argument default)
[source]
----
# Find orders placed in an organization (finds source Order entities)
hasEdge("placedInOrg", ${orgRefName})

# Find locations accessible by a specific associate (finds target Location entities)
hasIncomingEdge(canAccessLocation, ${principalId})
----

.Qualified edge filtering with exact property match
[source]
----
# Find accounts where user has a PRIMARY role
hasIncomingEdge("memberOf", ${principalId}, { role:"PRIMARY" })

# Find orders routed to a facility with an expedited service level
hasEdge("routedToFacility", "FAC-901", { serviceLevel:"EXPEDITED" })
----

.Qualified edge filtering with multi-attribute constraints
[source]
----
# Find suppliers with valid certified relationships and confidence >= 0.90
hasEdge("suppliedBy", @@507f1f77bcf86cd799439011, { certified:true && confidence:>=##0.90 })

# Find assets with active status and priority in high tiers
hasEdge("assignedToTeam", "TEAM-ALPHA", { active:true && tier:^[1, 2] })
----

.Combining edge traversal filters with root entity filters
[source]
----
# Orders in pending state placed in ORG-1 with a high-priority edge tag
hasEdge("placedInOrg", "ORG-1", { priority:"HIGH" }) && status:"PENDING" && total:>##500.00
----

===== Query Macros for Temporal & AI Confidence Governance

Before parsing, the query preprocessor (`MorphiaUtils.normalizeOperators`) rewrites two macros as plain text:

1. **`@asOf(timestamp)`** becomes `((validFrom:<=ts || validFrom:null) && (validTo:>=ts || validTo:null))`. Surrounding quotes are stripped so an ISO-8601 timestamp parses as a `DATE` / `DATETIME` token. Written as `edges.@asOf(ts)`, the field names get the `edges.` prefix.
2. **`@minConfidence(threshold)`** becomes `confidence:>=threshold` (or `edges.confidence:>=threshold`). The threshold text is inserted unchanged, so write it with the decimal prefix (`@minConfidence(##0.85)`) to have it compared as a number; without a prefix BIAPI reads the value as a string.

`validFrom`, `validTo`, `confidence` and `securityLabel` are fields of the stored edge document (`OntologyEdge`), indexed by `idx_domain_temporal`, `idx_domain_confidence` and `idx_domain_security`. Used in a query whose root type is the edge collection, the macros address those fields:

.Query Macro Example (root type `OntologyEdge`)
[source]
----
# Edges valid on a date, above a confidence threshold, with a security label
@asOf(2026-09-20T00:00:00Z) && @minConfidence(##0.8) && securityLabel:"CONFIDENTIAL"
----

Inside a `hasEdge(..., { edgeFilter })` block the expanded names follow the automatic field scoping rule above: `validFrom`, `validTo` and `confidence` are not reserved names, so there they address `props.validFrom`, `props.validTo` and `props.confidence`.

==== Expand directives

Two directives ask for related data to be returned with each row. Both switch the query to AGGREGATION mode:

[source]
----
# Hydrate a reference field (an EntityReference with @ReferenceTarget)
expand(customer) && status:active

# Hydrate the targets of a named, stable ontology relation under _rel.<relation>
expand(@hasShipment) && status:active
----

`expand(path)` takes a dotted field path with optional `[*]` array markers; `expand(@relation)` takes a relation name after the `@`. Neither takes further arguments. They filter nothing: use `hasEdge(...)` to restrict the root rows by a relationship. See xref:{doc-root}/user-guide/query-expansion.adoc[Query Expansion] for semantics, security and refusal codes.

==== Root projection recap: fields:[+…,-…]

To include or exclude fields from the root documents:

- Syntax: `fields:[+f1,+f2,-f3]`
- Include mode: if any `+` is present, only the listed fields are included (with explicit `-` carving out exceptions).
- Exclude mode: if only `-` entries exist, all fields are included except those.
- Default `_id`: preserved unless explicitly specified (`+_id`/`-_id`).
- `fields:[...]` is not part of the filter grammar. The query planner handles it, and only for queries that also contain `expand(...)`; in a plain filter query it is a syntax error. List endpoints take their projection as a separate request parameter instead.

Examples

[source]
----
# Include a few fields from the root and drop one
fields:[+_id,+total,-internalNotes]

# Combine with expansion (planner chooses aggregation mode)
expand(customer) && fields:[+_id,+customer,+total]
----

For expansion semantics and the pipelines it compiles to, see xref:{doc-root}/user-guide/query-expansion.adoc[Query Expansion].
