[[planner-and-query-gateway]]
== Planner and QueryGateway

The planner decides whether a query runs as a simple single-collection filter (FILTER mode) or as a MongoDB aggregation (AGGREGATION mode). This is transparent to callers.

In v1 the planner recognizes expand(path) and selects AGGREGATION mode when present. Otherwise, FILTER mode is used and the existing Morphia path is taken.

=== Planner decisions

- FILTER mode: No expand(...) in the query. The system generates a Morphia Filter and queries a single collection.
- AGGREGATION mode: One or more expand(...) directives are present. The system will build an aggregation pipeline (with $lookup, etc.). In v1, a placeholder pipeline is returned to establish the contract.

=== Public facade: QueryGateway

A new collection-agnostic facade exposes plan/inspect capabilities and will later execute aggregation pipelines when enabled.

.Java
[source,java]
----
import com.e2eq.framework.model.persistent.morphia.planner.PlannerResult;
import com.e2eq.framework.model.persistent.morphia.query.QueryGateway;
import com.e2eq.framework.model.persistent.morphia.query.QueryGatewayImpl;

public class PlannerSnippet1 {
  static class Order {}
  public static void main(String[] args) {
    QueryGateway gateway = new QueryGatewayImpl();
    PlannerResult pr = gateway.plan("expand(customer) && status:active", Order.class);
    System.out.println(pr.getMode());        // AGGREGATION
    System.out.println(pr.getExpandPaths()); // [customer]
  }
}
----

If you prefer a lower-level API:

.Java
[source]
----
import com.e2eq.framework.model.persistent.morphia.MorphiaUtils;
import com.e2eq.framework.model.persistent.morphia.planner.PlannedQuery;

PlannedQuery planned = MorphiaUtils.convertToPlannedQuery(
    "expand(items[*].product) && status:active",
    Order.class
);

switch (planned.getMode()) {
  case FILTER:
    // Use planned.getFilter() with Morphia datastore
    break;
  case AGGREGATION:
    // Use planned.getAggregation() to inspect the pipeline (placeholder in v1)
    break;
}
----

- No expansion (FILTER mode):

[[query-gateway-rest]]
=== REST endpoints (v1)

The gateway (`QueryGatewayResource`, `@Path("/api/query")`,
`@FunctionalMapping(area="integration", domain="query")`) exposes a planner endpoint
plus generic governed query operations:

- `POST /api/query/plan` -- returns planner mode (`FILTER` vs `AGGREGATION`) and expand paths detected
- `POST /api/query/find` -- executes governed `FILTER` and `AGGREGATION` queries, returning the standard `Collection<T>` envelope
- `POST /api/query/count` -- returns the governed count for a `FILTER`-mode query
- `POST /api/query/delete` -- deletes a single entity by id (governed; 404 across DataDomain boundaries)
- `POST /api/query/deleteMany` -- deletes the matching `FILTER`-mode set
- `POST /api/query/export` -- streams a governed CSV export

[[query-gateway-governance]]
=== Row- and Field-Level Governance

All query gateway operations execute through multi-layered row- and field-level security filters derived from `RuleContext` and `DataDomainResolver`, failing closed when no valid security context is established:

1. **Root Entity Governance**:
   - `securedFilterArray(...)` ANDs the query filter with the caller's active DataDomain scope and rule `filterConstraints` resolved from `RuleContext`.
   - Field-level exclusions (`applyExcludedFieldProjection(...)`) exclude sensitive fields at the MongoDB datastore level, preventing them from leaving MongoDB.
2. **Fail-Closed Guarantee**:
   - Unless `SecurityContext.isIgnoringRules()` is explicitly set, requests lacking an established `PrincipalContext` and `ResourceContext` are immediately refused with HTTP 500 (`{"error":"SecurityContextMissing"}`).
3. **Information Leakage Prevention**:
   - `delete` ANDs the target `_id` with the secured row filter; records outside the caller's DataDomain return HTTP 404 (`deletedCount=0`, `success=false`) without disclosing whether the entity exists in another tenant.

=== Governed Aggregation Execution & Per-Stage Security Pushdown

When a query contains `expand(...)` directives, the planner selects `AGGREGATION` mode and compiles the query into a multi-stage MongoDB aggregation pipeline via `MongoAggregationCompiler`:

```mermaid
flowchart TD
    subgraph Root ["Root Document Stage"]
        RMatch["$match: dataDomain + Root Rule Constraints"]
        RFilter["$match: User Root Filter"]
    end

    subgraph Hop1 ["Hop 1: $lookup inner pipeline (e.g. orderRef)"]
        H1Match["$match: $expr eq [_id, $$ref_id]"]
        H1Sec["$match: Order DataDomain + Order Rule Constraints"]
        H1Proj["$project: Exclude Order Sensitive Fields"]
    end

    subgraph Hop2 ["Hop 2: $lookup inner pipeline (e.g. supplierRef)"]
        H2Match["$match: $expr eq [_id, $$ref_id]"]
        H2Sec["$match: Supplier DataDomain + Supplier Rule Constraints (Accumulated)"]
        H2Proj["$project: Exclude Supplier Sensitive Fields"]
    end

    Root --> Hop1
    Hop1 --> Hop2
    Hop2 --> FinalProj["Final $project / field filtering"]
```

==== Per-Stage Pushdown Mechanics

1. **Root Pre-Filtering**: The root collection pipeline begins with a leading `$match` enforcing the root model's `DataDomain` policy and security rules.
2. **Inner Pipeline `$lookup` Security**: For each expansion hop, target entity row-level constraints are pushed directly into the inner `pipeline: [ ... ]` of MongoDB's `$lookup` stage.
3. **Monotonic Restriction Accumulation**: Security restrictions accumulate along multi-hop paths (e.g. Customer -> Order -> Supplier). Downstream hops inherit and compound upstream access constraints, ensuring that traversal can never be exploited to elevate privileges or bypass intermediate isolation boundaries.
4. **Target Field Exclusion Pushdown**: Target entity field exclusions (`excludedFieldPaths`) are pushed into the inner pipeline as a `$project` stage, redacting sensitive fields directly within the MongoDB engine.
5. **Cross-Tenant Reference Pruning**: If a foreign reference points to an entity in a different tenant or an entity that fails target row security, the inner `$match` stage filters it out. The populated property resolves to an empty array or `null`, completely preventing cross-tenant data leakage.

==== Configuration and Defaults

[cols="1,1,2,2"]
|===
| Property | Type | Default | Description

| `feature.queryGateway.execution.enabled`
| boolean
| `false`
| Guards execution of `POST /api/query/find` for aggregation queries. When `false`, aggregation queries return HTTP 501 (`ExecutionDisabled`). Must be set to `true` to enable governed aggregation pipeline execution.

| `feature.queryGateway.maxPageSize`
| integer
| `1000`
| Maximum allowed page size (`limit`) for `/api/query/find` requests. Requests exceeding this limit are capped.
|===

[NOTE]
====
`count` and `deleteMany` explicitly reject `expand(...)` queries with HTTP 400 (`InvalidQuery`) because relational hydration is invalid for scalar counting and bulk document deletion.
====

  "query": "expand(orderRef) && expand(orderRef.supplierRef) && status:active"

----

.Response body
[source,json]
----
{
  "mode": "AGGREGATION",

    "orderRef",
    "orderRef.supplierRef"

  "sort": [ { "field": "createdDate", "dir": "DESC" } ],

[source,json]
