[[getting-started]]
== Getting Started: Your First Quantum Application

This section walks through creating a simple multi-tenant Product catalog to demonstrate core Quantum concepts.

=== Prerequisites

- A JDK. The framework compiles to Java 17 bytecode (`maven.compiler.release=17`); the snapshot CI workflow builds and tests on GraalVM JDK 21.0.4.
- Maven (the project is verified with Maven 3.9)
- MongoDB running as a replica set. A single node is enough, but a standalone `mongod` is not: migrations and multi-document writes use transactions. See <<getting-started-mongo>>.
- Basic Quarkus knowledge (see xref:{doc-root}/appendix/quarkus-foundation.adoc[Quarkus Foundation])

=== Project Setup

Create a new Quarkus project with Quantum dependencies:

[source,bash]
----
mvn io.quarkus:quarkus-maven-plugin:create \
    -DprojectGroupId=com.example \
    -DprojectArtifactId=product-catalog \
    -DclassName="com.example.ProductResource" \
    -Dpath="/products"
----

Add Quantum dependencies to `pom.xml`:

[source,xml]
----
<properties>
    <quantum.version>1.4.3-SNAPSHOT</quantum.version>
</properties>

<dependency>
    <groupId>com.end2endlogic</groupId>
    <artifactId>quantum-framework</artifactId>
    <version>${quantum.version}</version>
</dependency>
----

`1.4.3-SNAPSHOT` is the current development line; `1.4.2` is the released long-term-support version. Snapshots are published to `https://central.sonatype.com/repository/maven-snapshots/`, so a build that uses one needs that repository with snapshots enabled (run Maven with `-U` to refresh a cached snapshot).

`quantum-framework` is the compatibility bundle and includes the framework's
server-side REST adapters. For a service with an explicit endpoint boundary,
select the narrower modules instead. For example, add
`com.end2endlogic:quantum-query-rest` only when that backend is intended to
host the existing `/api/query` API. SDK-only consumers should omit REST and
repository modules so they do not expose or persist server-owned APIs.

[[getting-started-modules]]
==== Modules

All modules share the group id `com.end2endlogic` and the version of the parent `quantum-parent`.

[cols="2,4"]
|===
|Module |What it holds

|`quantum-framework`
|Compatibility bundle. Depends on the models, repositories, security runtime, REST core, query, contract, system, seed, bootstrap, migration, application-registration, action-enablement, JWT provider, ontology (Mongo) and MCP server modules listed below.

|`quantum-util`, `quantum-models`
|Utilities; the base models (`BaseModel`, `DataDomain`), annotations and security model classes.

|`quantum-morphia-repos`
|Morphia repositories (`MorphiaRepo`), the rule engine (`RuleContext`) and the migration service.

|`quantum-query-runtime`, `quantum-query-rest`
|In-memory query predicates shared by persistence adapters; the `/api/query` Query Gateway REST adapter.

|`quantum-rest-core`
|`BaseResource`, CSV import and export, usage governance, media references.

|`quantum-security-runtime`
|`SecurityFilter`, principal resolution and session selection.

|`quantum-jwt-provider`, `quantum-default-keys`, `quantum-oauth-server`
|The `custom` JWT authentication provider; a development-only RSA key pair; the optional OAuth 2.0 / OIDC authorization server.

|`quantum-contract-core`, `quantum-contract-rest`
|Contract hashing and compatibility types and the usage-governance contracts; the opt-in `/contract-hash` REST adapter used by generated SDKs.

|`quantum-system`, `quantum-system-management`, `quantum-system-rest`, `quantum-control-plane-client`
|Control-plane split: the system directory and deployment mode; tenant provisioning, access invites and metering; the control-plane admin REST surface; the generated client a tenant-plane service uses to call the control plane.

|`quantum-application-registration`
|Optional SPI for an application to register with its environment at startup.

|`quantum-vocabulary-processor`
|Compile-time annotation processor that derives an application's functional vocabulary from `@FunctionalMapping` and `@FunctionalAction` and checks its identity pack against it.

|`quantum-seed-core`, `quantum-seed-rest`, `quantum-seed-s3`
|Seed packs: loader and startup runner; admin REST; optional S3 seed source.

|`quantum-bootstrap-core`, `quantum-bootstrap-rest`
|Bootstrap packs: runtime and startup runner; admin REST.

|`quantum-migration-rest`
|The `/system/migration` REST adapter.

|`quantum-ontology-core`, `quantum-ontology-mongo`, `quantum-ontology-policy-bridge`, `quantum-ontology-rest`
|Ontology: TBox, validator and reasoner; edge store and materialization; rule and list-query integration; ontology REST endpoints.

|`quantum-action-enablement-models`, `quantum-action-enablement-quarkus`
|Scoped action enablement contracts and runtime.

|`quantum-observability-quarkus`
|Micrometer meter tags (service, environment, version, revision) for service hosts.

|`quantum-secrets`
|Managed, encrypted tenant-level secrets.

|`quantum-mcp-server`
|MCP server and agent tools over the Query Gateway.

|`quantum-cli`
|Command-line tools (`ServiceTokenCLI`).
|===

=== Configuration

[[getting-started-mongo]]
Start a single-node MongoDB replica set and initialize it once:

[source,bash]
----
mongod --dbpath /path/to/data --replSet rs0 --bind_ip localhost
mongosh --eval 'rs.initiate()'
----

Basic `application.properties`:

[source,properties]
----
# MongoDB (replica set)
quarkus.mongodb.connection-string=${MONGODB_CONNECTION_STRING:mongodb://localhost:27017/?replicaSet=rs0}
quarkus.mongodb.database=${MONGODB_DATABASE:product-catalog}
quarkus.morphia.database=${MONGODB_DATABASE:product-catalog}
quarkus.morphia.packages=com.example.model

# JWT authentication (quantum-jwt-provider)
auth.provider=custom
mp.jwt.verify.issuer=https://example.com/issuer
mp.jwt.verify.publickey.location=publicKey.pem
# Access-token lifetime in seconds
com.b2bi.jwt.duration=3600

# Database migrations: the version this application requires, and a scope label.
# 1.0.9 is the highest version the framework's own change sets migrate to.
quantum.database.version=1.0.9
quantum.database.scope=DEV

# CORS for development
quarkus.http.cors=true
quarkus.http.cors.origins=http://localhost:3000
----

=== Your First Model

Create a Product model with multi-tenancy built-in:

[source,java]
----
package com.example.model;

import com.e2eq.framework.annotations.FunctionalMapping;
import com.e2eq.framework.model.persistent.base.BaseModel;
import dev.morphia.annotations.Entity;
import lombok.Data;
import lombok.EqualsAndHashCode;
import lombok.NoArgsConstructor;
import lombok.experimental.SuperBuilder;

import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;
import java.math.BigDecimal;

@Entity
@Data
@NoArgsConstructor
@SuperBuilder
@EqualsAndHashCode(callSuper = true)
@FunctionalMapping(area = "catalog", domain = "product")
public class Product extends BaseModel {

    @NotBlank
    @Size(max = 50)
    private String sku;

    @NotBlank
    @Size(max = 200)
    private String name;

    private String description;
    private BigDecimal price;
    private boolean active = true;
}
----

Key points:
- Extends `BaseModel` for automatic DataDomain, audit fields, and ID management
- `@FunctionalMapping` declares this model's business area and domain for security rules
- Standard Jakarta validation annotations
- Lombok reduces boilerplate

=== Repository

Create a repository. `MorphiaRepo` is a class; extend it and make the subclass a CDI bean:

[source,java]
----
package com.example.repository;

import com.e2eq.framework.model.persistent.morphia.MorphiaRepo;
import com.example.model.Product;
import jakarta.enterprise.context.ApplicationScoped;

@ApplicationScoped
public class ProductRepo extends MorphiaRepo<Product> {
    // Custom queries can be added here
}
----

=== REST Resource

Create a REST endpoint:

[source,java]
----
package com.example.resource;

import com.e2eq.framework.rest.resources.BaseResource;
import com.example.model.Product;
import com.example.repository.ProductRepo;
import jakarta.annotation.security.RolesAllowed;
import jakarta.ws.rs.Path;

@Path("/products")
@RolesAllowed({"user", "admin", "system"})
public class ProductResource extends BaseResource<Product, ProductRepo> {

    protected ProductResource(ProductRepo repo) {
        super(repo);
    }

    // Inherits all CRUD endpoints: GET, POST, PUT, DELETE
    // GET /products/list - paginated list with filtering
    // GET /products/id/{id} - get by ID
    // POST /products - create new product
    // PUT /products/set?id={id}&pairs=field:value - update fields
    // DELETE /products/id/{id} - delete product
}
----

`BaseResource` has no default constructor: pass the repository to `super(repo)`.

=== Running the Application

Start your application:

[source,bash]
----
./mvnw quarkus:dev
----

The application provides:
- Swagger UI at http://localhost:8080/q/swagger-ui/
- Dev UI at http://localhost:8080/q/dev/

=== Testing Your API

Requests are authenticated. Sign in to get a bearer token (the baseline system user and its development password come from `quantum.realmConfig.systemUserId` and `quantum.defaultSystemPassword`), then send it on each call:

[source,bash]
----
curl -s -X POST http://localhost:8080/security/login \
  -H "Content-Type: application/json" \
  -d '{"userId": "system@system.com", "password": "<password>"}'
# the response carries access_token; export it as TOKEN
----

Create a product. Do not send `dataDomain`: the server sets it from the caller (see xref:{doc-root}/user-guide/rest-crud.adoc#rest-crud-write-rules[Write rules the server enforces]).

[source,bash]
----
curl -X POST http://localhost:8080/products \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "sku": "WIDGET-001",
    "name": "Super Widget",
    "description": "The best widget ever",
    "price": 29.99,
    "active": true
  }'
----

List products:

[source,bash]
----
curl -H "Authorization: Bearer $TOKEN" "http://localhost:8080/products/list?limit=10&sort=+name"
----

Filter products:

[source,bash]
----
curl -H "Authorization: Bearer $TOKEN" "http://localhost:8080/products/list?filter=active:true&&price:>##20"
----

=== What You Get Automatically

With this minimal setup, Quantum provides:

**Multi-tenancy**: Each product is automatically tagged with the creator's DataDomain (tenant, org, owner)

**Security**: DataDomain filtering ensures users only see their own data by default

**Validation**: Jakarta Bean Validation runs before persistence

**Audit Trail**: Automatic createdBy, createdDate, lastUpdatedBy, lastUpdatedDate fields

**Consistent APIs**: Standard REST patterns across all resources

**Query Language**: Powerful filtering with the ANTLR-based query syntax

**OpenAPI**: Automatic API documentation

=== Optional: Enable Ontology Modules

You can adopt ontology incrementally. If you don’t enable it, everything works as before.

Quick checklist

1) Add dependencies (app-level)
- quantum-ontology-core, quantum-ontology-mongo, quantum-ontology-policy-bridge (the `quantum-framework` bundle already brings quantum-ontology-mongo)
- Do not add quantum-ontology-rest unless this application intentionally hosts the ontology control-plane API. Normal consumers call quantum-ontology-service through its generated SDK.

2) Configuration

There is no master switch property: the ontology is active when its modules are on the classpath. Write-time edge materialization is on by default and can be turned off:

[source,properties]
----
# default is true
ontology.auto-materialize=true
# packages scanned for @OntologyClass / @OntologyProperty
quantum.ontology.scan.packages=com.example.model
----

3) Provide an ontology registry (TBox)
- Start with an in-memory registry (recommended initially). See xref:{doc-root}/user-guide/ontology.adoc[Ontologies in Quantum].

4) Wire data and indexes
- Inject `OntologyEdgeRepo` as a CDI bean (@Inject). Edges live in the `edges` collection of the realm database.
- Indexes are declared on the `OntologyEdge` entity and are scoped by DataDomain, for example (DataDomain, p, dst) and (DataDomain, src, p).

5) Materialize edges on entity changes
- Use OntologyMaterializer when sources or intermediates change (e.g., Order/Customer/Org/Address/Shipment in the e‑commerce example).

6) Use edges in queries/policies
- Wrap BSON via ListQueryRewriter or constrain by _id sets. See xref:{doc-root}/user-guide/ontology.adoc#ontology-integration-morphia-permissions-section[Integrating Ontology].

Notes

- Keep it optional: an application that does not add the ontology modules is unaffected.
- Multi-tenant: every edge read and write takes the caller's DataDomain.
