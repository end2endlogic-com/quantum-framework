[[mcp-server-and-client]]
== MCP Server and Client

The `quantum-mcp-server` module exposes the Query Gateway as a set of https://modelcontextprotocol.io[Model Context Protocol (MCP)] tools and resources, adds ontology discovery and defect tracking tools, and brings in an MCP client library for calling external MCP tool providers. This enables AI assistants (Claude Desktop, Cursor, ChatGPT, and others) to discover and invoke your application's CRUDL (create, read, update, delete, list) operations, browse entity schemas, and receive query-building hints -- all through the standard MCP JSON-RPC protocol.

The module also includes a REST-based agent layer (`/api/agent/*`) that mirrors the same tool set for non-MCP integrations.

=== Module Overview

`quantum-mcp-server` is a standalone Maven module. It does not depend on the `quantum-framework` aggregate; its key dependencies are:

[cols="1,1,2", options="header"]
|===
| Dependency | Version | Purpose

| `quantum-query-rest`
| `${quantum.version}`
| Query Gateway endpoint owner (`QueryGatewayResource`), with its security and Morphia dependencies

| `quantum-rest-core`
| `${quantum.version}`
| `BaseResource`, used by the defect REST resource

| `quantum-ontology-mongo`
| `${quantum.version}`
| Ontology edge reads (`ComputedEdgeReader`) and the per-realm ontology registry, used by the ontology tools

| `quarkus-mcp-server-http`
| 1.9.1
| Quarkiverse MCP Server -- Streamable HTTP + legacy SSE transport

| `quarkus-langchain4j-mcp`
| 1.6.0
| Quarkiverse MCP Client via LangChain4j -- connect to external MCP servers
|===

Add the module to your application's POM:

[source,xml]
----
<dependency>
    <groupId>com.end2endlogic</groupId>
    <artifactId>quantum-mcp-server</artifactId>
    <version>${quantum.version}</version>
</dependency>
----

[[mcp-server]]
=== MCP Server

The MCP server exposes 18 tools and three resources at the `/mcp` endpoint: twelve Query Gateway tools (`McpGatewayTools`), two ontology tools (`McpOntologyTools`, see <<ontology-tools>>) and four defect tools (`McpDefectTools`, see <<defect-tools>>). MCP clients discover these automatically via the `tools/list` and `resources/list` JSON-RPC methods.

The transport comes from the Quarkiverse `quarkus-mcp-server-http` extension: Streamable HTTP at `/mcp`, plus the legacy HTTP/SSE transport. The root path is the extension's build-time property `quarkus.mcp.server.http.root-path` (default `/mcp`).

==== Security

The MCP server and the agent REST API require an authenticated caller. Every tool and resource class (`McpGatewayTools`, `McpOntologyTools`, `McpDefectTools`, `McpSchemaResources`, `McpQueryHintsResource`) and `AgentResource` carry the Quarkus Security `@Authenticated` annotation.

* **REST API (`/api/agent/*`):** Requires a valid Bearer JWT token in the `Authorization` header.
* **MCP Endpoint (`/mcp`):** The MCP protocol transport (Streamable HTTP or SSE) must include the same authentication mechanism (typically a `Authorization: Bearer <token>` header) as other REST APIs.
* **Realm:** A tool's optional `realm` argument does not switch tenants. For an authenticated caller it must equal the caller's effective realm (the principal's default realm; for the gateway tools, the principal's realm override for the `integration` area when one is set); any other value is refused. Omit it unless you want that check.

You can generate a long-lived service token for use with the MCP server using the xref:{doc-root}/user-guide/auth.adoc#using-the-quantum-cli[Quantum CLI].

==== Tools

The gateway tools are defined in `McpGatewayTools` using the Quarkiverse `@Tool` and `@ToolArg` annotations. Each tool delegates to `AgentExecuteHandler`, which routes to the `QueryGatewayResource` -- reusing the same security, realm resolution, and query execution as the REST API.

Every tool returns a JSON string. A gateway tool returns the body of the matching gateway response; the HTTP status is not carried over, so check the body for an `error` field. An exception thrown by the gateway (for example a refused realm) is returned as `{"error":"ExecutionFailed","message":"..."}`.

[NOTE]
====
Because the tools route through `QueryGatewayResource`, the data-access tools are
row- and field-governed. `query_find`, `query_count`, `query_delete`,
`query_deleteMany`, and `query_export` apply the caller's DataDomain scope plus the
`RuleContext` rule `filterConstraints`, and `query_find` additionally excludes
deny-wins `excludedFields` at the MongoDB level. The gateway **fails closed** (HTTP 500
`SecurityContextMissing`) if no security context is established for the request, so an
agent never executes an ungoverned query. `query_delete` returns "not found" for an id
outside the caller's DataDomain rather than revealing that the row exists.

`expand(...)` (aggregation) execution is off by default: with
`feature.queryGateway.execution.enabled=false` a `query_find` with `expand(...)` returns the
gateway's 501 body (`{"error":"NotImplemented", ...}`). When the property is `true`, the
aggregation runs under the root policy and every expand target under its own row and field
policy; a target whose policy cannot be resolved is refused (`ExpandPolicyUnresolved`). See
xref:{doc-root}/user-guide/planner-and-query-gateway.adoc#query-gateway-governance[Planner and QueryGateway: row- and field-level governance].
====

[cols="1,3", options="header"]
|===
| Tool Name | Description

| `query_rootTypes`
| List available entity types (root types) that can be queried, saved, or deleted

| `query_plan`
| Return the query execution plan (FILTER vs AGGREGATION) for a rootType and BIAPI query string

| `query_find`
| Execute a BIAPI query and return matching entities (supports pagination, realm override)

| `query_save`
| Save (insert or update) an entity by rootType

| `query_delete`
| Delete a single entity by its ObjectId

| `query_deleteMany`
| Delete multiple entities matching a BIAPI query

| `query_count`
| Count entities matching a BIAPI query

| `query_export`
| Export entities matching a BIAPI query as CSV; inline for small results, written to a server-side temporary file for large ones

| `query_import_analyze`
| Analyze CSV content for import, returning a session id, row counts and a preview of rows with their intent and validation errors

| `query_import_rows`
| List analyzed import rows from a session (supports paging and filtering by error or intent)

| `query_import_commit`
| Commit an analyzed import session, persisting the valid rows to the database

| `query_import_cancel`
| Cancel an import session and discard its analyzed rows
|===

===== Tool parameters

Required arguments are marked; all others are optional. `rootType` is an entity type simple name or fully qualified class name (use `query_rootTypes` to discover valid values).

[cols="1,3", options="header"]
|===
| Tool | Arguments

| `query_rootTypes`
| None.

| `query_plan`
| `rootType` (required), `query` (required).

| `query_find`
| `rootType` (required); `query` (BIAPI query string, e.g. `status:ACTIVE && region:West`; omit for all rows the caller may see); `realm`; `limit` (integer, default 50); `skip` (integer, default 0). The tool has no sort argument; the REST and `/api/agent/execute` forms accept `sort`.

| `query_count`
| `rootType` (required); `query`; `realm`. A query with `expand(...)` is rejected.

| `query_save`
| `rootType` (required); `entity` (required, a JSON object passed as a string; field names must match the type); `realm`. An entity with an id is updated, one without is inserted. Unparseable JSON returns `{"error":"InvalidEntity", ...}`.

| `query_delete`
| `rootType` (required); `id` (required, ObjectId hex string); `realm`.

| `query_deleteMany`
| `rootType` (required); `query` (required); `realm`. A query with `expand(...)` is rejected, and so is one that matches more than `quantum.queryGateway.deleteMany.maxMatches` entities.

| `query_export`
| `rootType` (required); `query`; `columns` (comma-separated field names); `realm`; `limit` (default: all rows); `skip` (default 0). The response has `mode` `inline` with `csvContent`, or `file` with `csvFilePath` when the row count exceeds `quantum.queryGateway.export.inlineThreshold`.

| `query_import_analyze`
| `rootType` (required); `csvContent` (required, CSV text including a header row); `columns` (required, comma-separated entity field names in CSV column order; headers are not inferred); `realm`; `fieldSeparator` (default `,`); `quoteChar` (default `"`).

| `query_import_rows`
| `sessionId` (required, from `query_import_analyze`); `rootType` (required); `realm`; `skip` (default 0); `limit` (default 50); `onlyErrors` (boolean); `intent` (`INSERT`, `UPDATE` or `SKIP`).

| `query_import_commit`
| `sessionId` (required); `rootType` (required); `realm`. Returns `imported` and `failed` counts.

| `query_import_cancel`
| `sessionId` (required); `rootType` (required); `realm`.
|===

==== Resources

Resources are defined in `McpSchemaResources` and `McpQueryHintsResource` using the `@Resource` annotation. MCP clients can read these to populate LLM context with schema information and query-building guidance.

[cols="1,3", options="header"]
|===
| Resource URI | Description

| `quantum://schema`
| Lists all available root types with class name, simple name, and collection name (the same response as `query_rootTypes`). There is no per-type schema resource; use `GET /api/agent/schema/{rootType}` for the fields of one type.

| `quantum://query-hints`
| BIAPI query grammar summary, example queries by intent, and tips (expand, wildcards, ontology)

| `quantum://permission-hints`
| Permission check/evaluate API summary, area/domain/action mapping, and example check requests
|===

==== Connecting an MCP Client

Any MCP-compatible client can connect to the `/mcp` endpoint. The client must send the caller's credentials (typically an `Authorization: Bearer <token>` header) with every request; how to set a header depends on the client. Example configuration for Claude Desktop (`claude_desktop_config.json`):

[source,json]
----
{
  "mcpServers": {
    "quantum": {
      "url": "http://localhost:8080/mcp"
    }
  }
}
----

For Cursor, add the server URL in Settings > MCP Servers.

Once connected, the client can:

1. Call `tools/list` to discover the gateway, ontology and defect tools
2. Call `resources/list` to discover schema and hint resources
3. Call `resources/read` with `quantum://query-hints` to learn the BIAPI query syntax
4. Call `tools/call` with `query_rootTypes` to see what entity types are available
5. Call `tools/call` with `query_find` to query data

[[mcp-client]]
=== MCP Client

The MCP client side is the Quarkiverse LangChain4j MCP extension (`quarkus-langchain4j-mcp`), which the module declares as a dependency so that an application can connect to external MCP servers and consume their tools. The module itself defines no MCP clients and no `quarkus.langchain4j.mcp.*` configuration; everything in this section is configuration and code you add to your application, using that extension's API. Use the MCP client when you need to:

* Integrate with external tool providers (e.g. Helix MCP, Brain, HelixAI, or any MCP-compliant server)
* Let your AI services discover and invoke tools from those servers at runtime
* Access MCP resources (files, API responses, etc.) programmatically or expose them as tools to the LLM

The client implements the https://modelcontextprotocol.io/specification/2025-11-25[MCP Specification] and works with any compatible MCP server (including the Quantum MCP server on another instance).

==== Configuration

External MCP connections are configured in `application.properties` using the `quarkus.langchain4j.mcp.<client-name>` prefix. Each named block defines one MCP client (e.g. `helix`, `brain`, `filesystem`).

[source,properties]
----
# Streamable HTTP (recommended for remote servers)
quarkus.langchain4j.mcp.helix.transport-type=streamable-http
quarkus.langchain4j.mcp.helix.url=http://helix-mcp.example.com/mcp

# STDIO (for local subprocess servers, e.g. npm-based MCP servers)
quarkus.langchain4j.mcp.brain.transport-type=stdio
quarkus.langchain4j.mcp.brain.command=npx,-y,@brain/mcp-server

# Optional: pass environment variables to the STDIO subprocess
quarkus.langchain4j.mcp.brain.environment.API_KEY=${EXTERNAL_API_KEY}
----

Supported transport types:

[cols="1,3", options="header"]
|===
| Transport | Description

| `streamable-http`
| Recommended for remote MCP servers; uses HTTP with the MCP streamable transport.

| `http`
| Legacy HTTP/SSE transport. URL typically ends with `/mcp/sse`.

| `stdio`
| Spawns the MCP server as a subprocess; communication via stdin/stdout. Use `command` (comma-separated parts) and optionally `environment.*` for env vars.

| `websocket`
| Bidirectional WebSocket. Supported by some servers (e.g. those built with `quarkus-mcp-server`).
|===

==== Using MCP Tools in AI Services

Enable tools from one or more MCP servers on an AI service using `@McpToolBox`. The LLM can then discover and call those tools during the conversation.

**Single MCP server:**

[source,java]
----
import io.quarkiverse.langchain4j.mcp.runtime.McpToolBox;
import dev.langchain4j.service.SystemMessage;
import dev.langchain4j.service.UserMessage;
import io.quarkiverse.langchain4j.RegisterAiService;

@RegisterAiService
public interface MyAiService {

    @SystemMessage("You are a helpful assistant.")
    @McpToolBox("helix")
    String chat(@UserMessage String userMessage);
}
----

**Multiple MCP servers:** pass an array of client names to use tools from several servers in one service.

[source,java]
----
@McpToolBox({"helix", "brain"})
String chat(@UserMessage String userMessage);
----

**All configured MCP servers:** omit the value to expose every configured MCP client's tools to the AI service.

[source,java]
----
@McpToolBox
String chat(@UserMessage String userMessage);
----

==== Programmatic Access to MCP Clients

For fine-grained control (custom tool filtering, non-AI workflows, or resource access), inject an `McpClient` directly with `@McpClientName`:

[source,java]
----
import dev.langchain4j.mcp.client.McpClient;
import io.quarkiverse.langchain4j.mcp.runtime.McpClientName;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;

@ApplicationScoped
public class McpClientService {

    @Inject
    @McpClientName("helix")
    McpClient helixClient;

    public void useClient() {
        // List tools exposed by the MCP server
        var tools = helixClient.listTools();

        // Execute a tool by name with JSON arguments
        var args = com.fasterxml.jackson.databind.node.JsonNodeFactory.instance.objectNode().put("key", "value");
        var request = dev.langchain4j.mcp.client.protocol.McpCallToolRequest.builder()
            .name("some_tool_name")
            .arguments(args)
            .build();
        var result = helixClient.executeTool(request);

        // List and read resources (if the server exposes resources)
        var resources = helixClient.listResources();
        var content = helixClient.readResource("some://resource-uri");
    }
}
----

Use programmatic access when you need to drive tool execution from non-AI code, filter or transform tool results, or integrate MCP resources into your own APIs.

==== Dev UI: Testing MCP Clients

In development mode (`mvn quarkus:dev`), open the Quarkus Dev UI at `http://localhost:8080/q/dev-ui` and use the **MCP clients** card to:

* View all configured MCP clients
* Browse tools (names, descriptions, parameter schemas)
* Execute tools with custom arguments and inspect results

This is useful for exploring a new MCP server or debugging tool arguments before wiring it into an AI service.

==== Optional: Resources as Tools

If an MCP server exposes resources, you can expose them as synthetic tools so the LLM can list and read resources:

[source,properties]
----
quarkus.langchain4j.mcp.expose-resources-as-tools=true
----

When enabled, the client adds `list_resources` and `get_resource` to the tool set; your AI service can then answer questions like “List available resources” or “Show me the content of resource X” when using `@McpToolBox` for that client.

==== Optional: Headers and Authorization

* **Static headers:** for HTTP-based clients, set headers via config:

+
[source,properties]
----
quarkus.langchain4j.mcp.helix.header.X-Custom-Header=MyValue
----

* **Dynamic headers:** implement `dev.langchain4j.mcp.client.McpHeadersSupplier` and provide a CDI bean; it will be used for Streamable HTTP clients to add headers per request.

* **Authorization:** implement `io.quarkiverse.langchain4j.mcp.auth.McpClientAuthProvider` to supply a bearer token or API key. Use `@McpClientName` on the bean to restrict it to a specific client. For OIDC, add the dependency `quarkus-langchain4j-oidc-mcp-auth-provider` to propagate the user’s access token to the MCP server.

See the https://docs.quarkiverse.io/quarkus-langchain4j/dev/mcp.html[Quarkus LangChain4j MCP documentation] for full details on transports, auth, and the MCP Registry client.

[[agent-rest-api]]
=== Agent REST API

The agent layer provides a REST interface at `/api/agent` that mirrors the MCP tools for non-MCP integrations. This is useful for custom agent orchestrators, webhook-based workflows, or testing.

==== Endpoints

[cols="1,1,3", options="header"]
|===
| Method | Path | Description

| GET | `/api/agent/tools` | List available gateway tools (optionally filtered by realm)
| GET | `/api/agent/schema` | List all root types (same as `query_rootTypes`)
| GET | `/api/agent/schema/{rootType}` | JSON Schema-like structure for a single entity type
| GET | `/api/agent/query-hints` | Query grammar summary and example queries
| GET | `/api/agent/permission-hints` | Permission check API summary and examples
| POST | `/api/agent/execute` | Execute a gateway tool by name
|===

==== Execute Request

The execute endpoint accepts a tool name and arguments:

[source,json]
----
{
  "tool": "query_find",
  "arguments": {
    "rootType": "Location",
    "query": "status:ACTIVE && city:Atlanta",
    "page": { "limit": 10, "skip": 0 }
  }
}
----

[source,bash]
----
curl -sS -X POST \
  -H 'Content-Type: application/json' \
  localhost:8080/api/agent/execute \
  -d '{
    "tool": "query_find",
    "arguments": {
      "rootType": "Location",
      "query": "status:ACTIVE && city:Atlanta"
    }
  }'
----

The response shape matches the corresponding Query Gateway REST endpoint (e.g. the Collection envelope for `query_find`).

The request body fields are `tool` (or `name`) and `arguments` (or `params`). `sessionId` and `traceId` are accepted but are not currently used by the handler. The tool names are the twelve `query_*` gateway tools; the ontology and defect tools are MCP-only. A missing tool name returns HTTP 400 `ToolRequired`, and an unknown one HTTP 400 `UnknownTool` with the list of `availableTools`.

`GET /api/agent/tools` returns `{"tools": [...], "count": 12}`. Each tool entry has `name`, `description`, `parameters` (a list of `{name, type, description}`), `area` (`integration`) and `domain` (`query`). The catalog is a static list; it is not filtered by the caller's permissions, and listing a tool grants nothing: each execution still passes the gateway's own checks.

[[tenant-agent-config]]
=== Per-Tenant Agent Configuration

Agent behavior can be customized per realm using MicroProfile Config properties:

[source,properties]
----
# Run agent tools as a specific user in the "acme" realm
quantum.agent.tenant.acme.runAsUserId=agent-user@acme.com

# Only allow find and plan tools for the "acme" realm
quantum.agent.tenant.acme.enabledTools=query_find,query_plan,query_rootTypes

# Cap find results at 100 for this tenant
quantum.agent.tenant.acme.maxFindLimit=100
----

Configuration properties:

[cols="1,1,3", options="header"]
|===
| Property | Type | Description

| `quantum.agent.tenant.<realm>.runAsUserId`
| string
| Optional userId intended as the security context for tool execution. Read into `TenantAgentConfig`; not applied by `AgentExecuteHandler` in this release (see below).

| `quantum.agent.tenant.<realm>.enabledTools`
| comma-separated
| Optional list of tool names that `GET /api/agent/tools?realm=<realm>` returns (all twelve when unset or empty). It filters discovery only.

| `quantum.agent.tenant.<realm>.maxFindLimit`
| integer
| Optional maximum number of results for `query_find`. Read into `TenantAgentConfig`; not applied in this release.
|===

The default implementation (`PropertyTenantAgentConfigResolver`) reads these from `application.properties` or environment variables. None of the keys has a default; a realm with none of them set has no tenant configuration. You can replace the resolver by providing a CDI bean implementing `TenantAgentConfigResolver`.

[IMPORTANT]
====
In this release the tenant configuration only affects discovery. `AgentToolsProvider` uses `enabledTools` to filter `GET /api/agent/tools` when a `realm` query parameter is given. `AgentExecuteHandler` and the MCP tools do not consult the tenant configuration: a tool left out of `enabledTools` can still be executed by a caller whose permissions allow it, `maxFindLimit` does not cap results, and execution always runs as the authenticated caller. Use permission rules to restrict what a caller may do.
====

==== Run-As Principal

`RunAsPrincipalResolver` is the extension point intended for `runAsUserId`: given a realm and a userId it returns the `PrincipalContext` to run under. The interface exists, but nothing in the framework calls it yet, so providing a bean has no effect on execution today. Its shape is:

[source,java]
----
import com.e2eq.framework.api.agent.RunAsPrincipalResolver;
import com.e2eq.framework.model.securityrules.PrincipalContext;
import jakarta.enterprise.context.ApplicationScoped;
import java.util.Optional;

@ApplicationScoped
public class MyRunAsPrincipalResolver implements RunAsPrincipalResolver {

    @Override
    public Optional<PrincipalContext> resolvePrincipalContext(String realm, String userId) {
        // Look up user and build PrincipalContext
        // Return Optional.empty() to fall back to caller's context
    }
}
----

[[agent-config-api]]
=== Agent Configuration API

The framework stores agent configurations as realm-scoped `Agent` entities in MongoDB (`agents` collection). Each agent pairs an LLM reference with a system prompt and a tool filter, enabling different personas for different use cases (e.g., a supply-chain analyst vs. a customer-service bot).

==== Agent Entity

[cols="1,1,3", options="header"]
|===
| Field | Type | Description

| `refName`
| string
| Unique reference name within the realm (e.g., `supply-chain-assistant`)

| `name`
| string
| Display name

| `llmConfigRef`
| string
| Reference to an LLM secret or config (e.g., `claude-sonnet`, `gpt-4o`)

| `context`
| list of PromptStep
| Ordered system/user prompt steps that define the agent's persona

| `enabledTools`
| list of string
| Tool names this agent can use (e.g., `["query_rootTypes", "query_find", "query_plan"]`)
|===

Each `PromptStep` has `order` (int), `role` (string: `"system"` or `"user"`), and `content` (string: prompt text).

==== CRUD Endpoints

All endpoints are at `/api/agent/config` (`AgentConfigResource`, in the `quantum-framework` module, functional area `integration`, domain `agentConfig`) and require a `realm` query parameter; a request without it returns HTTP 400.

[cols="1,2,3", options="header"]
|===
| Method | Path | Description

| GET
| `/api/agent/config/list?realm=X`
| List all agents in the realm

| GET
| `/api/agent/config/{refName}?realm=X`
| Get an agent by reference name

| GET
| `/api/agent/config/id/{id}?realm=X`
| Get an agent by ObjectId

| POST
| `/api/agent/config?realm=X`
| Create or update an agent

| DELETE
| `/api/agent/config/{refName}?realm=X`
| Delete an agent by reference name

| DELETE
| `/api/agent/config/id/{id}?realm=X`
| Delete an agent by ObjectId
|===

==== Example: Creating an Agent

[source,bash]
----
curl -sS -X POST \
  -H 'Content-Type: application/json' \
  'localhost:8080/api/agent/config?realm=acme-corp' \
  -d '{
    "refName": "supply-chain-assistant",
    "name": "Supply Chain Assistant",
    "llmConfigRef": "claude-sonnet",
    "context": [
      { "order": 1, "role": "system", "content": "You are a supply-chain analyst. Help users query orders, track shipments, and monitor inventory." }
    ],
    "enabledTools": ["query_rootTypes", "query_plan", "query_find", "query_count"]
  }'
----

NOTE: Agent configuration complements the property-based tenant configuration (<<tenant-agent-config>>). An `Agent` entity stores a per-use-case persona and tool list that can be managed via API. The framework stores and returns it; the MCP server and `/api/agent/execute` do not read `Agent` entities, so applying `enabledTools` or the prompt context is up to the application that runs the agent.

[[mcp-architecture]]
=== Architecture

The following diagram shows how the MCP server, agent REST API, and MCP client relate:

....
                        MCP Clients                    Custom Agents
                   (Claude, Cursor, etc.)            (REST, webhooks)
                          |                                |
                    JSON-RPC /mcp                   REST /api/agent/*
                          |                                |
                  +-------+--------+              +--------+-------+
                  | McpGatewayTools |              | AgentResource  |
                  | McpSchema*      |              +--------+-------+
                  | McpQueryHints*  |                       |
                  | McpOntologyTools|                       |
                  | McpDefectTools  |                       |
                  +-------+--------+                       |
                          |                                |
                          +---------- shared ----------+   |
                                                       |   |
                                              +--------+---+-------+
                                              | AgentExecuteHandler |
                                              +--------+-----------+
                                                       |
                                              +--------+-----------+
                                              | QueryGatewayResource|
                                              +--------+-----------+
                                                       |
                                                   MongoDB

    External MCP Servers (Helix, Brain, HelixAI)
                  |
          quarkus-langchain4j-mcp
                  |
        MCP Client (tool consumer)
....

Key design points:

- **Shared execution path**: Both the MCP gateway tools and the REST agent endpoint delegate to `AgentExecuteHandler`, which routes to `QueryGatewayResource`. Security rules, realm resolution, and query execution are identical regardless of entry point. The ontology tools read through `ComputedEdgeReader` and the realm's ontology registry, and the defect tools through `DefectRepo`; they do not pass through `AgentExecuteHandler`.
- **Zero reverse dependencies**: The `quantum-mcp-server` module depends on `quantum-query-rest`, `quantum-rest-core` and `quantum-ontology-mongo`; none of them knows about MCP. Applications that do not need MCP simply omit this module.
- **Tenant isolation**: Execution is bound to the authenticated caller's effective realm and DataDomain. Per-tenant tool filtering applies to discovery only (see <<tenant-agent-config>>).

[[ontology-tools]]
=== Ontology Tools

In addition to the twelve gateway tools, the MCP server exposes two ontology discovery tools via `McpOntologyTools`:

[cols="1,3", options="header"]
|===
| Tool Name | Description

| `query_relationships`
| Find ontology edges (relationships) for an entity -- outgoing, incoming, or both, with optional predicate filtering

| `query_predicates`
| List ontology predicates (relationship types) defined in the TBox schema, with optional domain/range filtering
|===

These tools allow AI assistants to explore the entity relationship graph.
For example, an agent can discover that an `Order` entity has a `placedInOrg` relationship to an `Organization`, then use `query_find` with appropriate filters to retrieve related data.

`query_relationships` arguments:

[cols="1,1,3", options="header"]
|===
| Parameter | Type | Description

| `entityId` | string | Required. The id the entity has in the edge store (its ObjectId hex string or its refName).
| `direction` | string | `out` (edges from the entity), `in` (edges to it) or `both`. Default `both`.
| `predicate` | string | Optional. Only return edges with this predicate.
| `realm` | string | Optional. Must equal the caller's effective realm.
|===

The result is `{"entityId", "direction", "count", "edges": [...]}`. Each edge has `direction` (`outgoing` or `incoming`), `predicate`, `src`, `srcType`, `dst`, `dstType`, `inferred`, and `derived` (true for an edge computed by a provider rather than read from the store). Edges are read through `ComputedEdgeReader`, so edges of LAZY and ONDEMAND computed relations (relations whose edges are computed when read instead of being stored) are included when their providers are registered.

`query_predicates` arguments: `domainFilter` (only predicates whose domain, the source type, is this type), `rangeFilter` (only predicates whose range, the target type, is this type) and `realm`; all optional, and the two filters are case-insensitive. The result is `{"count", "predicates": [...]}` sorted by name; each predicate has `name`, `domain`, `range`, `transitive`, `symmetric`, `functional`, `inferred`, and, when declared, `inverseOf` and `subPropertyOf`.

Security: both tools require an authenticated principal context with a default realm; `query_relationships` also requires the principal's DataDomain and reads edges only in that DataDomain. A `realm` argument that differs from the caller's effective realm is refused, and a `realm` argument cannot stand in for a missing principal. Failures are returned as JSON, for example `{"error":"RelationshipQueryFailed","message":"Requested realm 'tenant-b' does not match authenticated effective realm 'tenant-a'"}` or `{"error":"PredicateQueryFailed", ...}`; `query_predicates` returns `{"error":"NoRegistry", ...}` when the realm has no ontology registry.

[[defect-tools]]
=== Defect Tools

`McpDefectTools` lets an agent file and triage defects over MCP. A defect is a `Defect` entity (collection `defect`, functional area and domain `DEFECT`), persisted through `DefectRepo` like any other Quantum entity, so it is realm-scoped, audited and subject to the caller's permission rules. The same repository is exposed as REST CRUD by `DefectResource` at `/mcp/defects`.

NOTE: An application that hosts these tools must add the package `com.e2eq.framework.mcp.defect` to `quarkus.morphia.packages` so that the entity is mapped.

[cols="1,3", options="header"]
|===
| Tool Name | Arguments and behaviour

| `defect_create`
| `title` (required), `description` (required), `severity` (`low`, `medium`, `high` or `critical`; default `medium`, and any other value is stored as `medium`), `area`, `component`, `reporter` (defaults to the caller's userId, else subject id). The defect gets a generated refName `defect-<uuid>` and status `open`. Returns the created defect.

| `defect_list`
| Optional filters `status` (`open`, `in-progress`, `resolved`, `closed`), `severity`, `area`; each is a case-insensitive exact match. Returns `{"count", "defects": [...]}`.

| `defect_get`
| `refName` (required). Returns the defect, or `{"error":"DefectNotFound", ...}`.

| `defect_update`
| `refName` (required); `status`, `resolution`, `assignedTo`, `severity`. Only non-blank arguments are applied. The status value is stored as given; it is not checked against the four status names. Returns the updated defect.
|===

A defect is returned with the fields `refName`, `title`, `description`, `severity`, `status`, `area`, `component`, `reporter`, `assignedTo`, `resolution`, `relatedRefs` and `tags`. Failures are returned as JSON with `error` set to `DefectCreateFailed`, `DefectListFailed`, `DefectGetFailed` or `DefectUpdateFailed`.

[[claude-integration]]
=== Integrating with Claude

Claude supports MCP through Claude Desktop, Claude Code (CLI), and the browser-based Claude.ai (via Custom Connectors).
The Quantum MCP server works with all three.

==== Claude Desktop

Edit `~/Library/Application Support/Claude/claude_desktop_config.json` (macOS) or the equivalent on your platform:

[source,json]
----
{
  "mcpServers": {
    "quantum": {
      "url": "http://localhost:8080/mcp"
    }
  }
}
----

Restart Claude Desktop.
The Quantum tools appear in the tool picker and Claude can call them during conversations.

==== Claude Code (CLI)

Claude Code discovers MCP servers from project-level or user-level configuration.

**Project-level** -- create `.mcp.json` in your repository root. The `headers` entry carries the bearer token the server requires; `${QUANTUM_TOKEN}` is read from the environment:

[source,json]
----
{
  "mcpServers": {
    "quantum-mcp": {
      "type": "http",
      "url": "http://localhost:8080/mcp",
      "headers": {
        "Authorization": "Bearer ${QUANTUM_TOKEN}"
      }
    }
  }
}
----

**User-level** -- add the server with the CLI instead:

[source,bash]
----
claude mcp add --transport http quantum-mcp http://localhost:8080/mcp \
  --header "Authorization: Bearer $QUANTUM_TOKEN"
----

Once configured, Claude Code can use the Quantum tools in any conversation:

[source,text]
----
> Use query_rootTypes to list available entity types

Claude calls query_rootTypes and returns:
  Location, Order, CodeList, UserProfile, ...

> Find all active locations in the West region

Claude calls query_find with:
  rootType: "Location"
  query: "status:ACTIVE && region:West"
  limit: 10

Returns matching Location entities.
----

==== Claude.ai (Browser) with Custom Connectors

For cloud-hosted deployments, expose the `/mcp` endpoint over HTTPS and configure a Claude Custom Connector:

1. In Claude.ai, go to Settings > Integrations > Custom Connectors.
2. Add a new connector with your server URL (e.g., `https://api.mycompany.com/mcp`).
3. Configure authentication headers if required by your deployment.

==== Cursor IDE

Create `.cursor/mcp.json` in your project root:

[source,json]
----
{
  "mcpServers": {
    "quantum": {
      "url": "http://localhost:8080/mcp"
    }
  }
}
----

Or add the server URL in Cursor Settings > MCP Servers.

[[agent-tool-concepts]]
=== How MCP Maps to Framework Agent and Tool Concepts

The framework uses a layered architecture where MCP is one of several access paths to the same underlying tool execution engine.
Understanding how these concepts relate helps when extending the framework or building custom integrations.

==== Concept Mapping

[cols="1,1,3", options="header"]
|===
| MCP Concept | Framework Concept | Relationship

| MCP Tool
| `@Tool`-annotated method
| Each MCP tool is a Java method annotated with `@Tool` (Quarkiverse MCP Server extension) in `McpGatewayTools`.
Tools are defined in code (`McpGatewayTools`, `McpOntologyTools`, `McpDefectTools`) and registered by the extension at build time -- there is no database-backed tool registry.

| MCP Tool Name
| Method-derived name
| The tool name used in MCP `tools/call` (e.g., `query_find`) is the Java method name; the `@Tool` annotations in this module set only a description.

| MCP `tools/call`
| `AgentExecuteHandler.execute(tool, arguments)`
| Both the MCP gateway tools (`McpGatewayTools`) and the REST agent endpoint (`POST /api/agent/execute`) delegate to the same handler. The ontology and defect tools are not routed through it.

| MCP Resource
| `SchemaService` / `QueryHintsProvider`
| MCP resources (`quantum://schema`, `quantum://query-hints`, `quantum://permission-hints`) are backed by the same code that serves the REST `/api/agent/schema`, `/api/agent/query-hints` and `/api/agent/permission-hints` endpoints (`QueryGatewayResource.listRootTypes`, `QueryHintsProvider`, `PermissionHintsProvider`).

| MCP Client
| `quarkus-langchain4j-mcp`
| The framework can also _consume_ tools from external MCP servers.
External MCP clients are configured with `quarkus.langchain4j.mcp.*` properties. The `ToolProviderConfig` entity (collection `tool_provider_configs`: `refName`, `displayName`, `providerType` `REST` or `MCP`, `baseUrl`) lets an application store connection details for external providers; the framework does not create MCP clients from it.

| Agent Config
| `Agent` entity
| An `Agent` is a realm-scoped configuration envelope that pairs an LLM reference with a system prompt (PromptSteps) and a tool filter (enabledTools).
Managed via `/api/agent/config/*` CRUD API; the framework stores it but does not apply it.
|===

==== Execution Flow Comparison

Both MCP and REST reach the same execution path:

....
MCP Client                           REST Client
    |                                     |
tools/call "query_find"           POST /api/agent/execute
    |                             { "tool":"query_find", ... }
    v                                     v
McpGatewayTools                    AgentResource
    |                                     |
    +--------> AgentExecuteHandler <------+
                      |
                      v
              QueryGatewayResource
                      |
                      v
                   MongoDB
....

Row- and field-level governance (realm resolution, DataDomain scope, rule filters, excluded fields) is enforced at the `QueryGatewayResource` level, regardless of whether the request came through MCP or REST.

[[end-to-end-example]]
=== End-to-End Example: Claude Querying a Supply Chain Application

This walkthrough demonstrates a complete flow from starting the application to having Claude interact with live data through MCP.

==== Prerequisites

* Java 17+, Maven 3.9+
* MongoDB running locally (or via Quarkus Dev Services)
* Claude Desktop or Claude Code installed
* Your Quantum-based application (e.g., a supply chain app with `Location`, `Order`, `Shipment` entities)

==== Step 1: Add the MCP Server Module

In your application POM, add the `quantum-mcp-server` dependency:

[source,xml]
----
<dependency>
    <groupId>com.end2endlogic</groupId>
    <artifactId>quantum-mcp-server</artifactId>
    <version>${quantum.version}</version>
</dependency>
----

==== Step 2: Configure Agent Properties

In `src/main/resources/application.properties`:

[source,properties]
----
# --- Authentication ---
auth.provider=custom
quarkus.smallrye-jwt.enabled=true
mp.jwt.verify.publickey.location=publicKey.pem
mp.jwt.verify.issuer=https://myapp.example.com/issuer
mp.jwt.verify.audiences=my-api-client

# --- Query Gateway ---
# Needed for query_find with expand(...); off by default
feature.queryGateway.execution.enabled=true

# --- Per-tenant agent configuration (optional; filters GET /api/agent/tools only) ---
quantum.agent.tenant.default.enabledTools=query_rootTypes,query_plan,query_find,query_count
quantum.agent.tenant.acme-corp.enabledTools=query_rootTypes,query_plan,query_find,query_count,query_save,query_delete
----

The tenant properties shape what `GET /api/agent/tools?realm=...` lists; they do not restrict what the MCP tools execute (see <<tenant-agent-config>>). To make an agent read-only, give its identity permission rules that allow only the read actions.

==== Step 3: Start the Application

[source,bash]
----
mvn quarkus:dev
----

The MCP endpoint is available at `http://localhost:8080/mcp`.

==== Step 4: Configure Claude

**Claude Desktop** -- edit `claude_desktop_config.json`:

[source,json]
----
{
  "mcpServers": {
    "supply-chain": {
      "url": "http://localhost:8080/mcp"
    }
  }
}
----

**Claude Code** -- create `.mcp.json` in the project root:

[source,json]
----
{
  "mcpServers": {
    "supply-chain": {
      "type": "http",
      "url": "http://localhost:8080/mcp",
      "headers": {
        "Authorization": "Bearer ${QUANTUM_TOKEN}"
      }
    }
  }
}
----

==== Step 5: Interact with Claude

Below is a realistic conversation showing how Claude uses the MCP tools:

*User*: What entity types are available in the supply chain system?

*Claude* calls `query_rootTypes` and responds:

____
The system has these entity types: Location, Order, Shipment, Product, Customer, CodeList, UserProfile, Organization.
____

*User*: Show me all active warehouses in the Southeast region.

*Claude* calls `query_find`:

* `rootType`: `"Location"`
* `query`: `"status:ACTIVE && type:WAREHOUSE && region:Southeast"`
* `limit`: `20`

____
Found 3 active warehouses in the Southeast:

1. ATL-WH-01 -- Atlanta Distribution Center (Atlanta, GA)
2. MIA-WH-03 -- Miami Fulfillment Hub (Miami, FL)
3. CLT-WH-02 -- Charlotte Regional Warehouse (Charlotte, NC)
____

*User*: How many open orders are there for the Atlanta warehouse?

*Claude* calls `query_count`:

* `rootType`: `"Order"`
* `query`: `"status:OPEN && warehouseRef:ATL-WH-01"`

____
There are 47 open orders for the Atlanta Distribution Center (ATL-WH-01).
____

*User*: Show me the last 5 orders with their customer details expanded.

*Claude* calls `query_plan` first to check expand support:

* `rootType`: `"Order"`
* `query`: `"expand(customer) && warehouseRef:ATL-WH-01"`

Then calls `query_find` (this needs `feature.queryGateway.execution.enabled=true`, and `customer` must be an `EntityReference` field annotated with `@ReferenceTarget`). The `query_find` tool has no sort argument, so the rows come back in the store's order:

* `rootType`: `"Order"`
* `query`: `"expand(customer) && warehouseRef:ATL-WH-01"`
* `limit`: `5`

____
Here are 5 orders for ATL-WH-01, with customer details:

1. ORD-9921 -- Acme Corp (acme@example.com), 12 items, $2,340
2. ORD-9918 -- Beta Industries (beta@example.com), 3 items, $890
...
____

*User*: What relationships does the Atlanta warehouse have?

*Claude* calls `query_relationships`:

* `entityId`: `"ATL-WH-01"`
* `direction`: `"both"`

____
The Atlanta warehouse has these relationships:

Outgoing:
- `locatedIn` -> Organization "Southeast Division"
- `servesRegion` -> Region "Southeast"

Incoming:
- `fulfilledAt` <- 47 open Orders
- `shipsFrom` <- 12 active Shipments
____

==== What Happened Under the Hood

....
Claude Desktop / Claude Code
    |
    | (1) MCP tools/list -> discovers 18 tools; resources/list -> 3 resources
    |
    | (2) MCP resources/read "quantum://query-hints"
    |     -> learns BIAPI query syntax, expand(), ontology edges
    |
    | (3) MCP tools/call "query_rootTypes"
    |     -> McpGatewayTools.query_rootTypes()
    |        -> AgentExecuteHandler.execute("query_rootTypes", {})
    |           -> QueryGatewayResource.listRootTypes()
    |
    | (4) MCP tools/call "query_find" { rootType, query, limit }
    |     -> McpGatewayTools.query_find(rootType, query, realm, limit, skip)
    |        -> AgentExecuteHandler.execute("query_find", args)
    |           -> QueryGatewayResource.find(FindRequest)
    |              -> Morphia Query -> MongoDB
    |
    | (5) MCP tools/call "query_relationships" { entityId, direction }
    |     -> McpOntologyTools.query_relationships(entityId, direction, ...)
    |        -> ComputedEdgeReader.relationshipEdgesFromSrc() / relationshipEdgesToDst()
    |           -> stored edges plus LAZY/ONDEMAND computed edges
    |
    v
JSON response serialized and returned to Claude
....

At every step the caller must be authenticated, the realm is bound to the caller's effective realm, and the gateway applies the caller's DataDomain scope, rule filters and field exclusions.
A gateway call without an established security context is refused (`SecurityContextMissing`) rather than run unscoped.

==== Adding Ontology Context for Richer Queries

When your application has an ontology TBox defined (see xref:{doc-root}/user-guide/ontology.adoc[Ontologies in Quantum]), Claude can use the `query_predicates` tool to discover relationship types and then use `query_relationships` to traverse the graph.

For example:

*User*: What types of relationships exist between Orders and Organizations?

*Claude* calls `query_predicates`:

* `domainFilter`: `"Order"`
* `rangeFilter`: `"Organization"`

____
Found 2 predicates:

1. `placedByOrg` -- Order -> Organization (the org that placed the order)
2. `fulfilledByOrg` -- Order -> Organization (the org fulfilling the order)
____

This lets Claude build more targeted queries and provide richer answers about entity relationships.

[[mcp-server-config-reference]]
=== MCP Server Configuration Reference

The MCP server requires no additional configuration beyond including the `quantum-mcp-server` module.
The `/mcp` endpoint is automatically registered by the Quarkus MCP Server extension.

Optional properties:

[cols="1,1,3", options="header"]
|===
| Property | Default | Description

| `quarkus.mcp.server.http.root-path`
| `/mcp`
| Root path of the MCP HTTP endpoints (Quarkiverse MCP Server extension; fixed at build time)

| `quarkus.mcp.server.traffic-logging.enabled`
| `false`
| Set to `true` to log MCP JSON-RPC messages for debugging (Quarkiverse MCP Server extension)

| `quarkus.mcp.server.traffic-logging.text-limit`
| `200`
| Number of characters of each message that traffic logging writes

| `feature.queryGateway.execution.enabled`
| `false`
| Set to `true` to enable `expand()` (AGGREGATION mode) in `query_find`

| `quantum.queryGateway.deleteMany.maxMatches`
| `2000`
| Maximum entities that `query_deleteMany` will delete in a single call; a query matching more is rejected and nothing is deleted

| `quantum.queryGateway.export.inlineThreshold`
| `10000`
| `query_export` returns CSV inline when the governed row count is at or below this value, and writes a server-side temporary file above it

| `quantum.ontology.expand.max-targets`
| `1000`
| Maximum distinct targets one page may reach through `expand(@relation)` before the query is refused

| `quantum.ontology.expand.max-edges`
| `10000`
| Maximum edges read per page and relation for `expand(@relation)` before the query is refused

| `quantum.agent.tenant.<realm>.enabledTools`
| (unset)
| Tool names listed by `GET /api/agent/tools?realm=<realm>`; see <<tenant-agent-config>>

| `quarkus.morphia.packages`
| (application-specific)
| Must include `com.e2eq.framework.mcp.defect` for the defect tools
|===

See xref:{doc-root}/user-guide/ai-agent-integration.adoc[AI Agent Integration] for the full agent API design and additional scenarios.
