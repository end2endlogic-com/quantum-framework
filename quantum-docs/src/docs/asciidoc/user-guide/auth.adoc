[[auth]]
= Authentication and Authorization

Quantum integrates with Quarkus security while providing a pluggable approach to authentication. The repository includes a JWT provider module to get started quickly and an extension surface to replace or complement it.

[[authn-authz-separation]]
== Authentication and Authorization Are Separate

Authentication answers one question: who is calling. A verified token proves an identity, named by its issuer (`iss`) and subject (`sub`). Authorization is decided afterwards by the application that receives the request. That application maps the identity to roles, a realm (the database the request runs in), a tenant and policies, using records the platform holds: the credential, realm assignments (`UserRealmRole`), application bindings (`UserAppRole`) and policy rules.

A token is therefore not where roles or tenancy are granted. To give a user access, change the records (a realm assignment, an application binding, a policy); do not add claims to a token, widen its audience or mint a different one.

How `SecurityFilter` builds the principal (`PrincipalContext`) for a verified token depends on configuration:

[cols="2,2,3,4", options="header"]
|===
| Path | Selected by | Read from the token | Where roles, realm and tenant come from

| Local credential (default)
| Nothing set
| Identity, plus the signed `realm`, `tenantId` and role (`groups`) claims
| `PrincipalContextResolver` looks up the credential in the system realm and resolves roles through `IdentityRoleResolver`. Token roles count only in the realm the token was issued for; the signed tenant applies only while the request stays in that realm.

| Delegated claims
| `quantum.auth.trust-token-claims=true` (default `false`)
| Identity, `realm`, `realmRegEx`, roles
| The signed claims of the trusted issuer. No local credential is read. A token without a `realm` claim is refused.

| Remote principal source
| `quantum.auth.principal-source=remote` (unset by default)
| `iss` and `sub` only
| The central Auth service resolves identity plus this application to roles, realm and tenant. See <<remote-principal-source>>.
|===

Identity-only tokens are being introduced in steps. In `1.4.3-SNAPSHOT`:

* Step 1 is implemented. `PrincipalContextResolver` (`quantum-security-runtime`) is the single implementation of principal resolution. Its `IDENTITY` mode reads nothing from the token beyond the identity, resolves identity plus application to realm, tenant and roles, and refuses with typed codes (`PrincipalResolutionError`). Its `SIGNED_TOKEN_CLAIMS` mode is the local credential path above and behaves as before.
* Step 2 is implemented and opt-in. With the remote principal source a receiving application asks Auth instead of reading claims.
* Tokens issued by `quantum-jwt-provider` still carry `realm`, `tenantId`, `orgRefName`, `accountNum` and `groups` claims, and the default path still reads them. Retiring those claims is a later step that is not in this code. New code must not depend on them.

== JWT Provider

- Module: quantum-jwt-provider
- Purpose: Sign in users (`login`, `refreshTokens`), issue RS256-signed access and refresh tokens, and validate JWTs on incoming requests so the security principal carries a verified identity.
- Configuration: Standard Quarkus/MicroProfile JWT properties plus the token lifetime and key properties in the <<auth-configuration-reference,configuration reference>>.

== Pluggable Authentication

You can introduce alternative authentication mechanisms (e.g., API keys, SAML/OIDC front-channel tokens exchanged for back-end JWTs, HMAC signatures) by providing CDI beans that integrate with the security layer.

Typical steps:

1. Implement an `AuthProvider` that validates the token or credential.
2. Return the verified identity (subject and userId). A provider proves who the caller is; it does not decide the caller's realm, tenant or permissions.
3. Let the framework build the `PrincipalContext` from that identity (see <<authn-authz-separation>>). Resources and repositories read the principal, never the raw token.

== Creating an Auth Plugin (using the Custom JWT provider as a reference)

An auth plugin is typically a CDI bean that:

- Extends BaseAuthProvider to inherit user-management helpers and persistence utilities.
- Implements AuthProvider to integrate with request-time authentication flows.
- Implements UserManagement to expose CRUD-style operations for users, passwords, and roles.

A concrete provider should:

- Be annotated as a CDI bean (e.g., @ApplicationScoped).
- Provide a stable getName() identifier (e.g., "custom", "oidc", "apikey").
- Use config properties for secrets, issuers, token durations, and any external identity provider details.
- Build a Quarkus SecurityIdentity with the authenticated principal and roles.

== AuthProvider interface (what a provider must implement)

Core methods:

* SecurityIdentity validateAccessToken(String token)
  - Parse and validate the incoming credential (JWT, API key, signature).
  - Return a SecurityIdentity with principal name and roles. Throw a security exception for invalid tokens.
* String getName()
  - A short identifier for the provider. Persisted alongside credentials and used in logs/metrics.
* LoginResponse login(String userId, String password)
  - Credential-based login. Return a structured response:
    - positiveResponse (`LoginPositiveResponse`): userId, SecurityIdentity, roles, roleAssignments, accessToken, refreshToken, expirationTime, realm, and for application-scoped sign-in the token's `audiences` and `activeApplication`.
    - negativeResponse (`LoginNegativeResponse`): userId, errorCode, errorReasonCode, errorMessage, errorType, errorDetails and realm, for clients to act on (e.g., password change required).
* LoginResponse refreshTokens(String refreshToken)
  - Validate the refresh token, mint a new access token and a new refresh token, and return a positive response.
* String getIssuer() (default `null`)
  - The issuer this provider signs and accepts. Used to route a token to its provider when several are configured.

Optional methods with defaults:

* login(userId, password, applicationId) -- application-scoped sign-in. The default ignores the application and calls the two-argument login.
* login(userId, password, applicationId, realmId) -- realm- and application-scoped sign-in. The default throws `UnsupportedOperationException` when a realm is named, so a provider that does not understand realm membership cannot silently ignore it.
* loginWithVerifiedEmail(EmailChallenge proof, String realmId) -- sign-in for an address proven by an email challenge. It is an internal boundary called after the challenge is verified, never a public endpoint that accepts a "verified" flag. The default throws.

Notes:

- `LoginPositiveResponse` still has a `mongodbUrl` component for binary compatibility. It is never populated: `CustomTokenAuthProvider` passes `null`, and `AuthLoginService` does not copy it into the REST `AuthResponse`. A sign-in never returns the service's database connection string, and a custom provider must not put one there.
- Login flow should check force-change-password or equivalent flags and return a negative response when user interaction is required before issuing tokens.
- validateAccessToken should only accept valid, non-expired tokens and construct SecurityIdentity consistently with role mappings used across the platform.

== UserManagement interface (operations your plugin must support)

Typical responsibilities include:

* User lifecycle
  - String createUser(String userId, String password, [optional] Boolean forceChangePassword, Set<String> roles, DomainContext domainContext, [optional] DataDomain)
  - String createUser(String userId, String password, Boolean forceChangePassword, Set<String> roles, DomainContext domainContext, String applicationRegEx) -- default method; a provider that does not model application boundaries throws for a non-null pattern
  - String createEmailUser(String email, Set<String> roles, DomainContext domainContext, String applicationId) -- default method; throws unless the provider supports EMAIL credentials
  - void changePassword(String userId, String oldPassword, String newPassword, Boolean forceChangePassword)
  - void resetPassword(String userId, String newPassword, Boolean forceChangePassword)
  - void changeEmail(String userId, String newEmail)
  - void resendTemporaryPassword(String userId)
  - boolean removeUserWithUserId(String userId)
  - boolean removeUserWithSubject(String subject)
* Role management
  - void assignRolesForUserId(String userId, Set<String> roles)
  - void assignRolesForSubject(String subject, Set<String> roles)
  - void removeRolesForUserId(String userId, Set<String> roles)
  - void removeRolesForSubject(String subject, Set<String> roles)
  - Set<String> getUserRolesForUserId(String userId)
  - Set<String> getUserRolesForSubject(String subject)
* Lookups and existence checks
  - Optional<String> getSubjectForUserId(String userId)
  - Optional<String> getUserIdForSubject(String subject)
  - boolean userIdExists(String userId)
  - boolean subjectExists(String subject)

Return values and exceptions:

- Throw SecurityException or domain-specific exceptions for invalid states (duplicate users, bad password, unsupported hashing).
- Return Optional for lookups that may not find a result.
- For removals, return boolean to communicate whether a record was deleted.

Which credentials may hold a password:

- `AuthCredentialService` (`quantum-system-management`) checks the credential type before it resolves a provider for reset-password, change-password and resend-temporary-password. Only `PASSWORD` and `EMAIL` credentials are password-managed. A `SERVICE_TOKEN`, `API_KEY` or `OAUTH` credential is refused with "Credential type ... does not support password management", and naming a provider (`?provider=custom`) does not change that.
- Change-email is refused for the same non-user credential types.

== Leveraging BaseAuthProvider in your plugin

When you extend BaseAuthProvider, you inherit ready-to-use capabilities that reduce boilerplate:

* Impersonation controls
  - enableImpersonationWithUserId / enableImpersonationWithSubject
  - disableImpersonationWithUserId / disableImpersonationWithSubject
  - These set or clear an impersonation filter script and realm regex that downstream services can honor to act on behalf of another identity under controlled scope.

* Realm override helpers
  - enableRealmOverrideWithUserId / enableRealmOverrideWithSubject
  - disableRealmOverrideWithUserId / disableRealmOverrideWithSubject
  - These set or clear the credential's `realmRegEx`, the authority an explicit `X-Realm` request is checked against. Grant it only to identities that need to act outside their own realm (see <<realm-override-x-realm>>).

* Persistence utilities
  - Built-in use of the credential repository to save, update, and delete credentials.
  - Consistent validation of inputs (non-null checks, non-blank checks).
  - Hashing algorithm guardrails to ensure only supported algorithms are used.

Best practices when deriving:

- Record the auth provider name in stored credentials as informational provenance. It tells callers which provider resolved the credential or token; it is not an authentication routing or authorization binding.
- Reuse the role merge/remove patterns to avoid accidental role loss.
- Prefer emitting precise exceptions (e.g., NotFound for missing users, SecurityException for access violations).

== Implementing your own provider

Checklist:

* Class design
  - @ApplicationScoped bean
  - extends BaseAuthProvider
  - implements AuthProvider and UserManagement
  - return a stable getName()
* Configuration
  - Externalize secrets (signing keys), issuers, token durations, and realm details via MicroProfile Config.
* SecurityIdentity
  - Consistently build identities with principal and roles; include useful attributes for auditing/telemetry.
* Tokens/credentials
  - For JWT-like tokens, implement robust parsing, signature verification, expiration checks, and claim validation.
  - For non-JWT credentials (API keys, HMAC), ensure replay protection and scope binding.
* Responses and errors
  - Use structured LoginResponse for both success and error paths.
  - Prefer idempotent user/role operations; validate inputs and surface actionable messages.

== CredentialUserIdPassword model and DomainContext

This section explains how user credentials are represented, how those records tie to tenancy and realms, and how the server chooses the database (“realm”) for REST calls.

What the credential model represents

userId:: The human-friendly login handle that users type. Must be unique within the applicable tenancy/realm scope.
subject:: A stable, system-generated identifier for the principal. Tokens and internal references favor subject over userId because subjects do not change.
description, emailOfResponsibleParty:: Optional metadata to describe the credential and provide an owner contact.
domainContext:: The tenancy and organization placement of the principal. It contains:
  - tenantId: Logical tenant partition.
  - orgRefName: Organization/business unit within the tenant.
  - accountId: Account or billing identifier.
  - defaultRealm: The default database/realm used for this identity’s operations.
  - dataSegment: Optional partitioning segment for advanced sharding or data slicing.
roles:: The flat roles of the credential (e.g., `user`, `admin`). Flat roles are global by design: whenever the principal is resolved from the credential (the default path and identity-only resolution) they apply in every realm the credential can enter. Roles that should hold in one realm or tenant only belong on the realm assignment (`UserRealmRole`) or an application binding (`UserAppRole`), not here. A token issued for a realm other than the credential's home realm does not list the flat roles in its `groups` claim, so a service that runs on delegated claims sees only the roles that token carries.
credentialType:: `PASSWORD` (default), `EMAIL`, `SERVICE_TOKEN`, `API_KEY` or `OAUTH`. An `EMAIL` credential signs in by a single-use email challenge and may also set a password as a second sign-in method; a `PASSWORD` credential never gains email sign-in. Only `PASSWORD` and `EMAIL` credentials may hold a password.
serviceKind:: For service credentials only: `APPLICATION` (the service runs as itself in the one realm and tenant of its own DomainContext) or `DELEGATING` (a multi-tenant service that may act on behalf of an identity inside its impersonation authorization). An unset kind is never treated as `DELEGATING`.
parentCredentialSubject:: For a `SERVICE_TOKEN` credential, the subject of the credential that created it.
issuer:: An identifier for who issued the credential or tokens (useful for auditing and multi-provider setups).
passwordHash, hashingAlgorithm:: The stored password hash and declared algorithm. Server-owned and not exposed over REST: field-pair and bulk updates refuse them, and a save or merge that omits the hash keeps both as stored. Providers verify passwords against this.
passwordChangedAt, passwordRevision:: Server-owned and never read from or written by REST. `passwordRevision` counts password-hash changes; a session remembers the revision it signed in at and stops refreshing once it moves (see <<session-lifetime>>).
A save or merge of an existing credential that omits the password hash keeps the
stored hash, hashing algorithm, password revision and change time. This supports
metadata and role updates after reading a credential without its secret fields. A
changed, non-null hash still advances the revision. `passwordHash`, `hashingAlgorithm`,
`passwordChangedAt` and `passwordRevision` are server-owned: field-pair and bulk
updates refuse them, and a metadata save cannot change the algorithm on its own. Use
the password change/reset operations to replace a password and active status to
disable a credential; a null hash in a metadata update is not a password removal.

forceChangePassword:: Flag that forces a password reset on next login; the login flow returns a structured negative response instead of tokens.
lastUpdate:: Timestamp for auditing.
area2RealmOverrides:: Optional map to route specific functional areas to different realms than the default (e.g., “Reporting” → analytics-realm).
authorizedRealms, realmRegEx:: The realms this identity may enter besides its home realm. An explicit `authorizedRealms` list takes precedence; `realmRegEx` is used only when the list is empty. This is the authority an `X-Realm` request is checked against.
applicationRegEx:: The credential-wide pattern of applications this identity may sign in to (`*` means any). A realm assignment's `authorizedApplications` adds to it for that realm and never narrows it.
impersonateFilterScript, authorizedImpersonateIds:: Who this identity may impersonate, or for a delegating service whom it may act for: an explicit list of identities and/or a script that must return true.
dataDomainPolicy:: Optional per-credential rules for which DataDomain new records are written to (see the permissions guide).
authProviderName:: Informational provenance naming the provider that resolved this credential or token (e.g., “custom”, “oidc”). Provider selection comes from an explicit request override or the ordered `auth.provider` configuration, never from this field.

How the realm for a REST call is selected

- For each authenticated request the server builds a `PrincipalContext` for the verified identity. Its `defaultRealm` names the backing MongoDB database (“realm”) repositories use for that request.
- On the default path the realm is the one the token was issued for, or the credential's home realm (`DomainContext.defaultRealm`) when the token names none. An application may fix its own realm with `quantum.security.session.realm` (see <<application-session>>).
- With the remote principal source, a request that names no realm runs in the realm resolved from the application (see <<remote-principal-source>>).
- `X-Realm` is an explicit override that needs authority. Clients do not send it on ordinary calls (see <<realm-override-x-realm>>).
- `area2RealmOverrides` may route one functional area to another realm for that area alone.
- The remainder of DomainContext (tenantId, orgRefName, accountId, dataSegment) becomes the principal's DataDomain and is applied through permission rules and repository filters, so reads and writes are restricted to the correct tenant/org segment.

Typical flow

1. Login
   - A user authenticates with userId/password (or an email challenge).
   - On success the service returns an access token and a refresh token, with the realm, roles and applications the sign-in resolved.
2. Subsequent REST calls
   - The token is validated; the server resolves the identity to a `PrincipalContext` (realm, DataDomain, roles) as described in <<authn-authz-separation>>.
   - Repositories choose the datastore for the principal's realm and enforce tenant/org filters from its DataDomain.
   - If the request targets a functional area with a defined override, the operation may route to a different realm for that area alone.
3. UI implications
   - The client does not need to know which realm is selected; it simply calls the API with its token. The server selects the database from the resolved principal.

Best practices

- Keep userId immutable once established; use subject for internal joins and token subjects.
- Always attach the correct DomainContext when creating users to avoid cross-tenant leakage.
- Use realm overrides deliberately for well-isolated areas (e.g., analytics, archiving) and document them for operators.
- Do not rewrite a credential's DomainContext or flat roles to give access to one more realm or tenant. Add a realm assignment or an application binding instead (see xref:{doc-root}/user-guide/identity-and-membership.adoc[Identity, Organizations and Realm Access]).

== Quarkus OIDC out-of-the-box and integrating with common IdPs

Quarkus ships with first-class OpenID Connect (OIDC) support, enabling both service-to-service and browser-based logins.

What the Quarkus OIDC extension provides

* OIDC client and server-side adapters:
  - Authorization Code flow with PKCE for browser sign-in.
  - Bearer token authentication for APIs (validating access tokens on incoming requests).
  - Token propagation for downstream calls (forwarding or exchanging tokens).
* Token verification and claim mapping:
  - Validates issuer, audience, signature, expiration, and scopes.
  - Maps standard claims (sub, email, groups/roles) into the security identity.
* Multi-tenancy and configuration:
  - Supports multiple OIDC tenants via configuration, each with its own issuer, client id/secret, and flows.
* Logout and session support:
  - Front-channel and back-channel logout hooks depending on provider capabilities.

Integrating with common providers

- Works with any identity provider that exposes standard OIDC discovery.
- Configure the issuer URL and client credentials. Quarkus discovers endpoints via the provider’s .well-known/openid-configuration.
- Use the provider to prove who the user is. Roles and tenancy for a Quantum application come from the application's own records (realm assignments, application bindings, policies), as described in <<authn-authz-separation>>.

OIDC vs OAuth vs OpenID (terminology and evolution)

 OAuth 2.0::
  - Authorization framework for delegated access (scopes), not authentication. Defines flows to obtain access tokens for APIs.
OpenID (OpenID 1.x/2.0)::
  - Older federated identity protocol that preceded OIDC. It has been superseded by OpenID Connect.
OpenID Connect (OIDC)::
  - An identity layer on top of OAuth 2.0. Adds standardized authentication, user info endpoints, ID tokens (JWT) with subject and profile claims, and discovery metadata.
  - In practice, OIDC is the modern standard for SSO and user authentication; OAuth remains the authorization substrate underneath.
Summary::
- OpenID → historical, replaced by OIDC.
- OAuth 2.0 → authorization framework.
- OIDC → authentication (identity) layer built on OAuth 2.0.

OIDC and SAML in relation to SSO
 SAML (Security Assertion Markup Language)::

  - XML-based federation protocol widely used in enterprises for browser SSO.
  - Uses signed XML assertions transported through browser redirects/posts.
OIDC::
  - JSON/REST-oriented, uses JWTs, and is well-suited for modern SPAs and APIs.
- Relationship:
  - Both enable SSO and federation across identity providers and service providers.
  - Many enterprise IdPs support both; OIDC is generally simpler for APIs and modern web stacks, while SAML is entrenched in legacy/enterprise SSO.
- Bridging:
  - Gateways or identity brokers can translate SAML assertions to OIDC tokens and vice versa, allowing gradual migration.

Common customer IdP models and OIDC integration patterns

* Centralized IdP (single-tenant):
  - One organization-wide IdP issues tokens for all users.
  - Configure a single OIDC tenant in Quarkus; map groups/roles to application roles.
* Multi-tenant SaaS with per-tenant IdP:
  - Each customer brings their own IdP (BYOID).
  - Configure Quarkus OIDC multitenancy with per-tenant issuer discovery and client credentials.
  - Tenant selection can be based on domain, request header, or path; the selected OIDC tenant performs login and token validation.
* Brokered identity:
  - Use a broker (e.g., a central identity layer) that federates to multiple upstream IdPs (OIDC, SAML).
  - Quarkus integrates with the broker as a single OIDC client; the broker handles IdP routing and protocol translation.
* Hybrid API and web flows:
  - Browser apps use Authorization Code flow with sessions; APIs use bearer token authentication.
  - Quarkus OIDC extension can handle both in the same application when properly configured.

Best practices

- Prefer OIDC for new integrations; use SAML through a broker if enterprise constraints require it.
- Resolve roles server-side from the application's records so downstream authorization (RuleContext, repositories) sees the same role names whichever IdP authenticated the user.
- Use client credentials (service tokens) for service-to-service calls made as the service; do not reuse end-user tokens where not appropriate.
- For multi-tenant OIDC, secure tenant resolution logic and validate issuer/tenant binding to prevent mix-ups.

== Authorization via RuleContext

Authentication establishes identity; RuleContext enforces what the identity can do. For each action (CREATE, UPDATE, VIEW, DELETE, ARCHIVE), RuleContext can:

- Allow or deny the action
- Contribute additional filters (e.g., org scoping, functional-area specific sharing)
- Adjust UIActionList to reflect permitted next steps

This division of responsibilities keeps providers focused on identity while policies remain centralized in RuleContext.

[[jwt-tokens-for-api-access]]
== Generating JWT Tokens for API Access

Applications frequently need machine-to-machine access that does not go through an interactive login flow.
The framework provides two mechanisms: **short-lived user tokens** generated via the login endpoint, and **long-lived service tokens** generated via the dedicated service-token endpoint.
Both produce standard RS256-signed JWTs. The claims that matter to a receiver are the ones that prove identity: `iss`, `sub`, `aud` and `exp`.

=== Token Anatomy

`TokenUtils` (`quantum-jwt-provider`) signs these claims:

[cols="1,1,3", options="header"]
|===
| Claim | Example | Purpose

| `sub`
| `a1b2c3d4-...` (UUID)
| The subject -- a stable identifier for the principal. For user tokens, this is the user's `subject` from the credential store. For an identity-agnostic service token, the generated subject of its `SERVICE_TOKEN` credential.

| `iss`
| `https://myapp.example.com/issuer`
| Issuer -- must match `mp.jwt.verify.issuer` in the consuming application's config for the token to be accepted.

| `aud`
| `["acme-orders"]`
| Audience. An application-scoped user token carries the set of applications the user is authorized for in the realm (`*` for a wildcard grant). Tokens minted without application scoping use the fixed audience `b2bi-api-client`. Refresh tokens use `b2bi-api-client-refresh`. An identity-agnostic service token carries no `aud`.

| `azp`
| `acme-orders`
| The application the token was issued for (the one actively entered at sign-in), when one applies.

| `scope`
| `authToken`
| Distinguishes access tokens (`authToken`) from refresh tokens (`refreshToken`).

| `iat`, `exp`
| `1707849600`
| Issued-at and expiration timestamps (seconds since epoch).

| `auth_time`
| `1707849600`
| When the user originally signed in. Copied unchanged through refresh; the session's maximum length is counted from it.

| `token_type`
| `service`
| Present only on an identity-agnostic service token.

| `jti`
| credential id
| On a token bound to one user and one service: the id of the revocable credential record.

| `userId`, `realm`, `tenantId`, `orgRefName`, `accountNum`, `realmRegEx`, `groups`
| `["admin", "user"]`
| Legacy authorization claims: the user id, the realm and data domain the token was issued for, the credential's realm boundary and the roles resolved at sign-in. The default and delegated-claims paths still read them; the remote principal source ignores them. They are scheduled to be retired (see <<authn-authz-separation>>): do not grant access by adding or editing these claims.

| `pwd_rev`, `oauth_client_id`
|
| Refresh tokens only: the password revision the session signed in at, and the OAuth client the session is bound to.
|===

The token is signed with the application's RSA private key using the RS256 algorithm.
In the `dev` and `test` profiles the key defaults to `privateKey.pem` on the classpath (provided by the `quantum-default-keys` module).
In any other profile startup fails unless `quantum.jwt.private-key-location` and `quantum.jwt.public-key-location` are both set explicitly: there is no default-key fallback in production.
Consumers validate the signature using the corresponding public key (`publicKey.pem` or the configured `quantum.jwt.public-key-location`).

=== Generating User Tokens via Login

The standard way to obtain a token is the login endpoint, `POST /security/login` (`SecurityResource` in `quantum-system-rest`). The credentials go in a JSON body (`AuthRequest`), never in the URL:

[source,bash]
----
curl -sS -X POST \
  -H 'Content-Type: application/json' \
  http://localhost:8080/security/login \
  -d '{"userId": "admin@example.com", "password": "secret", "applicationId": "acme-orders"}'
----

`applicationId` names the application being signed in to. It may be omitted when the user is authorized for exactly one application or has a default; when several are possible and none is selected, the response lists the choices (`ApplicationSelectionRequired`). An application the user is not authorized for answers 403 (`ApplicationNotAuthorized`), and a credential with no application authorization at all cannot sign in (`ApplicationAuthorizationMissing`). An optional `realm` (or an `X-Realm` header; the two must agree) asks to sign in to a specific realm the credential is authorized for. Without one the sign-in uses the credential's home realm.

Response (`AuthResponse`):

[source,json]
----
{
  "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6...",
  "refresh_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6...",
  "expires_at": 1707853200,
  "realm": "acme-example",
  "roles": ["user"],
  "authProvider": "custom",
  "applications": ["acme-orders"],
  "activeApplicationId": "acme-orders"
}
----

The response also lists `accessibleRealms` and `accessibleTenants`. The camel-case aliases `accessToken`, `refreshToken`, `expiresAt` and `activeApplication` are still emitted for older clients and are deprecated. The response has no database URL: the `mongodburl` field is never populated.

[[session-lifetime]]
==== Session lifetime and refresh

The access token expires after the configured duration (`com.b2bi.jwt.duration` in seconds).
The refresh token has its own, longer lifetime (`quantum.auth.refresh-token.duration`, 7 days by
default, and never shorter than the access token's). Each refresh returns a new access token and a new refresh token.

Refreshing keeps a session alive for at most `quantum.auth.session.max-duration` (30 days by default), counted from the original sign-in (`auth_time`):

* Neither token of the last refresh may outlive that deadline. Both are cut short to it, so the final access token can be shorter-lived than the configured duration.
* The refreshed refresh token is minted at an absolute expiry, so a slow refresh cannot push it past the deadline.
* Once the deadline is reached the refresh is refused (`SESSION_MAX_DURATION_REACHED`) and the user signs in again.
* A refresh token issued before `auth_time` was carried counts its session from its own issue time.

A password change ends earlier sessions. The credential counts password-hash changes (`passwordRevision`, server-owned). A refresh token carries the revision its sign-in read (`pwd_rev`), and a refresh is refused (`SESSION_ENDED_BY_PASSWORD_CHANGE`) once the credential's revision has moved on. Access tokens already issued remain valid until they expire. Refresh tokens issued before the revision claim existed are compared with `passwordChangedAt` instead, and adopt the current revision on their next refresh.

Every refresh also re-checks the credential and its grants: the credential must be active, still authorized for the token's realm, and still authorized for the application.

Refresh with `POST /security/refresh`, sending the refresh token in the body:

[source,bash]
----
curl -sS -X POST \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: application/json' \
  http://localhost:8080/security/refresh \
  -d '{"refresh_token": "<refresh-token>"}'
----

The endpoint is annotated `@Authenticated`, so the request must also carry a bearer token the service accepts. A missing `refresh_token` answers 400; a refused refresh answers 401. A successful refresh answers with the same `AuthResponse` shape. An OAuth session is refreshed at `/oauth/token` instead (see xref:{doc-root}/user-guide/oauth-server.adoc[OAuth Server Module]).

This flow is appropriate for interactive clients (UIs, CLI tools) that can handle periodic token refresh.

==== Email sign-in and password setup

An `EMAIL` credential signs in by proving possession of the mailbox with a single-use challenge (`EmailChallenge`). A challenge has a purpose, and it redeems only for that purpose:

* `CLI_SIGN_IN` and `PORTAL_SIGN_IN` sign the user in.
* `PASSWORD_SETUP` is an emailed set-password link. It never signs anyone in, and a sign-in link never sets a password.

An `EMAIL` credential may set a password as an optional second sign-in method; email sign-in stays available. The framework provides the challenge model, the verifier (`EmailChallengeVerifier`) and `AuthProvider.loginWithVerifiedEmail`; the endpoints that send and redeem the emails belong to the service that hosts sign-in.

[[service-tokens]]
=== Service Tokens for System-to-System Integration

For integrations that cannot perform interactive login -- MCP servers, cron jobs, webhook handlers, CI/CD pipelines, partner APIs -- the framework provides **service tokens**: long-lived JWTs with a dedicated credential record.

==== Generating a Service Token

Service tokens are minted at `POST /security/service-token`. The endpoint is served by the service that owns sign-in (`quantum-auth-service` in the reference architecture). The framework modules in this repository supply the request record (`ServiceTokenRequest`), the minting primitives (`CustomTokenAuthProvider.generateServiceToken` and `generateBoundUserToken`) and the CLI client; they do not expose the endpoint themselves.

[source,bash]
----
curl -sS -X POST \
  -H 'Authorization: Bearer <access-token>' \
  -H 'Content-Type: application/json' \
  http://localhost:8080/security/service-token \
  -d '{
    "roles": ["user"],
    "expirationSeconds": 31536000,
    "description": "MCP server integration token"
  }'
----

Alternatively, you can use the **Quantum CLI** tool to generate service tokens interactively or via command-line arguments.

==== Request Parameters

[cols="1,1,1,3", options="header"]
|===
| Field | Type | Required | Description

| `roles`
| string array
| Yes
| Roles to embed in the token and store on the credential (e.g., `["user"]`, `["agent-read"]`). Give the token only the roles it needs.

| `expirationSeconds`
| long
| For an identity-agnostic token, no. For a token bound to the caller, yes.
| Seconds until expiry. When `null` on an identity-agnostic token, the token is issued for approximately 100 years. A token bound to the caller rejects a null duration and rejects a duration longer than 366 days.

| `description`
| string
| No
| Human-readable label for the credential (e.g., `"Nightly sync job"`, `"MCP integration"`).

| `userId`
| string
| No
| The caller's own user id. When present, the issued JWT is that user's token for `applicationRef`. A value other than the caller's user id is refused.

| `applicationRef`
| string
| For a token bound to the caller, yes. For an identity-agnostic token, no.
| The one service the token is for; it becomes the token's `aud` and `azp`. Omit it, and omit `userId`, to mint an identity-agnostic token.

| `realm`, `audiences`
| string, string array
| No
| Retained for wire compatibility. Ignored for an identity-agnostic token: a service token identifies its caller and is not bound to a realm or a resource. A token bound to the caller uses the caller's own realm.

| `authorizedTenantIds`
| string array
| No
| Tenants the service may select within its realm.
|===

==== Who may mint

Two permissions control this endpoint. They are roles on the caller's token. Neither is implied by `admin` or `user`, and neither implies the other.

* `mint-own-service-token` — the caller may mint a token for their own user and one service (`applicationRef`). If `userId` is omitted, the token is still bound to the caller. The JWT carries that user, realm, and tenant, `aud` and `azp` set to that service, a finite `exp`, and a `jti` credential id. It does not set `token_type` to `service`. This mint does not require `mint-agnostic-service-token`.
* `mint-agnostic-service-token` — required to mint an identity-agnostic service token, the credential for a multi-tenant or multi-user service. The request names neither a user nor one service. Holding this permission does not block a caller who also holds `mint-own-service-token` from minting an identity and service specific token, and it does not let the caller mint a token for someone else.

A request that names a `userId` other than the caller's is refused. If `X-Acting-On-Behalf-Of-UserId` disagrees with the bound user, the mint is refused. The header does not choose the payer.

==== What Happens on the Backend

When you call `POST /security/service-token`, the Auth service:

1. **Validates the caller** -- the endpoint allows `mint-own-service-token` or `mint-agnostic-service-token`. An identity-agnostic token requires the second permission. A token for the caller and one service requires the first, and names that service in `applicationRef`.
2. **Looks up the caller's credential** -- from the JWT `sub` claim, the framework finds the caller's `CredentialUserIdPassword` in the system realm.
3. **Creates a new `SERVICE_TOKEN` credential** with:
   * `userId`: `svc:<uuid>` (auto-generated, not user-controlled)
   * `subject`: A new UUID
   * `credentialType`: `SERVICE_TOKEN`
   * `parentCredentialSubject`: The caller's subject (for audit trail)
   * `roles`: From the request
   * `domainContext`: Inherited from the caller's credential (same realm, tenant, org)
   * `issuer`: The configured `mp.jwt.verify.issuer`
4. **Saves the credential** to MongoDB.
5. **Links it to the caller's UserProfile** via `additionalCredentialRefs` so the token can be traced to its creator.
6. **Signs and returns the JWT**. For a token bound to the caller and one service, the stored credential id is signed as `jti`, the JWT subject and `userId` are the caller's, and `aud` and `azp` are that service. That JWT does not set `token_type` to `service`. An identity-agnostic token keeps the generated service subject and sets `token_type` to `service`.

==== Using a Service Token

The service token is used like any other JWT -- pass it in the `Authorization` header:

[source,bash]
----
curl -sS -X GET \
  -H 'Authorization: Bearer <service-token>' \
  http://localhost:8080/api/query/rootTypes
----

The `SecurityFilter` validates the token. An identity-agnostic service token is looked up by its service `sub`. A token bound to the caller is that user's token: its `sub` and `userId` are the caller's, and its `jti` names the revocable credential record. A consumer that checks only the signature, issuer, and expiry accepts that token until `exp`; it does not see a later revocation of the credential record.

==== Example: Configuring an MCP Server with a Service Token

Generate a token for your MCP integration:

[source,bash]
----
# Login as admin first
ACCESS_TOKEN=$(curl -sS -X POST \
  -H 'Content-Type: application/json' \
  http://localhost:8080/security/login \
  -d '{"userId": "admin@mycompany.com", "password": "admin-secret"}' \
  | jq -r '.access_token')

# Generate a service token with read-only roles
SERVICE_TOKEN=$(curl -sS -X POST \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H 'Content-Type: application/json' \
  http://localhost:8080/security/service-token \
  -d '{
    "roles": ["user"],
    "expirationSeconds": 31536000,
    "description": "MCP integration - read-only"
  }' | jq -r '.token')

echo "Service token: $SERVICE_TOKEN"
----

Then configure your MCP client to use it via a bridge that includes the token:

[source,json]
----
{
  "mcpServers": {
    "quantum": {
      "command": "node",
      "args": ["/path/to/quantum-mcp-bridge/dist/index.js"],
      "env": {
        "QUANTUM_BASE_URL": "https://api.mycompany.com",
        "QUANTUM_AUTH_TOKEN": "<paste-service-token-here>"
      }
    }
  }
}
----

For the native MCP server (when the Quantum app itself serves `/mcp`), authentication depends on your deployment.
In development, the MCP endpoint may be accessible without a token if you configure it appropriately.
In production, configure your MCP client or reverse proxy to include the service token as a Bearer header.

=== How Tokens Scope to Security Policies

A token does not grant unlimited access.
Every API call passes through the same security pipeline regardless of whether it was made by a human user, an MCP client, or a service integration.

==== Token-to-Policy Flow

The flow below is the default (local credential) path. The other two paths in <<authn-authz-separation>> build the same `PrincipalContext` from a different source and then continue identically.

....
JWT arrives in Authorization header
    |
    v
SecurityFilter verifies the JWT (signature, issuer, audience, expiry)
    |
    v
PrincipalContextResolver: "sub" -> CredentialUserIdPassword in the system realm
    |
    v
Build PrincipalContext:
    - userId (from credential)
    - applicationId (the session application)
    - roles (TOKEN + CREDENTIAL + REALM + USERGROUP, see Role Merging)
    - defaultRealm (the realm the request runs in)
    - dataDomain (tenantId, orgRefName, accountNum, dataSegment, ownerId)
    - area2RealmOverrides (optional per-area realm routing)
    |
    v
Realm switch (only if requested), application admission, tenant selection
    |
    v
Determine ResourceContext:
    - area and functionalDomain (from @FunctionalMapping on the model or resource)
    - action (from @FunctionalAction, a path keyword, or the HTTP method)
    |
    v
RuleContext.checkRules(principalContext, resourceContext):
    - Match rules by identity (role or userId)
    - Match by area, functionalDomain, action
    - Apply DataDomain constraints (tenantId, orgRefName, etc.)
    - Return ALLOW / DENY with winning rule name
    |
    v
If DENY -> HTTP 403 with decision details
If ALLOW (EXACT) -> proceed, no data filters
If ALLOW (SCOPED) -> proceed with data-level filters applied at repo layer
....

==== Role Merging

On the default path `IdentityRoleResolver` computes the effective roles for (credential, realm, application) from four sources (`RoleSource`):

1. **TOKEN**: The roles in the verified token. They are honored only in the realm the token was issued for. After a realm switch, or for a token minted for another application, they are not adopted.
2. **CREDENTIAL**: The flat `roles` on the `CredentialUserIdPassword`. Flat roles are global by design: they apply in every realm the credential can enter.
3. **REALM**: The roles of the user's active `UserRealmRole` for the realm the request runs in. This is where per-realm roles belong. When `quantum.directory.mode=remote` the local copy of realm assignments is not an authority and is not read.
4. **USERGROUP**: Roles of the `UserGroup` records the user's `UserProfile` belongs to, in the system realm and in the target realm, for groups that apply to the session application.

The union becomes the effective role set for the request. With no role at all the principal gets `ANONYMOUS`.

In identity-only resolution the token contributes no roles: the result is the credential, realm and group roles, plus the roles of the application bindings that grant the selected tenant (see xref:{doc-root}/user-guide/tenant-models.adoc#application-bindings[Application bindings]).

==== Data Scoping via DataDomain

The realm the request runs in and the selected tenant determine which tenant, organization and account the principal operates within: the credential's own `DomainContext` in its home realm, the realm's registered `DomainContext` after a realm switch, or the selected tenant's membership in a shared realm.
This becomes a `DataDomain` that rules apply as query filters at the repository layer:

* **tenantId**: Isolates data by tenant.
* **orgRefName**: Scopes to an organization within the tenant.
* **accountNum**: Scopes to an account.
* **ownerId**: Set to the principal's userId; used for owner-based access rules.

These constraints are enforced by governed repositories and cannot be chosen by the token holder: a request body or CSV import cannot set a record's `dataDomain` (see the permissions guide).

[[application-session]]
==== Application Session (`quantum.security.session.*`)

A verified token says who the user is; it does not decide which application or realm the request runs as.
By default `SecurityFilter` takes the session application from the token's `azp` and the realm from the token, so a token minted by another application (for example a launch pad handoff) is evaluated as that application in its realm.

An application opts into its own session by setting:

[source,properties]
----
quantum.security.session.application-id=decision-intelligence
quantum.security.session.realm=di-realm
----

With these set, a user's `PrincipalContext` (and `ResourceContext`) carries the configured application id, the request runs in the configured realm (the user must be allowed in it, exactly as for `X-Realm`), and roles resolve through `IdentityRoleResolver` for (userId, that realm, that application).
How the user signed in does not matter.
A token minted for another application (its `azp` differs, or is missing) says nothing about this one:

* the user must be admitted to the session application in the session realm by the application admission rule (see _Which application may run there_ under the remote principal source); otherwise the request is refused with 403 "Signed in as <user>, no access to application '<app>' in realm '<realm>'";
* the token's roles are not adopted, neither by the policy engine nor by `@RolesAllowed`: the session's roles are re-derived from the credential, the realm assignment and the session application's user groups.
With `quantum.auth.trust-token-claims=true` there is no local group catalog, so such a session gets the credential's flat roles the token also names plus the realm assignment's roles (as after a realm switch); application-scoped group roles are not added.
An explicit `X-Realm` still applies with its own checks.
Service tokens and anonymous requests are unchanged.
Leave both unset to keep the token-derived behaviour.

[[remote-principal-source]]
==== Remote principal source (`quantum.auth.principal-source=remote`)

An application that receives tokens issued by a central `quantum-auth-service` can ask Auth who the caller is instead of reading roles, realm or tenancy from the token (identity-only tokens, step 2).
After the token's signature is verified locally, `SecurityFilter` calls the deployed `RemotePrincipalSource` for every verified JWT (user and service tokens, from the `Authorization` header or a cookie), with this application's id and the request's `X-Realm`, `X-Tenant-Id`, `X-Impersonate-*` and `X-Acting-On-Behalf-Of-*` selections.
A token without `iss` or `sub` is refused (401 `PRINCIPAL_UNKNOWN`) before Auth is asked.
Platform operations that the local paths exempt from tenant selection (control-plane and identity directory resources, service-token and realm administration) ask with `tenantSelection: "optional"`: with no tenant requested Auth answers without one instead of `TENANT_SELECTION_REQUIRED`, and a requested tenant is still authorized.
Auth applies the realm switch, application grant, default-tenant rule, impersonation and delegation; the filter skips its own realm override, admission and tenant selection, and still runs `PrincipalContextPropertiesResolver` beans.
`@RolesAllowed` sees the roles Auth resolved (plus `user`), never the token's `groups`, and the migration check uses the realm Auth resolved.
Questions asked before the resource is matched (roles, a refusal, the migration realm) are asked with tenant selection optional; `SecurityFilter` then asks with the resource's own rule. Each distinct question is asked once per request.
Only `iss` and `sub` are read from the token. `PrincipalContextPropertiesResolver` beans still run and receive the verified token: they must not read roles, realm or tenancy from its claims, only from the principal context they are given.

*Which realm the request runs in.* Without `X-Realm`, identity-only resolution takes the realm from the application: a realm the application owns (`Realm.applicationRef`) is where its data lives. If the identity's home realm is owned by the application, the request runs there. Otherwise it looks at the realms the application owns in which the identity holds an active assignment (status `active` or unset; not `invited` or `suspended`), allowed by its realm authorization (`authorizedRealms`, `realmRegEx`), and, for a shared realm, with at least one tenant it can reach. This holds even when the home realm also grants the application.

* None: the request stays in the home realm, and application admission decides there as before.
* Exactly one: the request runs in it. This is how a shared-realm application (one realm owned by the application) reaches identities homed elsewhere, with no realm configured in the application.
* Several: 403 `REALM_NOT_AUTHORIZED`; the realm must be selected explicitly (the reasons are logged by Auth, not returned).

The tenant is then chosen in that realm by the default-tenant rule. A delegating service acting for an identity is checked against the realm chosen this way for that identity, after the identity is confirmed to be in the service's scope; any refusal about the acted-for identity reads `DELEGATION_NOT_ALLOWED`. Impersonation still runs in the target's home realm. Applications configure nothing for this: remote mode still refuses `quantum.security.session.realm`.

*Which application may run there.* Wherever a user's application is checked against a realm (identity resolution, an `X-Realm` switch, and an application session receiving another application's token), one admission rule decides. An application is admitted in a realm when the realm is owned by it (`Realm.applicationRef`), or when it is granted to the identity there, either on its realm assignment (`authorizedApplications`) or by the credential's `applicationRegEx`. That is the grant login applies. Having a session in the realm is not itself a grant: switching into the realm, or receiving another application's token there, admits only an application the identity is granted. A resource server that trusts token claims (`quantum.auth.trust-token-claims=true`) has no local credential catalog: there only the realm's owner and the assignment admit, and repeating the token's own realm is not re-checked. A calling service's `X-Realm` switch is governed by the service's realm authorization, not by this rule.

*Application bindings decide first.* Before the rules above, identity-only resolution reads the identity's application bindings (`UserAppRole`): the identity's own active binding marked `defaultRealm` chooses the realm, a binding for the application in the realm admits it and supplies the tenant and the binding's roles, and only when no binding applies does the realm assignment's `authorizedApplications` grant decide. A suspended or malformed binding refuses; it never falls back. See xref:{doc-root}/user-guide/tenant-models.adoc#application-bindings[Application bindings].

*Impersonation and delegation.* A request either impersonates an identity (`X-Impersonate-Subject` or `X-Impersonate-UserId`, one of them) or acts on behalf of one (`X-Acting-On-Behalf-Of-*`), never both.

* Impersonation is for user credentials. The caller needs an `impersonateFilterScript`; a requested realm is checked against the caller's realm authorization and by the script before any target is looked up; the request then runs as the target in the target's home realm, which must be the requested realm when one was named. When the caller lists `authorizedImpersonateIds`, the target must be one of them. The target's roles are resolved without the impersonator's token roles. Every failure reads `IMPERSONATION_REFUSED`, so a refusal does not reveal whether the target exists. A service credential never impersonates.
* Delegation is for service credentials whose `serviceKind` is `DELEGATING`. The service needs a delegation scope (`authorizedImpersonateIds` and/or `impersonateFilterScript`), and its own realm authorization bounds the realms it may act in. The service is checked before the acted-for identity is looked up; after that every refusal reads `DELEGATION_NOT_ALLOWED`, so delegation cannot be used to probe which identities exist. The result is the acted-for identity resolved as if it had signed in to the same application, with the acting service recorded on the resolution. An `APPLICATION` service runs as itself and may not act for anyone.

* Auth's typed refusals pass through with Auth's status and `{"code", "message"}` body. The codes `PrincipalContextResolver` produces (`PrincipalResolutionError`) are `PRINCIPAL_UNKNOWN` and `PRINCIPAL_DISABLED` (401), `APPLICATION_NOT_GRANTED`, `REALM_NOT_AUTHORIZED`, `TENANT_NOT_AUTHORIZED`, `IMPERSONATION_REFUSED` and `DELEGATION_NOT_ALLOWED` (403), and `TENANT_SELECTION_REQUIRED` (400). Any other code Auth answers passes through unchanged. A request that names no application is refused with `APPLICATION_NOT_GRANTED`: there is no resolution without an application. An untyped 401 from Auth is answered 401 `PRINCIPAL_UNKNOWN`. The refusal is answered before the resource is matched, so `@RolesAllowed` endpoints answer with the same status and code.
* Auth unreachable, or an answer that is not a valid `helixor.principal_context.v1` for this application, with no unexpired resolution held: 503 `PRINCIPAL_RESOLUTION_UNAVAILABLE`. There is no fallback to token claims.
* The receiving application id is `quantum.security.session.application-id`, else `quantum.application-registration.application-id`.
* Startup fails when the value is not `remote`, when no `RemotePrincipalSource` bean is deployed (`quantum-auth-client-provider` provides it), when no application id is configured, or together with `quantum.security.session.realm` or `quantum.security.session.selection-policy`.

[source,properties]
----
auth.provider=quantum-auth-service
quantum.auth-service.base-url=${QUANTUM_AUTH_SERVICE_URL}
mp.jwt.verify.issuer=${HELIXORQ_ISSUER}
mp.jwt.verify.publickey.location=${HELIXORQ_JWKS_URL}
quantum.security.session.application-id=acme-orders
quantum.auth.principal-source=remote
----

Leave the property unset to keep the paths described above unchanged.

[[realm-override-x-realm]]
==== Realm Override with `X-Realm`

`X-Realm` is an explicit override, comparable to `sudo`: it asks to run one request in a realm other than the one the principal would resolve to. It is not a default and clients must not send it on ordinary calls. Without it the realm comes from the token or credential, from `quantum.security.session.realm`, or (identity-only resolution) from the application. UI code that attaches `X-Realm` to every request turns a safety check into routine noise and breaks as soon as the user's authority and the header disagree.

The override needs authority, and the header alone grants nothing:

* the target realm must be registered in the realm catalog;
* the credential must be authorized for it: listed in `authorizedRealms`, or, when that list is empty, matched by `realmRegEx`. With delegated claims the signed `realmRegEx` boundary decides, and a switch into the system realm is never honored;
* when the request carries an application id, the user must be admitted to that application in the target realm;
* token roles and the signed tenant do not carry over: roles are re-derived for the target realm, and in a shared realm the caller must select a tenant (`X-Tenant-Id`) it is authorized for.

A refused override answers 403. On success the `PrincipalContext` is rebuilt with the target realm's `DomainContext` (the caller's userId stays the `ownerId`). During impersonation the realm switch is not applied.

Legitimate uses are operator tooling and service tokens: an identity-agnostic service token has no realm of its own, so it names the realm (and tenant) it works in.

[source,bash]
----
curl -sS -X POST \
  -H 'Authorization: Bearer <service-token>' \
  -H 'X-Realm: acme-corp-staging' \
  -H 'Content-Type: application/json' \
  http://localhost:8080/api/agent/execute \
  -d '{"tool": "query_find", "arguments": {"rootType": "Order", "query": "status:OPEN"}}'
----

==== Limiting Service Token Scope

To follow the principle of least privilege:

* **Assign minimal roles** -- give the service token only the roles it needs. If it only reads data, do not include `admin`.
* **Use per-tenant agent configuration** -- configure `quantum.agent.tenant.<realm>.enabledTools` to restrict which gateway tools the agent can call.
* **Set `maxFindLimit`** -- cap query results with `quantum.agent.tenant.<realm>.maxFindLimit`.
* **Do not send `X-Realm` unless the token must act outside its own realm** -- see <<realm-override-x-realm>>.
* **Use `expirationSeconds`** -- even for long-lived tokens, set an expiration. A 1-year token (`31536000` seconds) is preferable to an effectively infinite one.
* **Monitor and audit** -- the `parentCredentialSubject` on `SERVICE_TOKEN` credentials links every service token to the admin who created it. Token validation logs include the userId and realm for each request.

=== Calling Another Service on a User's Behalf

When your service handles a signed-in user's request and has to call another Quantum service to do it, the user's identity must reach that service. Do not reconstruct it with headers: the receiving service resolves realm, tenant and roles from a verified token, exactly as for a call the user made directly.

Pick the credential by situation:

[cols="2,2,3",options="header"]
|===
| Situation | Credential to send | Headers

| A user is present, the target only needs the user's own permissions (reads, user-level writes), and the target accepts the user's token (see the note below)
| The user's access token, forwarded unchanged
| None. Pass on `X-Realm`, `X-Tenant-Id` or `X-Impersonate-*` only if the user's own request carried that switch; never add one yourself.

| A user is present and your service acts as a proxy with its own credentials (a governed step such as activating an ontology after a steward approves it)
| Your service token
| `X-Tenant-Id` (and `X-Realm` across realms) for the target data; `X-Acting-On-Behalf-Of-UserId` to attribute the user, or `X-Impersonate-*` when the call must run as the user (requires impersonation rights). The user may also be named in the target's own request contract.

| No user is present (scheduled, queued or replayed work)
| Your service token
| `X-Tenant-Id` naming the tenant and `X-Realm` naming its realm (required unless it is the system realm: a service token has no realm of its own); `X-Acting-On-Behalf-Of-UserId` to attribute the work
|===

==== Forwarding the user's token

[source,bash]
----
# inside your handler: reuse the caller's bearer as-is
curl -sS -H "Authorization: Bearer ${USER_ACCESS_TOKEN}" \
  https://ontology.example.com/v1/ontology/tbox
----

The receiving service builds the same `PrincipalContext` the user would get from a direct call, by whichever path it is configured for (see <<authn-authz-separation>>): the user's realm, tenant and roles apply. Your service's own roles play no part.

[NOTE]
====
* A receiver that enforces application admission (`quantum.auth.expected-audience` and `ApplicationTokenAdmissionFilter`, both provided by `quantum-auth-client-provider`, which is not a module of this repository) accepts a user token only if it was issued for that application (`aud` contains it and `azp` is absent or equal to it). A token the user got for application A is refused (403) by application B. Across applications, call B with your service token.
* The forwarded token is the user's full-lifetime bearer. Forward it only within the application's own trust boundary, and never log it.
====

==== Why not a service token with `X-Acting-On-Behalf-Of-*`?

`X-Acting-On-Behalf-Of-*` is for attribution only (see the permissions guide). With a service token the request still runs as your service: without `X-Realm` it runs in the system realm, the tenant comes from `X-Tenant-Id`, and your service's roles apply. Use it only when no user is present.

=== Generating RSA Key Pairs

The framework signs tokens with an RSA key pair.
To generate a new key pair:

[source,bash]
----
# Generate a 2048-bit RSA private key in PKCS#8 format
openssl genpkey -algorithm RSA -out privateKey.pem -pkeyopt rsa_keygen_bits:2048

# Extract the public key
openssl rsa -pubout -in privateKey.pem -out publicKey.pem
----

IMPORTANT: The private key must be in PKCS#8 PEM format (begins with `-----BEGIN PRIVATE KEY-----`). PKCS#1 format (`-----BEGIN RSA PRIVATE KEY-----`) is not supported. If you have a PKCS#1 key, convert it:

[source,bash]
----
openssl pkcs8 -topk8 -inform PEM -outform PEM -nocrypt -in rsa_private.pem -out privateKey.pem
----

==== Where to Place the Keys

There are three options, from simplest to most production-ready:

**Option 1: Use the default keys (development only)**

Add the `quantum-default-keys` module to your application POM.
This places a pre-generated key pair on the classpath automatically — no files to copy.

[source,xml]
----
<dependency>
    <groupId>com.end2endlogic</groupId>
    <artifactId>quantum-default-keys</artifactId>
    <version>${quantum.version}</version>
</dependency>
----

WARNING: The default keys are published in the open-source repository.
Never use them in production.

**Option 2: Classpath keys (simple deployments)**

Place `privateKey.pem` and `publicKey.pem` in `src/main/resources/` of your application module.
The framework loads them from the classpath at startup and caches them in memory.
Outside the `dev` and `test` profiles you must still name them explicitly (`quantum.jwt.private-key-location=classpath:privateKey.pem` and the matching public-key property), or startup fails.

**Option 3: External keys via configuration (recommended for production)**

Store the keys outside the application artifact and configure their locations in `application.properties`:

[source,properties]
----
quantum.jwt.private-key-location=file:/etc/quantum/keys/privateKey.pem
quantum.jwt.public-key-location=file:/etc/quantum/keys/publicKey.pem

# SmallRye JWT validation also needs the public key path
mp.jwt.verify.publickey.location=/etc/quantum/keys/publicKey.pem
----

This approach allows key rotation without rebuilding or redeploying the application.
See xref:{doc-root}/user-guide/multiple-auth-providers.adoc#per-tenant-key-pairs[Key Pair Management] for the full configuration reference.

[[request-authorization-lifecycle]]
== Request authorization lifecycle

In `1.4.3-SNAPSHOT`, role augmentation performs blocking authority lookups on a
Quarkus authentication worker. Delegated application sessions can reuse the
same successful role resolution during REST admission in that HTTP request.
Reuse requires matching issuer, subject, user ID, effective realm, application
ID and token roles. A subsequent request resolves roles again, so this does
not introduce a cross-request authorization cache.

Provider validation and realm, application and tenant admission still run.
An internal immutable principal projection is available only after principal
admission; it is not a resource permission decision. Existing resource rules,
public provider interfaces, response formats and embedded custom role resolvers
retain their contracts. Embedded custom role resolution is not cached.

External tenant membership is a receiver-side exception to retaining signed role
authority: after tenant selection, `PrincipalContextResolver` reads the complete
realm assignment and replaces roles with `external` plus already-resolved own
user binding roles. This applies to credential, signed-token and trusted-claims
paths, including dedicated realms. Ordinary memberships retain their existing
role behavior. See xref:tenant-models.adoc[External members and rollout ordering].

When `quantum.auth.trust-token-claims=true`, augmentation and authenticated JWT
migration checks do not consult local credentials. Without an explicit
`X-Realm`, migration checks select the system realm for service tokens, or the
configured session realm / signed realm for user sessions. A missing required
signed realm is rejected. This selection does not authorize realm access.

Applications should continue using existing provider and property/role resolver
contracts. Request-state types remain internal. Realm selection also supports
the optional proposal SPI described below. Full shared authority provenance, coarse/fine
role parity and new session-policy extension contracts remain planned. See the
security-runtime README for the lifecycle diagram and test boundaries.


[[session-realm-proposals]]
=== Application-specific realm proposals

Implement `com.e2eq.framework.security.session.SessionSelectionPolicy` in an
application CDI bean to choose between a fixed workspace and a requested one.
Select its id and exact version using
`quantum.security.session.selection-policy` and
`quantum.security.session.selection-policy-version`. Both unset preserves legacy
behavior. Explicit missing, duplicate or incompatible selections fail startup.

The pure policy receives identity metadata and realm selectors and returns only
a realm proposal. It cannot grant membership, roles or application access.
Service and anonymous identities do not invoke it. Null realm means retain the
principal's realm; null output or blank realm fails the request. The framework
still admits the selected realm, application and tenant. See the security-runtime
README for a complete policy example and the two HTTP conformance fixtures.


=== Shared sign-in and independent application authorization

Authentication establishes identity under the trusted issuer and audience.
Each application still admits that identity using its own application binding,
realm and tenant membership and resource permissions. Being signed in is not an
application grant. A 401 indicates authentication failed; a valid identity may
still receive 403 because authorization fails.

The security-runtime cross-application HTTP tests send one unchanged signed
fixture through two independently configured application boots. They verify
foreign-application grant isolation, role revocation without token replacement, no local
credential lookup, and issuer/audience/signature/expiry rejection. Their shared
audience is explicit; do not broaden an application's audience to make a token
portable. Different audiences can require different access tokens while still
sharing an issuer sign-in session.

Keep application selection in request context and mutable grants in authoritative
services. Do not rewrite signed `azp` or add application-specific claim dialects
for workspace selection. Existing supported token claims remain compatible.

==== JWT compatibility and revocation boundary

An app-A token in the same signed realm takes different paths at A and B.
At A, existing delegated behavior retains signed token roles and signed-origin
application admission while the provider still accepts the token. At B, an
explicit application session re-resolves roles and checks application admission.
Removing the current assignment's roles or application grants therefore does
not establish immediate revocation at A. The cross-application tests now cover
both paths with an unchanged app-A fixture; they preserve this existing behavior.
Provider-specific revocation may reject a token earlier, but is not established
by these mocked-provider tests.

Do not change this default implicitly during an upgrade. Applications needing
current-authority checks on every request need an explicit freshness contract
covering both role gates and provider availability, with compatibility tests for
existing token-based consumers. Keep that authority outside the token; additional
per-app claims would not solve stale grants.

For JWT-based sign-in, validate the existing login/refresh provider and frontend
token handoff. Shared JWT identity does not require introducing OAuth browser
sessions. Browser handoff, logout and production-provider revocation remain
separate acceptance checks; these server HTTP tests do not prove them.
OAuth/OIDC protocol completion is optional work when applications actually use
those protocols, not a prerequisite for the JWT review.


=== Stable core and application extension ownership

The design intention is to let applications vary behavior without recurring
framework edits. Existing interfaces remain the default path; proposed future
features are not prerequisites for ordinary JWT authentication.

[cols="1,2,2",options="header"]
|===
| Application variation | Existing seam | Core invariant
| Login, validation, refresh | `AuthProvider`, `ClaimsAuthProvider`, factory configuration | Verified identity and existing provider/response compatibility
| Fixed application or workspace | `quantum.security.session.application-id`, `.realm` | Effective request context never rewrites signed claims
| Workspace choice beyond configuration | `SessionSelectionPolicy` | Proposal only; core membership/admission checks remain mandatory
| Embedded role derivation | `IdentityRoleResolver` | Roles retain authority and application/realm scope
| Delegated grants and membership | Existing directory/membership providers | No per-app credential store or authorization inferred from a selection callback
| Resource, action and data access | Existing `RuleContext` and policy records | Authentication alone never grants access
|===

Change the owning seam only when an agreed application behavior cannot be
expressed by the existing contract, demonstrated by a failing contract test.
Keep authentication, context selection and authorization distinct. Avoid parallel
validators, policy engines and token formats. No new extension is required merely
to enumerate future possibilities. Preserve existing defaults; a change in role
freshness or admission is an explicit behavioral change, not a transparent refactor.
