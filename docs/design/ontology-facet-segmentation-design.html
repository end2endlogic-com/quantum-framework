Section 1

The Reframe: Three Things Quantum Conflates

Quantum’s multi-tenant segmentation model has historically bundled three separate responsibilities into one monolithic concept: coordinate semantics, data carriage, and storage layout mechanics. Disentangling them is the fundamental move that removes the hard dependency on MongoDB while preserving physical isolation guarantees.

Concern What It Is Current Framework Reality Target Architectural Location
Semantics The multi-tenant coordinate (realm · org · account · tenant · dataSegment), hierarchy rules, and comparison axioms. Tied to Morphia base classes (FullBaseModel, UnversionedBaseModel) and persistence interceptors. Admitted ontology (TBox) + store-free pure POJO evaluation library (quantum-models).
Carriage How a given row, record, or entity acquires its multi-tenant coordinate. Implicitly assumed to be physically stamped on Morphia documents via bm.setDataDomain(dd). Declared per binding: constant, derived, or stamped.
Mechanics Realm-to-database routing, Morphia annotations, filter-string DSL, and CDI wiring. Hardwired into MorphiaRepo.getListByQuery(realm, ...) and MongoDB drivers. Stays in Quantum persistence tier unchanged; preserves physical database isolation.
The Core Architectural Shift: The segmentation model is a coordinate system and a comparison function. It is not a storage layout. Currently it appears to be a storage layout because getListByQuery(realm, ...) enforces realm at the API boundary and FullBaseModel physically stores bmFunctionalArea and bmFunctionalDomain.
Section 2

The Action Space Is Not the Ontology

Functional Area / Functional Domain / Functional Action describe an action that can be taken. Paired with an attribute-based filter, they define the data scope that action is permitted to touch.

Why Actions and Entities Must Remain Decoupled

Actions are coarse-grained and routinely span dozens of entities; entities are fine-grained and singular.

When a tenant administrator grants "View orders for Location ABC", they think in terms of business capability. Fulfilling that single grant requires reading Customer, Order, Shipment, Invoice, Inventory, and several relationship types. Requiring grants to enumerate the transitive entity closure would be brittle and unusable.

grant = capability(area, domain, action) × scopeFilter(facets)
data = coarse functional coordinate (match key)
+ facet values (scope evaluation)
+ ontology binding (meaning & lineage)

Three Structural Consequences

  • 1. Grant Coarse, Attest Fine: The administrator grants "View Orders"; the cryptographic execution receipt attests the exact four entities and three relationship edges traversed.
  • 2. Action-Level Pushdown Validation: If a facet declares pushdown: required, every source and entity reachable by the coarse action must be able to push the predicate down. If one bound source cannot, the entire action is refused at registration.
  • 3. Reachability Transparency: Reachability preview calculates all reachable entities and edge types up front, preventing accidental over-broad traversal before grants are finalized.
Section 3

Enforcement Is at the Edge: Staged Filter Maps

Permissions must be enforced as the ontology is traversed, not merely at the root entry collection. A principal permitted to query Customer reaches Order, Invoice, Location, and Supplier. Each hop is governed by its own entity-specific filter, and each edge by its own traversal rule.

// Resolution: Once per action, pinned to policy revision Map<OntologyEntity, EntityPolicy> entityFilterMap; Map<RelationshipType, TraversalRule> edgeRuleMap; // Application: Per hop during query execution Entering Node E → Apply E.rowFilter + E.fieldExclusions Crossing Edge R → Apply R.traversalPredicate

Two Lookups, Two Keys

Entity Filter (keyed by ontology entity): Determines which rows of that entity are visible, and which sensitive attributes are stripped.

Edge Rule (keyed by relationship type): Determines whether the relationship can be traversed at all. If denied, graph expansion prunes immediately before reading the target collection.

Four Traversal Invariants: (1) Unknown edge types are not traversable (fail-closed, edge analogue of onAbsent: deny). (2) Restriction is monotonic along a path (once a hop trims or masks fields, downstream hops cannot widen permissions). (3) Re-entry by another path unions and explicitly records which path authorized access. (4) Traversal carries a declared depth/fan-out budget to prevent unbounded graph expansion.
Section 4

Deep Dive: Customer → Order → Supplier Traversal

Consider the real-world scenario: A customer queries their orders and views supplier details. However, they should only see active, retail-approved suppliers, and sensitive wholesale financials must be redacted.

Multi-Stage Aggregation Pipeline Pushdown

⚠ Vulnerability in Current Framework

In MongoAggregationCompiler.java today, $lookup constructs an inner pipeline that only checks ID equality and tenant ID. It embeds the entire Supplier document wholesale:

// Current MongoAggregationCompiler: Unfiltered Hydration Document lookup = new Document("$lookup", new Document() .append("from", "suppliers") .append("let", letDoc) .append("pipeline", List.of(new Document("$match", matchExpr))) .append("as", temp)); // No stage-level row security. // No stage-level field exclusions. // Result: wholesaleCost and taxId leak into Customer payload!

✔ Target Staged Pushdown Execution

The target compiler consults the resolved Filter Map for each stage in the expansion tree. The inner pipeline injects both target row filters and field exclusions:

// Target: Security & Redaction Pushed Inside MongoDB pipeline: [ { $match: { $expr: { $eq: ["$_id", "$$suppId"] }, "status": "ACTIVE", "type": "RETAIL_APPROVED" }}, { $project: { "wholesaleCost": 0, "marginRate": 0, "taxId": 0 }} ] // Unapproved suppliers evaluate to null. // Sensitive fields never cross the database wire.

Historically, DataDomainPolicy and DataDomainResolver were used only on creation/write persistence (ValidationInterceptor.prePersist) and ingestion. The query engine bypassed policy and blindly injected the caller's login domain (${pTenantId}) everywhere.

Section 6

Relationship-Level Filtering & Grammar Extension

Relationships are rarely unadorned boolean pointers. In enterprise ontologies, relationships have qualifiers (roles, priority, capacity), temporal validity (start/end dates), and provenance (source system, derivation rules).

Grammar Extension (BIAPIQuery.g4)

Extend the ANTLR query grammar to accept an optional 3rd argument for edge qualification:

// Extended Grammar Specification hasEdgeExpr: HASEDGE LPAREN predicate=(STRING|TEXT|QUOTED_STRING|VARIABLE) COMMA dst=(STRING|TEXT|QUOTED_STRING|VARIABLE|OID|REFERENCE) (COMMA lp=LBRCE edgeFilter=query rp=RBRCE)? RPAREN;

Example: hasEdge("assignedTo", ${locId}, { role: "PRIMARY" && status: "ACTIVE" })

OntologyEdge Schema Enrichment

Formally equip OntologyEdge with open properties and compound indexes:

public class OntologyEdge extends UnversionedBaseModel { protected String src; protected String p; protected String dst; // NEW: Open edge properties map protected Map<String, Object> props; // Existing metadata now queryable protected boolean derived; protected boolean inferred; protected Map<String, Object> prov; }
Repository Pushdown: OntologyEdgeRepo.srcIdsByDst(dataDomain, predicate, dst, Filter... edgeFilters) pushes the edge property filters directly into the MongoDB query on the edges collection. Edges that do not satisfy the qualifier are discarded at the index level before source IDs are gathered.

Open-Set Facet Contract & Admission Guards

Rather than hard-coding tenancy axes into rigid Java fields, segmentation is expressed through facets. The facet set is open (domains can declare jurisdiction, contractId, retentionClass), but facet declarations are strictly admitted into the TBox with cryptographic hash pinning.

Section 8

Structural Realm Isolation vs. Logical Facet Predicates

This distinction must remain absolute or the fundamental security property that makes Quantum trustworthy is compromised:

Realm is an Admission Gate

Realm is resolved before query lowering. It selects the physical MongoDB database or cluster. A realm mismatch means the query is never constructed. Cross-realm joins are structurally unrepresentable, not merely policy-forbidden. Realm must never become a filterable facet.

Facets are Lowering Predicates

All other coordinates (orgRefName, accountNum, tenantId, dataSegment, and custom facets) are predicates in the plan. They compile into the stage-level $match filters inside that realm’s database boundary.

Section 9

Store-Free Decoupling & Second-Store Wedge

To fulfill the strategic goal of governing customer data where it resides (PostgreSQL, S3, APIs), coordinate resolution must not depend on a running MongoDB instance:

What Moves to Store-Free Core (quantum-models)

  • DataDomainPolicy & DataDomainPolicyEntry (already pure POJOs).
  • DataDomainComponentBinding.
  • DataDomainResolver interface and its default evaluation logic.
  • Facet declaration schemas and validation rules.

What Stays in Quantum Persistence (quantum-morphia-repos)

  • Realm-to-database connection pooling and routing.
  • Morphia entity mapping and change streams.
  • MongoDB aggregation pipeline compiler.
  • Provisioning and decommissioning lifecycles.
Section 10

Formal Invariants & Acceptance Testing

INV-01: Policy naming an unadmitted facet is rejected at registration with the literal named.
INV-02: Facet with no declared onAbsent defaults to deny; allow requires steward attestation.
INV-03: Pushdown validation is verified per-action across all reachable bindings.
INV-04: Realm is resolved before query lowering and cannot appear as a filterable predicate.
INV-05: A lowered query cannot be constructed without a resolved coordinate.
INV-06: Restriction along a traversal path is monotonic; downstream hops cannot loosen filters.
INV-07: Denied edges prune before target entity reads; withheld edges are named on the audit receipt.
INV-08: Sub-collections in $lookup must execute stage-specific $match and $project.
The Benchmark Acceptance Test: Execute a pilot against a customer’s PostgreSQL database, an S3 object store, and an external REST API—with zero MongoDB instances in the deployment—and produce a cryptographic receipt carrying an exact trim record naming every withheld row and stripped attribute.
