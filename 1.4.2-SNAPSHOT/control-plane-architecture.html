This is the deep dive on the control-plane/data-plane split introduced on branch the integration branch (design source: docs/design/CONTROL_PLANE_SPLIT_DESIGN.md; work plan: WP1 workstream B; compatibility contract: WP3). It explains what the quantum-system module is, why each contract lives where it does, what quantum.mode changes at runtime, and how the deployment tiers map to configuration.

1. Why a split

Historically every Quantum app owned a system realm (system-psa-com, system-b2bi-com, …​) holding credentials, the realm catalog, and tenant provisioning state, and exposed the admin REST surface that manages them. A multi-tenant platform deployment needs those concerns in ONE control plane — tenant lifecycle, identity, catalog, metering — while existing apps keep working unchanged. The split is therefore strictly opt-in: every existing app remains a valid embedded deployment forever.

2. Module layering

quantum-models          contracts & entities (Rule, Realm, UserRealmRole,
        ▲               FieldPolicyEnforcer, RoleSource, ...)
quantum-morphia-repos   repos + RuleContext (policy engine) + MigrationService
        ▲
quantum-system          CONTROL-PLANE module: SystemDirectory + local impl,
        ▲               RealmCatalogService, TenantLifecycle contract,
        |               QuantumModeConfig / SystemRealmOwnership,
        |               RealmMembershipService, metering contracts.
        |               No JAX-RS resources in this jar.
quantum-framework       app framework: REST resources, seeds/bootstrap,
                        startup coordination, TenantProvisioningService

Placement rules that shaped this:

  • Contracts sit as low as their consumers. MigrationService lives in quantum-morphia-repos and therefore cannot see quantum-system; instead of making it mode-aware it gained an explicit initializeStartupRealms(boolean includeSystemRealm) overload — mode is resolved above it and passed down.

  • quantum-framework depends on quantum-system (not vice versa), so every existing app’s classpath is unchanged and the control-plane contracts are available to all of them.

  • The embedded implementations are the defaults. TenantLifecycle is implemented by TenantProvisioningService by delegation — its existing signatures are untouched (WP3 rule: the contract mirrors, never replaces).

5. The admin REST surface

The physical quantum-system-rest jar split landed in 1.4.1-SNAPSHOT. Tenant applications omit that server module and therefore do not expose its security and control-plane endpoints. quantum-auth-service explicitly adds the module and publishes the API consumed through its generated SDK.

For deployments that include the server module, quantum.system-rest.enabled remains a build-time, default-true gate for the annotated control-plane admin resources. The next modularization step moves the resources' service closure (provisioning → seed subsystem and shared BaseResource REST infrastructure) below the server jar so it no longer needs the full quantum-framework dependency.

Control plane owns the system realm and identity; this app runs only app-realm workloads and validates JWTs against the control plane’s JWKS. the tenant-plane app is the reference deployment.

7. Identity in the split

Per the realm-membership ADR: users hold ONE global identity (credential in the system realm) plus per-realm role assignments (UserRealmRole). At token issuance the IdP unions the assignment for the target realm into the JWT’s role claims (CustomTokenAuthProvider.login), with role provenance exposed in the login response (RoleSource.REALM). The tenant plane validates via JWKS and routes by claims — no per-request callback to the control plane.

8. Field-level and relationship policy (one policy source, every egress)

The same rules that scope rows (andFilterString/orFilterString, including ontology traversals like hasEdge('assignedTo', …​)) also scope fields (excludedFields). Resolution happens once (RuleContext.getExcludedFieldPaths); enforcement is layered per egress: Mongo projection on reads, preserve-hidden-fields on merge, FieldPolicyEnforcer.mask for non-Mongo datasources, and the REST serialization interceptor as the last lock. See the Field-Level Policy section of permissions.adoc.
